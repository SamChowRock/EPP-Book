# 38A 登录事务遇到多实例和密钥轮换

单进程版本用五分钟的 Map 保存未完成的登录，数据库只留长期映射。这个选择很容易从“一个进程能用”被误写成“把 Map 换成 Redis 就能上线”。先不选技术，看看实际会丢什么，又有什么不能重复。

**时间参考（估算）**：阅读约15～22分钟。这里改变运行条件推导存储与信任策略，不要求另部署缓存或身份服务器。

## 把回调交给另一台机器

用户从实例 A 开始，在提供方输入密码，回调却由负载均衡器送到了实例 B。B 的 Map 为空，收到正确的 code、state 和临时 Cookie，仍没有 verifier，也不知道应该把哪个本地账号关联到哪一方。400 并不能证明用户没点同意；它准确表达的是“本实例无法证明这次回调的来历”。把没查到的 state 临时补成一条，等于让收到回调的人自行创造登录意图。

让负载均衡器暂时把同一个浏览器送回 A 可以减少偶发错误，却不能挽救滚动发布中被替换的 A。想允许用户重开一次就好，单进程失败关闭已经有明确的恢复办法；若承诺滚动重启不打断进行中的登录，就必须让接替者能取回仍有效的事务。数据至少包含 state 索引、浏览器绑定、期限、issuer、回调地址、nonce、verifier、登录或关联用途及本地证明。能读 verifier 的主体能参与兑换，不能因为表只活五分钟就公开给分析系统。

共享存储还必须表达**只有正确浏览器能取走这行，而且只取走一次**。例如 PostgreSQL 把下面的判断写在同一个语句里，而不是先 SELECT、比对完再 DELETE。下例是多实例设计示意，不是本章已建立的数据库表：

```sql
DELETE FROM pending_login
WHERE state_digest = $1 AND browser_digest = $2
  AND expires_at > clock_timestamp()
RETURNING verifier, nonce, purpose, expected_user_id;
```

设两个正确的回调几乎同时到。一个事务删除并提交，另一个拿不到行，只有前者可以兑换。换成知道 state 的另一个浏览器，它的 browser_digest 不符，一行也删不掉；真正发起者仍能继续。若存储工具只提供无条件“取走值”，再在应用中比较浏览器，知道 state 的人反而能把别人的登录机会消耗掉。还要有过期清理、容量、访问权限、不同实例一致的 Cookie 和代理配置。数据库时间或统一 TTL 比用各进程自己的单调时钟互减合理：单调时钟适合本机计算经过多久，不能把 A 的起点当成 B 的起点。

如果 A 已取走事务，兑换成功后尚未写本地映射便宕机，B 能不能给 A 自动补发同一个 code？不能。提供方的一次消费和本地提交没有共同事务。让用户取得新的证明，以稳定的 (iss, sub) 重查映射，就算上一次已经提交也不会重新分配用户。如果需求升级为“同一次尝试必须返回同一份结果”，先明确要回放的是否包含秘密会话令牌、谁有权取回它，再设计结果状态机。把 token 明文塞进重试回执，反而损坏了第33章已经建立的保护。

## 把同一份 JWT 送到另一个应用

想象两个应用都连同一个供应商，都能取到同一份公开密钥集合。攻击者把应用甲的真实 ID Token 放进应用乙的一次登录响应。数学验签可能成功，那只说明签发方用相应私钥签过这些内容；乙不是这份回答指定的受众，应当拒绝。再改变一项：受众也对，但这是一小时前另一次登录留下的证明。除了期限，还要用**这一次**的 nonce 核对。只用签名、只用邮箱、只用时间，这三种简化分别丢失了“给谁”“是谁”“哪一次”的某一部分。

再假设供应商轮换签名键。一个仍在缓存内的公钥集合找不到新 token 的 kid，不等于用户被封号，也不意味着客户端可以去 token 头里随附的 URL 下载公钥。kid 是在**已经信任的 issuer 的键集合**内挑键的提示，本身不提供信任。凭受信元数据，按库的缓存和限额规则更新 JWKS；没有可验证的匹配键就拒绝。对每个陌生 kid 无条件发起网络请求，会让无效输入放大成外呼风暴。排查时记录哪个受信提供方、哪一阶段和错误类别，不记录整份 JWT。

另一个变化更容易误判：供应商换了 issuer 地址，看起来组织、邮箱、显示名都一样。这是身份命名空间变化，不等于同一 issuer 的密钥轮换。原联合主键理应不匹配。若需要迁移，须取得双方稳定主体的可信对应关系，先核对一对多冲突和回退方式，再迁移映射；不因为地址长得像而批量把不同用户当成一人。

最后把问题换成本地撤权。签名依旧正确，用户也确实刚刚登录提供方，但 EPP 已关闭他的 Web 资格。本地账号状态在**本地**判定；多刷新几次 JWKS 不会使 403 变成有权访问。反过来，撤销 EPP 的会话不替其他应用撤销同一个人的平台会话。沿失败发生的那一层处理，才能把“可信身份”“当前登录尝试”和“此刻可做的事”分开。

| 名称 | 用途 | 判断边界 |
| --- | --- | --- |
