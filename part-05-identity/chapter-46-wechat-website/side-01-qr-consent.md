# 46A 扫了转发来的二维码，会登录哪台电脑

你在自己的电脑上打开 EPP，点“前往微信扫码”。手机显示了正确的应用名称，确认后回到自己的电脑，原素材可以读取。这时有两个事实碰巧同时成立：发起请求的浏览器在你手边，你也打算把自己的身份交给这台电脑。把二维码换成聊天里别人发来的截图，这两个事实还能从请求中看出来吗？

## 把同一个流程换一台电脑

设甲在甲的电脑上开始普通登录，电脑保留了 EPP 的临时 Cookie。甲把微信授权页上的有效二维码发给乙，请乙“帮忙扫个码”。设平台允许这次跨屏扫描，乙在手机上确认，平台完成的是**甲那次请求**。甲的浏览器持有正确的临时 Cookie，返回的 state 也属于甲；服务器的浏览器绑定、一次领取和兑换检查都可以通过。平台返回的却是乙的网站 OpenID。如果乙已经关联 EPP 且有网站资格，甲的电脑就可能取得乙的 EPP 会话。

和正文中“把回调链接发给别人”的例子对照。转发回调链接时，收到链接的浏览器缺少临时 Cookie，服务端有可检查的差异。转发待扫二维码时，电脑一直是原来的电脑，换的是手机上确认的人。EPP 收到的每一份机器证明都可能属实，仍不能从它们推断乙和甲坐在一起，或乙理解自己在授权哪台电脑。把 state 从 32 字节增加到 64 字节，或缩短二维码寿命，都不能区分有效期内的这两种确认。

关联比普通登录影响更久。假如甲选择关联，输入的是甲自己的 EPP 密码，乙的微信身份尚未建立映射，则两项证明可能使乙的微信与甲的本地账号关联。稍后乙自己普通扫码，可能看见甲的账号。这解释了为什么页面要明确告诉用户正在**关联已有账号**，为什么发现冲突要停在 409，以及为什么用户自己没有发起的网站登录不能代扫。已经存在的冲突映射由唯一约束保护，尚未绑定的身份没有那道冲突可供检测。

## 保留浏览器和 state，只换授权码

还有一种失败甚至不用转发二维码。设乙在自己的浏览器完成授权，回调还没有抵达 EPP，其未用的 code 已被甲取得，例如能读取完整跳转 URL 的代理日志在兑换前泄露。甲在自己的浏览器也发起同一网站应用的登录，然后用甲的 state 和 Cookie 提交乙的 code。甲无需知道乙的 Cookie 或网站 secret，兑换由持有 secret 的 EPP 完成。攻击需要有效且未使用、可在同一客户端兑换的 code，还要抢在乙之前提交；只知道一个已兑换的旧码不够。

在已构建的第46章配套工程和已迁移的独立 VERIFY 中执行：

```bash
unset DATABASE_URL TEST_DATABASE_URL
verify_db='epp_ch39_verify'  # 换成建库或恢复时独立选定的实际库名
NODE_ENV=test node --env-file=.env.test --input-type=module -e '
await import("./test/database-env.mjs");
const { withVerifiedDatabase } = await import("./scripts/verify-database.mjs");
await withVerifiedDatabase(process.argv[1]);
await import("./test/wechat-web.test.mjs");
' "$verify_db"
```

打开 `test/wechat-web.test.mjs` 中的 `fromA`、`fromB`。A 已关联开通的原用户，B 属于另一个本地账号。两笔普通登录各有自己的 Cookie，两次模拟授权都停在 303 尚未跟随的位置。先把 A 的整条回调交给 B 的浏览器，返回 400。现在只把 A 的 code 填进 B 的回调地址，仍用 B 的 Cookie 发送。这次返回 303 和新会话；在 B 的浏览器用它查 `/auth/me` 得到的是 A 的原用户 ID，再按原 captureId 读素材竟然返回 200，内容和关联前相同。再送原 B 回调是 400（B 的本地事务已领走），再送原 A 回调是 401（A 的 code 已被消费）。实验直接取得两端的跳转结果以设立泄露条件，只验证这套本地协议模型的边界。

在 S256 流程里，提供方签发 B 的 code 时已经记住 B 的 challenge，兑换时会将 A 的 verifier 散列后比较，拒绝错配。网站适配器只向固定端点出示应用凭据和 code；随机 state、临时 Cookie 和单次领取仍各自有用，但没有承担这项逐笔兑换检查。对授权页、回调和代理日志隐藏查询参数，限制跳转、使用 HTTPS 并及时消费，可以减少获得活码的机会；若业务必须在授权结果泄露后仍能拒绝替换，就需选择有可验证逐笔绑定的协议或另行设计足够独立的身份证明。即使采用 PKCE，转发**原来那笔**二维码由他人扫码时 challenge 仍一致，前节的确认风险仍然存在。[RFC 9700 第 5.5 节](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.5)

## 按权限大小决定还要确认什么

个人素材站点可以在发起页提示“只扫自己刚在电脑上打开的页面”，让用户在会话列表查看新设备、撤销可疑网站会话。撤销会话只终止那份令牌。如果错误的长期身份映射仍在，普通登录还可以再发新会话。处理误关联要分别查这次发给哪个本地用户的会话、哪条映射是这次新建的，以及该账号还有没有可用的恢复方式。核对双方证明后依账号恢复流程处理，避免删除用户和旧素材。[第 44 章支线中的解绑与恢复](../chapter-44-mini-program/side-01-account-linking.md)

如果业务改成“用手机批准把团队资料导出到某个邮箱”，登录结果只告诉服务端操作者是谁。批准导出还必须让确认者看到目标资料库、接收邮箱和实际动作。由 EPP 保存一笔短期操作，将确认绑定到这笔操作和完整参数，执行前再查当前权限；邮箱一旦改变，原批准也应失效。普通授权页没有受本地业务约束的字段可表达这层意思。即使改用能在两端显示同一短码的自有确认页，短码也只能帮助用户比较正在看的两次显示；有人把短码连同二维码一起转发时，仍要依靠用户识别动作与目标。权限越大，越需要限制会话能直接执行的操作，把额外证明确实用在危险动作上。

回到本章，平台顶层授权适合网站登录，重复登录复用映射，受限账号拿不到新会话。遇到“用户刚才明明确认过”的新需求，先把确认内容写出来：确认本网站取得微信身份、让一台电脑取得本地会话，还是同意执行指定操作。三者需要的证据和留下的持久状态不同。

## 附录：本支线必要技术点速查

| 条件变化 | 服务端能观察什么 | 怎样处置 |
| --- | --- | --- |
| 回调链接换浏览器 | state 可相同，临时 Cookie 缺失 | 兑换前拒绝，新浏览器重新开始 |
| 在同应用两笔事务间替换未用 code | 浏览器与 state 匹配，兑换返回另一主体 | 核对是否存在逐笔绑定，防止回调参数泄露 |
| 二维码转发给另一个人扫描 | 原浏览器和 state 仍匹配 | 提示确认对象，限制会话权限，提供撤销与恢复 |
| 登录升级为具体业务批准 | 登录证明缺少动作和目标 | 绑定一次操作、完整参数与期限，执行时复查权限 |
