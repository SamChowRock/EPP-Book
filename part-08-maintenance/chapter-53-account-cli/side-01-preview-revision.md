# 53A　如果审批只对预览时的状态有效

本章的预览可以在午饭前做，执行可以在午饭后做。假设维护者的授权是“把甲的 Web 资格设为关闭”。执行时有人已经关了，写一张前后都是 false 的收据就完成了工作。现在换一条审批要求：“只有账号处置情况跟我签字时完全一致，才允许执行。”即使操作 ID 从未用过，原命令也可能越过这条要求。

考虑三个时刻。九点预览时 web_enabled 为 true。十点有另一单暂停，十一点复核后恢复，值又是 true。十二点第一次执行九点那张单。把 SQL 改成“仅当 web_enabled = true 才更新”，此时还是会成功。若审批只要求**眼前的值**相同，这已经够了。若复核决定使旧审批失效，就得让执行端看到中间发生过变化。Web 位只有两种取值，无法讲述这段历史。

一种做法是在用户行增加权限修订号。迁移给所有旧账号一个起始值；从启用这套协议开始，每个改变审批依据的写入者都在同一事务里递增修订号。预览返回当前版本 8。相继暂停、恢复把它推进到 10。命令带上“我获准基于第 8 版操作”，拿到用户锁读取 10，就拒绝写、返回需重新审批。这里要先定清审批范围。如果停用整个账号也会使这张批准单失效，写 status 的入口同样必须推进这个版本；如果改昵称不影响审批，就不该因昵称变化取消决定。只在 CLI 增加计数，允许旧 SQL 直接改资格却不推进计数，无法兑现这个承诺。

为什么不在预览时就锁住账号，等人签字才提交？签字可能耗上一天。连接池先占一席，同一行的后续资格修改也得等，签字人合上电脑还需要处理连接中断。短事务比较版本，把冲突变成一次明确的重新审批，付出的代价是多一个持久字段、覆盖所有写入入口，以及人工处理真正冲突。

执行顺序也变了。仍先确认目标并锁住账号，再查同一操作键是否已经完成。假如第一次基于 8 成功提交，自己已把版本推到 9，回执却丢失。若重试时先检查版本就会把自己的成功误报为审批过期。查到收据须同时核对目标值与批准版本，吻合才返回原结果。只有首次办理才比较批准版本与当前版本，再更新资格、推进版本并记收据。新审批分配新 ID，原单不能悄悄换成新版本重试。要证明由谁批准，还得把可信审批身份绑定到目标、操作及版本；操作人自己填个 8 只能传递条件，不能证明有人授权。

回到眼前的 EPP，维护者获准设置一个账号的目标值，按操作键找历史，再按账号读当前事实，已足以解释下午为何保持恢复。若需求出现“只按这一版执行”，先问清楚哪些变化会使授权失效，再决定版本放在哪里。到那时，需要改变的是写入契约和审批依据，单给预览多印一个时间戳没有这种效果。
