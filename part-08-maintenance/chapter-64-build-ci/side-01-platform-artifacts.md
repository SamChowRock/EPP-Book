# 64A　同一份锁文件能复用哪一层产物

假设你已在 Mac 上验证账号 CLI，接班人的任务改成“把同一提交交给 Linux 主机运行，明天还能退回今日版本”。你给他一个 Git 提交、一份 package-lock.json 和 Mac 上的 node_modules，哪一样解决的是回退问题？

先看实际依赖。sharp 的 JS 入口需要能在当前系统加载的原生库。Biome 也按平台选择二进制程序，不过它只参与构建。锁文件能同时记录 macOS arm64、Linux x64 等候选包的版本和完整性摘要，安装后的目录只包含当前平台需要的那一部分。换一台 Linux 主机，再问它能不能执行 Mac 的二进制，答案已经与 JS 源码无关了。Linux 上还要考虑 CPU、系统库及所用 Node 版本的兼容条件。从“同一个锁文件”推不出“两个安装目录的每个字节都相同”。

为什么 workflow 可以缓存 npm 下载内容？假设库里有两个平台的压缩包，当前 npm 按锁选择所需条目，缺少的去下载，命中时仍按完整性信息校验。缓存能减少获取成本；清除缓存后，在依赖来源仍可用的前提下，干净安装应当仍能完成。若缓存的是已经展开的 node_modules，命中后直接跳过安装，平台、Node、安装策略甚至某次残留文件都成了成功的隐含条件。只有明确这些输入、用它们隔离缓存键，还保留未命中时的正确路径，复用安装结果才有可靠依据。

再看今日的验收到底对应哪份东西。团队上午在 Linux 构建并验证 A；晚上重新检出同一提交，在另一台机器重打一次包 B。如果部署记录只写了提交号，出问题后无法证明运行的就是上午检查过的那些字节。编译器、基础镜像、原生依赖、安装时脚本及环境的变化，都可能进入第二轮。若“验过哪份就发布哪份”成为要求，可以在目标平台构建完整运行制品，给它记录摘要、平台、源码提交及检查结果，后续按制品身份晋级。运行时的数据库密码、HMAC 密钥与服务地址仍由环境注入。打包前把本机 .env 一同拷进去，会把一次交付变成一次秘密分发。

回退时再换一个条件：旧程序启动成功，库里却已经执行了旧版本读不懂的新迁移。把二进制换回来只还原了程序，不会自动还原数据库、在途任务或对象。发布前要在副本用旧数据跑升级，并按预计的回退版本读写验证。需要跨版本共存时先扩展结构、再逐步切换读写，确认旧读者退出后才能收缩。备份能参与恢复，但恢复至过去的时刻还会影响之后已经接受的业务写入。这里不能从“有旧包”直接得出“可以无损回退”。

第 64 章只有一套单包服务，交付实验用干净目录和一次性库，足以抓到缺配置、运行依赖误归类、生成文件滞后这几类错误。读它的 CI 结果时可以明确哪些事仍需另做：新的目标平台要实际运行，承诺发布同一字节要保留已验证制品，承诺数据回退要有经过验证的兼容或恢复路径。下一篇部署时，这三项各有自己的记录对象。
