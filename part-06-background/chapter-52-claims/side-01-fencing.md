# 支线 52A　工作超过租期：续租和围栏各自保护什么？

一份批量导出通常耗时两分钟，偶尔碰上大客户要二十分钟。把第 52 章的三十秒租期调到半小时，看起来两头都解决了：几乎不会把健康的执行者错当成过期。可如果进程领取后第一秒就断电，用户要白等将近半小时。反过来，固定三十秒，每份正常报表都可能被重复计算。一只钟同时承担“别太早判死”和“尽快接手”，两个目标会相互拉扯。

先问报表能不能拆。假如能按稳定的记录范围分段，每段只读同一个输入版本，把最后已提交的位置与该段产物一起保存，那么崩溃后只要重做最后一段。拆分也有条件：若每次都按不断变化的表做 OFFSET 分页，两次读取之间新增了行，所谓“已经完成前一千行”就可能指不同的内容。得先固定输入身份、顺序和覆盖范围；若算法必须一次看完全量，硬拆成片反而会改变报表含义。

对于还在工作的长任务，可以允许持有者在截止前**续租**。例如给三十秒租期，每十秒尝试延长一次。领取身份仍是当次 UUID；续租须在取得行锁后同时检查身份、状态和旧期限仍有效，再用数据库的当前时刻计算下一期限。更新零行表示应停止推进，不能“我还活着，所以先改回自己的名字”。如果续租只按消息 ID 更新，A 睡过头后醒来会给 B 的领取改期限；若还把所有者改回 A，就直接夺走了 B 的授权。只查领取身份又有另一处缺口：即使没人接手，已经失效的 A 仍可能续活自己。即便还没有 B，允许过期者复活也会让“过期意味着什么”随操作顺序飘忽。本章选的是失效即失效：需要重新领时就换身份。

心跳是所有者最近有机会联系数据库的证据，不是任务真的前进了十页。一条专管续租的定时器可以在导出逻辑卡死时一直正常工作；反过来，CPU 密集工作若堵住同一个 Node 事件循环，任务虽在计算，心跳却发不出去。可以把可恢复的进度与续租一起登记，同时限制无进展时长；不得因多发一个心跳，就把不再属于自己的结果公布出去。若用户只容许等待一分钟，要用健康运行和进程退出两种情形一起检验方案，不能单靠调大超时。

现在改一个约束：结果要写到另一个服务的“当前报表”，读者总从同一个名字取文件。A 持第 7 代授权把报表算完，写文件的网络包延迟；B 已持第 8 代写好新版。A 最后才到。两个随机 UUID 只回答“相同吗”，目标服务单看两个陌生 UUID 不知道哪一个更新。在**同一数据库**中，我们可以直接检查当前保存的 UUID；面对一个独立的写入目标，若它支持版本比较，则可在每次接手时由可信的持久化计数分配递增代数。目标为同一份报表原子地记住已接受的最大代数；见过 8 后拒绝 7。这道由**目标执行**的检验常称为围栏（fencing）。相同代数重放时是否允许，要另按操作身份和内容判断；晚到的同代不同内容不能只凭“相等”放过去。

还有比要求文件服务懂围栏更简单的做法：A、B 各写自己的不可变文件，最后只在本库用当前领取身份有条件地切换“哪一份对读者可见”的指针。A 失权最多留下一个待清理的孤立文件，无法覆盖 B 的已发布文件；代价是额外存储、清理，以及读者必须沿指针读取。若承诺的是发邮件或一次计费推理，就没有一根可在本库原子切换的发布指针。把数字 8 塞进邮件头、日志或本地表，而对方不会据此拒绝旧请求，不能产生围栏。若对方支持同一业务键去重，它解决的是同一动作的重复；单调围栏解决的是对同一资源的新旧写入顺序。两者目标不同。

回到验证邮件：短小的准备步骤可以在过期后安全接手，通道的外部副作用却无法靠本地续租消除。前者适合用随机领取身份做条件更新；后者靠保留 attempting 与通道占用，让下一位执行者知道应该停在哪里。报表方案只有在能隔离产物或目标能比较版本时才能直接迁移回来。

## 附录：本章必要技术点速查

| 问题 | 应查的条件 |
| --- | --- |
| 续租 | 本代身份、尚未过期、允许的工作阶段；等锁后再查时刻 |
| 围栏 | 代数对同一资源单调；真正写资源的一方能原子比较并拒绝旧代 |
| 分段／发布指针 | 输入范围稳定、分段结果能恢复；产物不可变，切指针受当前身份保护 |
| 外部去重 | 去重键代表业务动作，涵盖重试窗口和相同内容；不能推导任意新旧写入顺序 |

可回查 PostgreSQL 18 的[事务内行锁](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS)。外部目标为什么必须参与比较，可对照 Martin Kleppmann 的[迟到写入与 fencing token 原例](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)。阅读约 9～12 分钟。
