# 支线 56A　如果离线期间的每一步都要重放

同一条通知在手机上被标记已读，随后又被清除。电脑关机一晚，第二天打开收件箱。只要这条通知从列表消失，页面就已经追上了当前状态。现在换个需求：用户要查设备离线时发生过的每次操作，包括哪条通知何时被标记、何时清除。重新拉取列表只得到一个空结果。即使把首页到末页全部翻完，也无法从空列表还原那两个动作。

## 用什么表示“我已经处理到这里”

逐项重放需要一份按顺序追加的历史。可以为每次动作保存账号、事件 ID、通知 ID、动作种类以及回放所需的最少数据。同一动作重试时沿用原事件 ID，并对这个 ID 加唯一约束，避免多记一笔。同一通知先标记后清除，要留下两个不同事件。还要有一个位置，让读取者可以说“请从我已处理的位置之后继续”。第 55 章列表游标回答的是“从哪一条之后向旧记录翻页”。它绑定了查询条件，也允许清除后的条目从结果中消失。把它复制到 SSE 的 `id:` 字段，并不会让刚消失的动作重新出现。

为什么不给动作表加一个自增主键就完事？设同一账号有两笔并发事务，分别处理不同通知。电脑上次处理成功的位置是 40。

| 时刻 | 写入 A | 写入 B | 重连的设备 |
| --- | --- | --- | --- |
| 1 | 从序列取得 41，插入后停在提交前 | | 查不到 41 |
| 2 | 仍未提交 | 取得 42，插入并提交 | 查到 42，把已处理位置推进到 42 |
| 3 | 提交 41 | | 按“大于 42”再查，永远跳过 41 |

即使 41 和 42 最终都提交，中间那次读取也足以漏事。一直等待所有号码连续到齐同样行不通，事务回滚会消耗序列号。随机 UUID 可以判断“两次看到的是同一事件”；按毫秒时间加 UUID 排序可以解开同一时间值的并列。两种方法都允许先取值的事务后来才提交。**推进到位置 P 时，必须能确定以后不会再出现本应排在 P 以前的新事件。** [PostgreSQL 18 序列函数](https://www.postgresql.org/docs/18/functions-sequence.html)

可以在第 56 章的独立练习库把表中这三步做出来。打开两个 DBeaver 编辑器 A、B，各自执行 `SELECT current_database(), pg_backend_pid()`；库名相同，PID 必须不同。两处都用自动提交，A 用显式 BEGIN 拉开时间。先在 B 建一张仅用于本轮的普通表，让两个会话都能看到它。如果表名已占用，就换一个新名字并替换下文各处。

```sql
CREATE TABLE public.ch47_replay_demo (
  position bigint GENERATED ALWAYS AS IDENTITY (START WITH 41) PRIMARY KEY,
  action text NOT NULL
);
```

在 A 选中下面两句执行，看到 41 后保留事务：

```sql
BEGIN;
INSERT INTO public.ch47_replay_demo(action) VALUES ('read') RETURNING position;
```

在 B 分别执行下面两句。INSERT 已自动提交，SELECT 只有 42。假设客户端把 42 保存为进度：

```sql
INSERT INTO public.ch47_replay_demo(action) VALUES ('clear') RETURNING position;
SELECT position, action FROM public.ch47_replay_demo ORDER BY position;
```

现在才在 A 执行 `COMMIT;`。回到 B，先查 `WHERE position > 42`，再读全表。

```sql
SELECT position FROM public.ch47_replay_demo WHERE position > 42;
SELECT position, action FROM public.ch47_replay_demo ORDER BY position;
```

前一条返回零行，后一条包含 41 和 42。这个结果把“尚未提交”和“游标永远跨过去”分开了。要在中途退出，先在 A 结束事务；对照完毕只删除刚才在练习库创建的表：`DROP TABLE public.ch47_replay_demo;`。

对于一个只需**每账号有序**的历史，可以给每个账号预置一行普通计数器。每笔业务事务先更新该账号计数器 `position = position + 1 RETURNING position`，再用返回值追加历史，连同这次业务修改一起提交，约束同账号的位置唯一。第二个写入同一账号的事务必须等第一个事务释放行锁：A 提交后 B 才取得下一个位置；A 回滚时计数器和历史一起撤回。同一账号的热点写入因此会排队，不同账号的计数器可独立推进。这种顺序只覆盖遵守同一写入路径的操作。若采用独立日志系统，也要说清业务提交如何可靠地交给日志，以及偏移量只在哪个分区内有意义。[PostgreSQL 18 行级锁](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS)

## 从最后一次处理成功的位置继续

假定客户端本地已应用到 40。恢复时，服务端按当前会话确认账号，以该账号为查询条件，从 40 之后升序分批返回事件。即使重放改走 HTTP 分页、实时唤醒用 SSE，两条路径也能读取同一份历史。处理并保存完一批再从本批末尾查下一批，新提交的行会排在末尾之后。追平以后，实时信号只负责叫醒查询；在订阅成功后再查一次，且定期从已处理位置补查，堵住“刚读空、还没开始监听”以及信号丢失留下的空档。

假如浏览器收到了 41，处理函数还在写本地数据库时页面崩溃。原生 EventSource 可在同一对象自动重连时携带最近的事件标识 `Last-Event-ID`，浏览器无需等业务写入成功才记下这个值。重新打开页面还会创建新的 EventSource。要求逐项处理时，恢复入口应从应用自己保存的进度起步。例如让普通分页接口接收已应用位置，用一个本地事务把“已应用 41 的结果”和“进度 41”一起保存。提交前退出时仍从 40 取，提交后退出时从 41 取。遇到重复 41 可按事件 ID 忽略。若处理动作还会调用外部服务，而对方支持幂等键，可让它用事件 ID 识别重复，并按对方保存去重记录的期限设计重试。对方未提供这种保证时，崩溃后应先核对外部结果。[HTML 标准中的 EventSource](https://html.spec.whatwg.org/multipage/server-sent-events.html#the-last-event-id-header)

进度还属于某个读取者。手机已经处理到 73，电脑上的本地视图却可能只到 40。用账号下所有设备共享的一个“最后收到”覆盖本地进度，会使电脑跳过 41～73。恢复请求既要验证当前身份，也要将进度约束到同一账号、同一条历史和相应读取者。登出或切换账号时清掉旧索引和订阅，不能用持有旧位置证明今天仍有读取权限。若历史涉及团队资源，回放时还要按产品约定处理已撤销的资格和允许保留的字段；仅在最初订阅时鉴权，可能把已失去权限的内容送回旧设备。

## 历史已经清理时，能恢复什么

假设按账号保存最近七天事件，最早尚存的位置为 80。停在 79 的设备还能拿齐后续事件；停在 40 的设备已经缺少 41～79。每批读取都要在同一快照里检查仍可接续的最早位置并取事件。即使第一批读得到，客户端暂停期间清理也可能追过它。发现缺口就返回进度过旧及恢复入口。若调用方只需要重新构建当前视图，可以在同一数据库快照读取该账号的状态以及位置 H，用这份结果替换本地视图，再从 H 之后接续。若先读状态，稍后另查最新 H，夹在两次读取之间的修改会被错误地标为已应用。多页快照也要属于同一个版本，普通活列表逐页读取无法给出这项保证。

如果七天里没有新动作，清理可能把这个账号的历史行全部删光。`MIN(position)` 此时为 NULL：从没产生过事件，和已经写到 90 又全部清掉，表里看起来一样。为每个账号持久保存“已清理到的位置” F（初始为 0），只清除连续前缀，并在同一事务推进 F；计数器仍保存已提交的最高位置 H。服务端在同一快照比较客户端位置 P 和两个边界：P 小于 F 就已缺历史，P 等于 F 可以从下一条继续，P 大于 H 则须核对进度所属的账号与历史。即使已清到 F = H = 90，停在 89 的设备也必须走恢复入口，停在 90 的设备可以安全等待 91。只看这次查询返回零行，分不出这两种结果。

若合同要求逐项说明哪个动作发生过，快照只能恢复工作界面，无法补出 41～79。需要延长可查询历史的期限、准备受同样权限约束的归档，或明确最长支持离线多久。首次上线也要约定历史起点：昨天还没有记录动作，今天开始发事件，无从倒推出昨天的操作顺序。

回到 EPP，打开收件箱需要的是当前账号此刻可见的条目。允许几秒或更长的延迟时，页面也可以在回来或定时刷新时查询；希望页面保持打开时更早获知变化，就保持一条 SSE 连接。如果后来要在同一连接里双向交换高频命令，再考虑 WebSocket。换传输方式会改变连接和收发代码，前面那笔晚提交的 41、尚未保存的本地进度和超期的历史仍各自需要处理。

## 附录：本章必要技术点速查

| 遇到的问题 | 应回查的事实 |
| --- | --- |
| 同一事件出现两次 | 业务重试是否沿用事件 ID，处理结果和进度是否一同持久化 |
| 断线后漏一条 | 位置是否按可见顺序推进，尾部唤醒和补查是否接得上 |
| 切换设备、账号或团队 | 这份进度属于谁、哪份本地状态，当前还能读哪些历史 |
| 离线超过保留期 | 最早可用位置、可恢复的快照版本，是否仍能取得逐项历史 |
