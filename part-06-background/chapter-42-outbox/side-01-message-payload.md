# 42A　发件箱里该保存当时的值，还是一条引用？

产品想在用户修订素材后给本人发邮件。原文改成了第二版，一秒后又改成第三版。处理程序晚了两分钟才醒来。假如发件箱只写了 captureId，两条任务都会查到第三版。究竟算不算事故，取决于邮件打算让读者相信哪件事。

**“你有一条更新，点开查看。”** 两封信的入口都指向当前素材，在这个约定里读到第三版是合理的。甚至可以把同一用户对同一素材尚未发送的提醒合并。合并依据是用户只需要知道有更新，必须保留的每次修改已经在修订表中。若素材在排队期间删除，或归属变化，先按当前身份和权限检查，再决定跳过。链接打开时仍需授权，邮件中少放一段原文也减少向旧邮箱泄露内容的机会。

**“这是你在十点确认的版本。”** 这里邮件承诺的是一个历史事实。在第 22 章的模型中，一次修订有自己的 ID 和不可变内容。业务事务既追加第二版，也留下指向**这个修订 ID** 的消息，后来追加第三版不会改变第二封承诺所依赖的内容。按 captureId 查最新修订会出错，用第二版的 ID 查则能重建当时的原文和意图。前提是旧修订的保留时间覆盖积压和恢复时间。如果消息允许一个月后才补寄，修订却在七天后清理，数据库里一条合法引用也无法恢复正文。可延长被引用版本的保留期，或把本次承诺的必要字段随任务做快照；快照要承担额外的个人数据保留、访问限制与清理责任。[第 22 章的修订记录](../../part-04-consistency/chapter-22-revisions/chapter.md)

再改一次条件：争议处理要求能复核当时的展示金额，而模板后来更改了舍入规则。只存金额输入和修订 ID 仍会用新规则生成不同正文。此时要保存当时的结果、币种和适用规则版本；若承诺的是逐字相同的文档，则需保留那份文档本身或可严格复现的模板、数据与渲染版本。消息的版本字段帮助新程序读懂旧载荷，无法替事后才想到的事实补录历史值。反过来，保存完整文档用于一次普通更新提醒，会把并不需要传递的内容留在另一个系统里。

**把判断带回验证邮件。** 验证意图同时具有两种时间要求。收件地址、用途和签发代次属于当次申请，要固定；过期、消费、重发及凭据是否仍有效，依赖执行或确认时的状态，要重新检查。本章消息把这两部分接起来。若改为每次发送都查“这个用户当前使用的邮箱”，在地址变更时可能把旧恢复机会交给新地址。若反过来只看快照，旧请求又可能越过已经发生的重发或改密。从同一条业务记录发出两种时间语义的邮件，值得用不同消息类型命名、分别约束其载荷。

如果渠道要求用同一外部操作号重试完全相同的请求，还要保留稳定的消息 ID 以及构造同一请求所需的数据，并查明对方是否承认该操作号、在多长时间内去重。SMTP 的接受应答本身没有作出这种承诺。第 42 章选择允许用户重新申请，因而可以推迟生成秘密，并在结果未知时停下。换成付款收据、具有法律效力的通知或不可重复的扣费指令，就必须先改变恢复契约，不能直接复用“换一枚令牌再发”的做法。

## 附录：本章必要技术点速查

| 选择 | 它依赖的前提 |
| --- | --- |
| 当前实体引用 | 接收者要看执行时的当前状态，并能处理删除或权限变化。 |
| 不可变版本引用 | 承诺当时的内容，版本在消息有效期内一直可取。 |
| 随消息保存快照 | 后续源数据或渲染规则可能变化，允许为这一目的保存必要内容。 |
| 签发代次与执行前复查 | 固定本轮申请的对象，同时尊重稍后发生的失效条件。 |

外部接受责任可回查 [SMTP RFC 5321 第 4.2.5 节](https://www.rfc-editor.org/rfc/rfc5321#section-4.2.5)。阅读约 10～14 分钟。
