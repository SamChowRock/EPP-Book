# 支线 46A　一条公告发给十万个人，要写多少行？

主线的一次注册只关乎一个用户。现在运营要发一则停机公告，十万名用户都可以看，且每个人都可以自己划掉它。如果把十万人当成一个“公共账号”，给它一条带 read_at 的通知，第一个点开公告的人就会替其他九万九千九百九十九人标成已读。先想清楚：公告正文属于发布者，阅读与清除属于“某个收件人对某个公告”的关系。这两个事实的行数可以不同。

**发布时展开。** 公告表保存正文和版本，收件箱保留 (announcement_id, user_id) 及每个人的状态。若要求“发布时具有资格的十万人以后都能补查”，应先固定受众，例如保留一份按组织成员版本确定的名单。分批按稳定的成员键读取，使用 (announcement_id, user_id) 唯一约束，插入本批投递与推进检查点在同一事务中提交。一次事务写十万行会拉长锁持有和回滚时间；拆批以后要接受一部分人先看到、另一部分稍晚看到。批次在第42,000人处退出可以重取尚未确认的范围。不固定名单却用会变化的成员列表和 OFFSET 接着扫，会因有人退组而发生位置前移，漏掉一部分应收人。

这种做法把成本放在发布时。用户开收件箱只需沿个人索引查；发布者也能回答“当时给哪些账号生成过收件项”。若十万人中只有两千人打开页面，也已经为其他九万八千人付了写入和保留成本。可以把正文只存一份，各收件项引用公告版本。若允许发布后原地修改，阅读回执只能说明用户看过某个公告 ID；需要证明看的是修订前的条款时，版本必须进入回执身份。

**打开收件箱时合并。** 若产品承诺是“有效期内登录的当前成员都能看”，可以只写一条公告。用户打开列表时取当前符合条件的公告，左连接以 (user_id, announcement_id) 为键的个人回执。没有回执表示尚未记录操作，页面第一次标记已读或清除时才创建回执。并发更新时，读取的一方不能把另一方刚写的 cleared_at 覆盖回空。只关心少量活跃用户时，这条路省去大批写入；代价落到每次查询的资格判断、两类来源的排序与分页。

两种来源合并时也要有统一顺序。各取第一页、分别前进一整页的游标，再把结果合起来截十条，会把某个来源已经跳过、实际上没显示的条目丢掉。可以统一按 (展示时间, 来源, 来源内 ID) 排序，对两个来源都应用**最后实际展示的边界**再取下一页；若坚持保留两只游标，两边只能分别前进到已经消费的位置。时间相同的行还需要稳定的来源和 ID 打破平局。权限、清除和有效期仍要在各自的候选查询中先过滤。

改变一个条件就会改变选择。一个用户在公告发布后才进组，展开的历史名单不包含他；按当前资格合并则理应让他看到。又如某人先清除公告，随后退出再加入同一组织，他是否应重见这一条？若视为同一公告，就保留独立于成员关系的个人回执；若重新入组本身触发新的确认义务，回执应包含这次入组或公告版本。要按人数和访问频率算开销，更要先请业务确定这两个例子的预期结果。

回到 EPP。注册或重置有明确且唯一的账号，事件 ID 同时标识一份个人通知。让十万人共用一个事件 ID 后，主线的 notifications.id 主键只能允许第一份写入。要沿用发布时展开，应给每人一份投递身份，并在数据库额外保证同一公告、同一收件人只生成一份。若选择按需合并，则直接维护公告与个人回执。无需先给注册提示装上一整套广播系统，理解这处身份边界已经能解释何时必须改模型。

## 附录：本章必要技术点速查

| 机制 | 用途与代价 |
| --- | --- |
| 写入时展开（fan-out on write） | 发布时逐收件人生成记录；分批续作需要稳定受众和幂等键 |
| 读取时合并（fan-out on read） | 查询时按资格取公告，与个人回执一起过滤；发布轻，列表查询和分页更复杂 |
| 复合唯一键 | 区分一则公告与一个人的那一份；要求回执对应版本时将版本纳入键。[PostgreSQL 18 唯一约束](https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS) |
| 游标边界 | 按最后实际展示的位置续查，给跨来源的并列键一个稳定次序 |
