# 第六篇　可靠后台执行：Outbox、Worker 与实时更新

注册页告诉用户去查邮件时，数据库里可能已有一份十五分钟后到期的验证意图，收件箱却是空的。上一章把 API 停在这两件事之间。现在关掉那台 API，换一个进程：它凭什么知道还有哪封信要寄？如果它发现信已经寄过一半，又凭什么决定再寄一次？

本篇从[第五篇回顾的故障现场](../part-05-identity/chapter-41-review/chapter.md#415-邮件请求返回以后谁接着做)继续，代码接第 36 章的密码路线。带着该章的独立验证库、注册／重置请求和本机 Mailpit 即可开始。可选平台登录的账号和迁移留在各自的练习库。

先让数据库同时记住业务变化和应当做的事，用一个只执行一次的程序核实交接。接下来再把它放进长期运行的进程，处理同时领取、执行者退出和外部应答丢失。到了通知场景，接收者变成会断线的浏览器：先提供能补查的通知记录，再用 SSE 提醒页面有更新。贯穿这些步骤的是同一个判断：观察到的最后一项事实，允许下一位执行者采取什么行动？
