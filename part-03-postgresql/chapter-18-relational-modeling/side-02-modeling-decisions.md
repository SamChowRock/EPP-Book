# 支线 18B：从一张宽表走到可维护的模型

正文已经用用户与记录说明事实归属，但两张小表还不足以暴露所有设计问题。这里换成一个培训报名场景，完整推导拆表，再回到 EPP 判断一对一扩展、历史、冗余、JSON 与删除。下面的表是设计草图，U1、C1 等是便于阅读的身份代号；不在 epp_dev 中创建这些对象，也不改动正文的两条记录。

## 先让一张看起来方便的表经历变化

假设系统允许一个学员报名多门课程，每个学员对每门课程只有一条当前报名；每门课程当前由一个部门负责。学员姓名、课程标题、部门名称都是当前资料，可以修改。最直接的列表结构如下：

| student_id | student_name | course_id | course_title | department_id | department_name | enrolled_at |
| --- | --- | --- | --- | --- | --- | --- |
| U1 | 小林 | C1 | SQL 入门 | D1 | 后端组 | 11 月 1 日 |
| U1 | 小林 | C2 | Node 实践 | D1 | 后端组 | 11 月 2 日 |
| U2 | 小周 | C1 | SQL 入门 | D1 | 后端组 | 11 月 3 日 |

作为查询结果，这张表很清楚；作为所有事实的唯一存储，它把几种生命周期捆到了一起。部门改名要更新三行，课程还没招到学员时无法自然登记，最后一人退课后课程标题可能跟着消失。一个人退课，本应删除报名关系，却可能顺带删除课程资料。这说明问题来自行里混合的事实。

先明确依赖：student_id 决定当前姓名；course_id 决定当前标题与所属部门；department_id 决定当前部门名称；`(student_id, course_id)` 决定当前报名时间。最后一条依赖需要两个 ID：只知道学员，不知道是哪门课；只知道课程，不知道是哪位学员。

这些规则必须来自需求。当前表中所有课程都属于 D1，不表示 course_id 与 department_id 可以互换；以后一个部门当然可以负责多门课。相同示例值不是函数依赖的证据，更不是业务唯一性的依据。

## 第一、第二、第三范式分别在消除什么问题

如果一开始把 C1、C2 塞进 `course_ids = 'C1,C2'`，同时把两个报名时间也放进逗号字符串，就需要靠位置把课程和时间配对。删除 C1 后漏删第一个时间，数据仍是合法字符串，关联已经错位。先改成每行一份报名，让字段表达这份事实中的一个值，这体现了第一范式对单值属性的要求。

这里的“一个值”要结合所选数据域理解。日期不必拆成年、月、日，原文不必拆成字；PostgreSQL 也有合法的数组和 JSON 类型。是否拆开，要看内部成员是否有独立身份、约束、查询和更新责任。具有独立报名时间的多个课程关系，不适合靠一个整体字符串来维护。

回到上面的宽表，它的候选键是 `(student_id, course_id)`。student_name 只依赖其中的 student_id；course_title、department_id 和 department_name 只依赖 course_id，后者还经过部门依赖。这些非键属性没有依赖完整组合键，属于部分依赖。第二范式要求在第一范式基础上，非主属性不能依赖任何候选键的真子集；“非主属性”就是不属于任何候选键的属性。

因此先拆出 students，保存学员当前资料；拆出 courses，保存课程当前资料；enrollments 只保留两个 ID 与 enrolled_at。每份报名的时间必须同时依赖“谁”和“哪门课”，留在关系表恰当。添加一个自增 enrollment_id 并不能替我们完成拆分：业务候选键仍是那一对 ID，重复资料的问题也仍然存在。

此时 courses 如果保留 `course_id, course_title, department_id, department_name`，仍有 course_id → department_id → department_name。课程换部门，应更新它的 department_id；部门改名，应更新部门本身，不该逐门课程修改。因此再拆出 departments，只让 courses 保存 department_id。

这一步消除了本例的传递依赖，达到第三范式。更准确地说，对每条非平凡函数依赖 X → A，第三范式要求 X 是超键，或者 A 是某个候选键的组成属性。超键是能唯一识别行的属性集合，可以包含多余列；候选键则不能再删列。“非平凡”表示 A 不在 X 里面，例如 course_id → course_title，而不是 course_id → course_id。本例只有上述明确的候选键，第三范式的检查就落成了“把部门名称放回部门”。

不必每次设计都先做一页符号推演，但要能用依赖解释拆分理由。若只背“每表都有主键、每列不能再分”，仍会保留这个部门改名异常。更严格的 BCNF 要求每个非平凡依赖的决定因素都是超键；涉及多个重叠候选键时值得继续分析，但不要把范式等级当成性能分数。

最后得到：

| 表 | 一行代表什么 | 键与应保留的事实 |
| --- | --- | --- |
| students | 一个学员的当前资料 | student_id 主键，student_name |
| departments | 一个部门的当前资料 | department_id 主键，department_name |
| courses | 一门课程的当前资料 | course_id 主键，course_title，department_id 外键 |
| enrollments | 一位学员对一门课的当前报名 | 两个 ID 组合主键，分别为外键，enrolled_at |

现在部门改名只改 departments；尚无人报名的课程可以独立存在；删除一条报名不会消灭课程。重新读取列表时，由 enrollments 分别找到唯一的学员与课程，再由课程找到唯一的部门，能重建原来的组合。

保留 enrollments 尤其关键。若只留下“有哪些学员”和“有哪些课程”，再把它们任意配对，U2 会凭空多出 C2 的报名。**拆表必须保留原有关系，关联时不能产生假事实**，这就是无损分解所关心的问题之一。另一个检查是依赖是否便于维护：姓名由学员主键定位，课程归属由课程主键定位，重复报名由关系表组合键拒绝；不需要每次改名都把四张表拼起来才能判断合法。

以上范式与依赖概念可对照作者提供的 [Database System Concepts：Normalization](https://www.db-book.com/slides-dir/PDF-dir/ch7.pdf)。实际设计先从明确的业务规则和反例开始，范式用来校验推导。

## 一对一扩展与关联实体：按生命周期决定是否拆开

回到 EPP。未来用户多了头像与简介，是不是必须建 user_profiles？如果这些字段很少、总是一起读取、生命周期也相同，直接放在 users 上通常更简单。一个字段允许为空，不是单独建表的充分理由。

若资料只在部分用户中存在，字段较多，或者需要独立的写入权限与管理流程，再考虑一对一扩展。让 user_profiles.user_id 同时是主键和指向 users.id 的外键，就表达了“资料只能属于已有用户，每个用户至多一份资料”。它没有保证每个用户必有资料；创建用户时不创建资料行仍然合法。若需要两者同时出现，必须由创建流程和事务共同落实。

反过来，给资料表单独分配 id，却忘了 user_id 唯一，那么同一用户仍能拥有两份资料，图上写“一对一”并不能改变这个事实。表拆开也不会自动完成权限隔离；数据库账号和应用入口仍需要相应授权。

正文的共享成员是另一种情况：permission 与 granted_at 描述的是“哪个人对哪条记录”的关系，不能归到任意一端。这就是关联实体。判断它的一个方法是改变一端：同一个人对另一条记录有不同权限，说明权限依赖整对关系；同一条记录换一个成员，授权时间也可以不同。拆分来自事实归属，不来自“凡是多对多都要一张只有两个 ID 的空桥表”。

## 当前状态、历史快照和版本记录为什么不能混用

把前面报名系统的规则改一个条件：报名确认页必须保留报名当天的课程标题。课程以后改名，历史确认页仍显示旧标题。这时 enrollments 中保存 `course_title_at_enrollment` 是合理的，因为它描述这次报名发生时的事实；它与 courses.course_title 表示不同时间语义。不能因为两者刚创建时相等，就按“消除冗余”删掉快照。

比较三种变化后的结果：

| 保存方式 | 课程改名后，旧报名显示什么 | 维护责任 |
| --- | --- | --- |
| 只保存 course_id，读取当前标题 | 新标题 | 当前资料只有一份 |
| 报名时保存标题快照 | 报名时的旧标题 | 写入时取得并保存正确的快照，之后不随改名同步 |
| 报名引用一个明确课程版本 | 被引用版本的标题 | 版本内容稳定，报名能定位当时的版本 |

快照不是随便复制一下就结束。若报名与课程改名并发，必须定义以哪个读取／提交时点取得的标题为准，再用合适的事务完成；否则同一次报名的标题、价格等字段可能来自不同版本。当前阶段先明确语义，一致性篇再落实竞争下的写入策略。

版本模式则适用于需要保留完整修订过程、让其他数据准确引用某一版的场景。例如记录保留稳定 capture_id，修订表每行是一版内容，以独立 revision_id 标识，并对 `(capture_id, revision_number)` 保证唯一。不能因为版本号叫 number，就用“查最大值再加一”假定并发安全；分配和冲突处理需要单独设计。

如果还有 current_revision_id，它表示当前选择，历史修订表示过去内容，两者的责任不同。只给 current_revision_id 加一个指向 revisions.id 的外键，还不能保证这一版属于当前 capture；错误地指到另一条记录的修订也满足“存在”。要用包含 capture_id 的组合引用等方式表达归属，或明确由受控写入过程维护。这里不提前确定后续 EPP 修订实现，只说明评审这种方案时不能漏掉的关系。

EPP 当前只保存创建时原文，没有修订行为，因此不现在增加一套版本表。将来需求要求“旧候选必须对应生成时的原文”，才需要把内容版本与引用一起落到模型里。历史、审计和当前状态可以协作，但单加 updated_at 无法恢复被覆盖的旧内容，也不能回答是谁因为什么改了它。

## 反规范化要先回答谁负责修复副本

假设列表需要显示每位用户的记录数。先从 captures 按用户统计，数值来自已有事实；数据多了以后若确实成为瓶颈，再考虑在 users 保存 capture_count，减少反复计算。这是派生值缓存式的反规范化。

一旦保存，就增加了维护责任。创建记录要加一，删除要减一，导入、批量删除、失败重试也不能遗漏；若采用“读取旧值、加一后覆盖”，两个并发请求还可能丢掉一次增加。把记录写入与计数变更放到同一事务、采用合适的更新方式，可以保证特定数据库写入路径中的原子性，但所有入口必须遵守相同规则。若选择异步更新，则要允许并说明短暂过时，并安排重试与重新计算。

最容易判断这个设计是否完整的变化是：故意让缓存不可信，还能从 captures 重算并校正吗？如果能，captures 是权威事实，计数是可恢复副本；如果不能，说明把一份必要事实误当缓存处理了。历史标题快照就不能按当前课程标题“重建”，它不是同一种重复。

因此采用反规范化前，应先确定准确性要求，查看真实查询成本，考虑索引或查询调整，再决定是否承担同步、修复和额外存储。表多不等于慢，少一次 JOIN 也不自动等于整体更快；写入变复杂、索引维护和数据不一致都是成本。执行计划与索引实验在后续章节展开，本章先建立作这个决定所需的责任边界。

## JSON 与软删除：灵活的表示也会留下规则

如果 EPP 未来保存外部服务返回的诊断信息，各供应商字段不同，通常作为一次调用的整体读取，很少逐项关联，那么一列 jsonb 可以减少频繁变化的辅助列。它适合明确边界内的可变文档；核心身份、归属和稳定查询条件仍可以使用普通列。需要查询 JSON 内部字段时，也必须据实际访问方式设计索引，而不是假设“用了 JSON 就不用设计”。

把共享成员全部放进 JSON 数组则有另一组后果：普通外键不能直接保证每个成员存在，组合唯一约束也不能直接保证数组里同一用户只出现一次，独立修改成员时还要处理整个文档所在行的更新竞争。可以另写机制补足，但如果成员本来就有独立身份、权限和生命周期，关联表通常更直接。选择依据是约束和修改粒度，不是前端已经有一个对象。

最后看“所有表都加 deleted_at”的通用模板。假设标签名称在同一用户下唯一。软删除旧标签后，普通唯一约束仍会占住那个名称；若产品允许重新使用，则需要只约束活跃行，例如以 `deleted_at IS NULL` 为条件的部分唯一索引。可是一旦新标签使用了旧名称，再恢复旧标签就会冲突。必须事先选择恢复失败、重命名或合并等行为，索引不能替产品作决定。

软删除的父行也仍然存在，所以外键仍允许引用它；“只能关联未删除对象”不是普通外键已经解决的规则。列表、关联查询和统计要有一致的有效性条件，历史记录是否显示已删除对象又可能不同。把 deleted_at 加上以后忘记这些读取路径，会出现首页看不见、搜索却能找到的矛盾。

因此只在确实需要撤销、留存或处置流程时引入软删除，并设计后续清理和恢复。对本章用户与记录，先用明确的 RESTRICT 拒绝未定义的账号删除过程，比增加一个没有配套语义的字段更完整。相关机制可查阅 PostgreSQL 的 [JSON 类型](https://www.postgresql.org/docs/18/datatype-json.html)、[约束](https://www.postgresql.org/docs/18/ddl-constraints.html)与[部分索引](https://www.postgresql.org/docs/18/indexes-partial.html)。

回到自己的模型，先让它经历一次改名、关系增加、历史回看和删除恢复，再检查哪些数据应该变化、哪些必须保持。如果答案要求反复同步同一事实，考虑规范化；如果要求保留当时事实，考虑快照或版本；如果只是为了更快地读取可计算结果，明确派生副本的维护与重建。模式是对这些约束的回应，不能替代对需求的判断。

时间参考（估算）：阅读约 40～50 分钟；本支线以数据表和需求变式推演，不另设数据库操作，不需要创建实验表。

## 附录：本支线必要技术点速查

| 名称 | 本支线用途 | 必要注意点 |
| --- | --- | --- |
| 函数依赖／候选键 | 判断事实由哪些属性决定 | 依据合法业务状态，不能从样本碰巧相同推出 |
| 第一／第二／第三范式 | 分析重复组、部分依赖和本例的传递依赖 | 检查全部候选键，代理主键不消除业务依赖 |
| 无损分解 | 拆表后保留原有信息与关系 | 不丢归属，也不通过任意配对制造假关系 |
| 共享主键的一对一扩展 | 为同一实体分离可选资料 | 保证至多一份，不自动保证每位用户必有资料 |
| 关联实体 | 保存关系自己的属性 | 组合唯一性与两端存在性分别表达 |
| 快照／版本／当前状态 | 区分当时内容、修订与当前选择 | 时间语义与引用归属必须明确 |
| 反规范化 | 用派生副本减少重复读取成本 | 明确权威来源、并发更新、重试与重建 |
| jsonb | 保存边界明确的可变文档 | 不自动获得内部成员的关系约束 |
| 软删除／部分唯一索引 | 保留已删除行、约束活跃集合 | 恢复冲突和“仍存在但已失效”需要独立规则 |
