# 支线 19A：等待结束后，写入到底发生了没有

主线用两个列表请求分别观察了池获取到期和数据库等锁超时。列表没有写副作用，所以恢复后再读很自然。把同样的错误处理复制到创建接口，问题立刻不同：客户端说失败，究竟哪一步失败？已经保存的事实会不会被重复创建？

本支线沿第十三章的工作追踪、第十七章的提交可见性继续推导，不新增业务接口。阅读约 20～25 分钟，按约 2300 个汉字和两组时序对照估算，尚未经过读者实测；不另设操作。

## 一次请求同时跨过几种状态

考虑“创建一条原文”的过程。请求到达后完成校验，生成 ID，然后等待连接；取得连接后发送 INSERT；数据库检查约束、执行并提交；服务端收到结果，构造响应，最后客户端收到并解析。每一步都有自己的完成条件。

主线的池等待到期，若能确定本次唯一 SQL 还没有发送，就能推断这次写入没有执行。但 HTTP 调用方只收到统一的存储失败信息，通常看不见它发生在这个阶段还是稍后的网络阶段。如果未来一个业务操作包含多个 SQL，“第二次获取连接失败”更不能证明第一次写入也没有发生。

服务器 `statement_timeout` 则在数据库正在处理语句时起作用。当前只有一条 INSERT，若收到数据库明确的超时取消错误，该语句事务不会部分提交一行。若语句放进显式事务，异常后事务通常进入失败状态，仍需回滚；错误消息到达客户端不是“事务已经由应用妥善清理”的同义词。

还有一种看起来相似的结果：客户端的等待定时器先到，数据库仍在执行。`Promise.race([write(), timeout()])` 只决定哪一个 Promise 的结果先被调用方看到，不会把另一个计算从数据库里删除。第十三章的 ApplicationState 继续追踪已接受工作，就是为了不让“调用方不等了”变成“系统认为工作不存在”。

## 三秒不是整条请求的上限

假设池获取最多等两秒，服务器语句最多执行三秒。一个请求排队 1.8 秒才拿到连接，再用 2.7 秒完成 SQL，数据库部分已经花了 4.5 秒。两个局部上限都没有违反，但总耗时显然大于三秒。

这时把 HTTP 超时设成三秒，只会让 HTTP 等待先结束，不会自动让所有下游阶段分享同一个期限。若要实现端到端预算，需要记录整体截止时间，每进入一个阶段计算还剩多少，再选择能真正取消该阶段工作的机制；过期后要说明已发生副作用如何处理。没有这些协作，仅给更多地方加 timeout 可能增加未知结果的数量。

再改变一个条件：请求会顺序执行三条 SQL。每条各三秒，整个业务可能接近九秒；事务总时限与单语句时限也不是一个东西。本章没有多语句业务事务，不提前引入复杂期限框架，但已经必须知道现有配置保证到哪里。

主线的 `idleTimeoutMillis` 更不属于请求预算。它回收已空闲的连接；没有正在使用的请求因此被取消。`idle_in_transaction_session_timeout` 是服务器对空闲事务的保护，常用于避免忘记结束的事务长期占锁；它也不等同于关闭 API 的总期限。

## 两个“失败”留下不同的数据库事实

第一种时序：

| 次序 | 实际发生的事情 | 可以依据什么判断 |
| --- | --- | --- |
| 1 | API 准备创建 A，但尚未取得连接 | 池中排队，没有向 PostgreSQL 发送本次 INSERT |
| 2 | 获取等待到期 | 本次单语句没有进入数据库 |
| 3 | API 返回 503 | 此例没有新增 A，但一般调用方未必能确认全部内部条件 |

第二种时序：

| 次序 | 实际发生的事情 | 可以依据什么判断 |
| --- | --- | --- |
| 1 | API 发送创建 B | SQL 已到数据库 |
| 2 | PostgreSQL 提交 B | 数据库中已经有 B |
| 3 | 返回路径断开，API 或客户端没有收到成功确认 | 外部结果未知，不能反推 B 不存在 |
| 4 | 相同正文再次 POST，Service 生成 C 的新 UUID | B 与 C 都可以合法存在，主键不会阻止语义重复 |

第二种情况不是事务失效。数据库正确完成了它负责的事务，网络没有替整个业务完成成功通知。单表原子性解决部分写入，不解决成功确认必达。把事务扩大到响应发送也不可行：响应可能已经离开服务端，但客户端还没收到；服务端没有一种本地操作能把双方的确认永久锁在一起。

本章的错误描述因此保守地提示“写入结果可能未知”。它不意味着每次失败都真的写入了，而是公共错误契约没有足够信息承诺“肯定没写”。语义诚实比给出一个方便重试却错误的确定性更重要。

## 为什么按原文查重不足以恢复

如果 API 生成的 ID 已知，可以按该 ID 查询，核对归属和内容。这比“列表最后一条是不是它”可靠，因为并发、同毫秒时间与列表排序都可能改变末尾位置。但当前创建 ID 通常随成功响应返回；响应完全丢失时，客户端未必知道它。

按原文搜索也无法唯一认定同一次请求。用户可以在不同时间记录相同句子，本书目前允许这种行为；禁止重复原文会改变业务规则。X-Request-Id 用于串联一次 HTTP 的日志，重试产生另一编号，且它没有作为业务幂等依据持久化，不能凭名字接近就承担去重职责。

如果需求变成“客户端安全地重发同一次创建”，应让客户端在首次提交之前持有稳定的操作标识。服务端将该标识、请求内容的关联和最终结果持久化，并用唯一约束与事务处理并发重试。同一标识却携带不同内容时，要拒绝而不是返回一个不相干的旧结果。这里的设计依据是“同一次意图可识别”，不是“正文看起来一样”。后面的幂等章节会落实保存结构、竞争与重放结果，本章不偷偷改变现有 POST 协议。

## 取消和重试应该落在哪一层

查询列表失败通常可以由调用方重新查询，因为读取不会创建第二条业务记录；但重试仍消耗连接与数据库时间，服务过载时无限立即重试会扩大排队。一个受控的重试策略还需要次数、间隔和整体预算。

创建接口则先判断是否具备幂等保证，不能看到 503 就对所有方法自动重发。数据库适配层也不应替 Service 重试任意 write：它不知道重复一次业务是否合理。只有明确失败发生在无副作用阶段，或业务具有可证明的幂等语义时，重试才有可靠依据。

如果调用方主动取消请求，Controller 可能已经开始写入。当前实现允许已接受的单语句完成，并保留工作追踪，关闭进程时等待它收尾。若将来需要把取消传到数据库，必须使用实际支持取消的协议，同时处理取消与提交竞争；不能把取消成功当成永远没有结果。

回到本章的连接实验，最有价值的观察不是获得两个红色的 503，而是解释：一个请求还在应用池里，一个已经进入数据库；它们由不同期限结束，证据也在不同位置。以后面对任务队列、外部供应商或支付接口，同样先定位阶段、已有事实和确认边界，再决定能否重试。

## 附录：本支线必要技术点速查

| 名称 | 用途 | 边界 |
| --- | --- | --- |
| 池获取期限 | 限定等待可用连接 | 不能代表整个请求预算 |
| 语句取消 | 由服务器结束正在执行的语句 | 需区分明确取消与连接失去确认 |
| 客户端等待到期 | 结束调用方的等待 | 不自动撤销数据库工作 |
| 结果未知 | 表示无法根据响应确定是否已提交 | 应查询已有事实，不盲目重复写入 |
| 请求 ID | 关联日志与一次 HTTP 处理 | 不自动具备持久化幂等语义 |
| 幂等标识 | 识别同一次业务意图 | 要与内容、结果及并发约束一起设计 |
