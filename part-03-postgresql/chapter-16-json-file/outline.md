# 第 16 章 两次都写成功，JSON 文件里为什么少了一条素材

**章节提要**　承接第 15 章「第二篇回顾：沿一次请求解释职责与生命周期」。练习从[已有配套](https://github.com/SamChowRock/epp-public/tree/part-02/chapter-15)的副本开始。

## 16.1 给素材仓储换一份可以重开的文件

从 Nest 素材服务的存储接口出发，保留 Controller、输入校验、返回的 ID 和 Location。在独立练习目录中实现文件仓储，明确文件缺失时由初始化步骤创建空数组。写入素材 A，退出进程，重启后按原 ID 查详情。然后往另一份文件写半截 JSON，要求启动报告解析失败并保全原字节，防止把读错当成第一次启动。

## 16.2 把两次修改停在读完旧文件的位置

从只有 A 的副本启动两个 Node 写入者。每个先读数组、追加自己的 UUID，再打印 ready 并等待标准输入。等两边均就绪，依次放行 B 和 C。收下两次退出状态、两份原始 ID 和最终文件，逐一检查 A、B、C。文件仍能解析、两个写入者都报成功时，指出哪份旧数组覆盖了谁。

## 16.3 完整替换文件能保住两次写入吗

每个进程在目标文件同一目录写各自的临时文件，写完再改名替换。分别在改名前中止和改名后正常退出，核对旧文件或新文件完整、暂存何时遗留。重新运行上一节双写时序，即可检验完整替换能否保住两次追加。讨论单进程串行队列何时有效，以及第二个进程如何绕过它。

## 16.4 把丢失的 ID 带到数据库篇

用原始副本恢复，先按单写者规则重放两条已知练习输入，逐项对照三个 ID。若现场只剩最终文件，列出哪条内容无法从中重建。将跨进程协调、提交与失败恢复列为下一篇对 PostgreSQL 的验收要求。
