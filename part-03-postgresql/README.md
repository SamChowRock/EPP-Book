# 第三篇 持久化与结构演进：PostgreSQL、SQL、Prisma

第三篇从已有 CaptureStore 契约进入 PostgreSQL：模型和查询怎样落实已有接口约定，约束由哪一层保证，连接与事务怎样影响失败判断，以及结构变化时怎样保留旧数据。这些问题决定数据库接入以后能否继续独立开发和维护。

本篇按实际研发顺序展开：准备和诊断数据库环境，从已有需求推导关系和约束，直接写 SQL 查看结果，再引入 Prisma 管理访问与结构演进。贯穿过程的要求是保留已经写入的数据，不能每增加一个字段就重新建库。

本篇重点是学会设计：解释一行代表什么、事实归谁、为什么拆表、哪些重复必须拒绝，以及历史、查询成本与旧数据怎样影响方案。数据库原理和建模模式随这些判断展开，可视化工具用于观察和验证选择；SQL 与 ORM 是落实模型的手段。

起点沿用第十四章主线，也就是第十三章的 2000 单元创建规则、三个记录接口和 Map。第十四章的 1200 单元限制与数组存储是隔离练习，不作为数据库接入的前置变更。日常开发继续使用带 Inspector、自动编译重启和保存的 Postman 请求的默认流程；数据库作为独立进程运行。日常数据库实践使用 DBeaver Community：在 SQL 编辑器执行并保存脚本，在对象属性和 Data 页查看结构与数据；psql 保留为备用复现工具。

本篇会建立最小用户和记录表，先用固定开发用户说明归属，再保存原文、ID、创建时间；之后给已有记录追加中文意图。固定用户只承担当前建模与查询的前置条件，身份认证和用户隔离另有后续实现。修订、候选、采纳和并发事务在后面的实际需求中继续展开。

## 中断后，从当前数据库状态接着做

本篇的代码分支、数据库和运行进程各有自己的状态。关闭编辑器、切换 Git 分支或重新编译，都不会让数据库自动回到某章。下面集中列出逐章建立的连接；读到哪一章才创建哪一个，不需要在第十五章提前准备全部数据库。

| 数据库 | 首次使用与职责 | 客户端或配置入口 | 中断后应保留什么 |
| --- | --- | --- | --- |
| `postgres` | 第十五章，创建角色与数据库的管理连接 | DBeaver ADMIN；`epp_admin` | 实例及角色；日常业务 SQL 使用 DEV |
| `epp_dev` | 第十五章起的日常库；第十六章起积累业务行 | DBeaver DEV；迁移 `.env.database`；第十九章起 API `.env` | 所有合法业务行、结构和迁移历史 |
| `epp_migration_check` | 第十八章，独立重放并核对结构 | DBeaver VERIFY；`.env.database-verify`；`npm run db:verify` | 已应用历史与校验结果；正常路径业务表为空 |
| `epp_shadow` | 第二十章，开发迁移清理重放的工作库 | `.env.database` 中的 `SHADOW_DATABASE_URL` | 不存需要保留的业务数据；由迁移工具管理重放 |
| `epp_ch20_recovery` | 第二十章，隔离的迁移失败恢复实验 | DBeaver RECOVERY-A/B；`.env.database-recovery` 与专用 Prisma 配置 | 失败／成功尝试及实验结构，供恢复和回查 |

这些名字表示用途，不是连接正确的证据。它们默认位于同一台 `127.0.0.1:55432` 实例，除管理连接外使用 `epp_owner`；实际操作前，仍在当前编辑器查询库名、角色、地址、端口，双会话实验再比较 PID。工具中的连接标签可以改，查询返回的实际身份才决定 SQL 将作用于哪里。

配置文件也不是自动串联的：`npm run db` 只加载 `.env.database`，`npm run db:verify` 只加载 `.env.database-verify`；第十九章的 `npm run dev` 加载 `.env`。修正迁移配置后，API 的配置不会跟着变化。Node 已有进程环境优先于 env 文件；按对应章节清除残留变量，再从原入口重启，不打印含密码的 URL。第二十一章另建的旧产物使用其独立目录中的 `.env.production`，不复制到当前源码目录。

回来继续时，先按[第十五章的日常恢复](chapter-15-postgresql-environment/chapter.md#隔天继续开发时从哪里接上)连接原实例，再判断已走到哪一步：

| 已完成阶段 | 日常库应有的状态 | 接下来可以做什么 |
| --- | --- | --- |
| 第十五章 | 开发角色与库已建立，尚未建业务表 | 进入第十六章建模和首次建表 |
| 第十六、十七章 | `users`、`captures` 及保留的原文；尚未登记 Prisma 基线 | 重新查询旧行，继续 SQL 或基线；不重复建表和 seed |
| 第十八、十九章 | 已登记 `0_init`；无中文意图列 | 第十八章 API 仍用 Map，第十九章完成接入后才读取数据库 |
| 第二十章 | 已追加可空 `chinese_intent`，数据库 CHECK 上限为 1000 字符 | 读取旧值，继续意图功能或隔离恢复实验 |
| 第二十一章 | CHECK 已放宽到 2000 字符，可能已有长意图 | 同时确认当前程序是 A、B 还是 C，再决定能否运行它 |

这张表帮助定位阶段，不能替代实际检查。第十八章起先查 `migrate status` 和已有对象；第二十、二十一章的 CHECK 还要查完整定义，因为 Prisma diff 不覆盖它。若磁盘缺少已经应用的迁移，先恢复正确代码上下文；若记录显示失败，沿第二十章检查实际回滚情况。不能为了让表格对上而清库。

暂停前，双会话事务和持锁实验要在各自原会话结束；临时表一旦断开就会消失，下次按该实验重新准备。保留数据库、私有配置、当前章节及必要的比较结果即可。第二十一章另外记下补丁是否应用、哪个端口运行 A/B/C、是否已写入超过 1000 个 UTF-16 单元的值：存在长值后，结构相同也不能保证 A 读得了，恢复依据见[21.3](chapter-21-review/chapter.md#213-用失败和恢复区分三个版本)。
