# 第三篇 持久化与结构演进：PostgreSQL、SQL、Prisma

第三篇从已有 CaptureStore 契约进入 PostgreSQL：模型和查询怎样落实已有接口约定，约束由哪一层保证，连接与事务怎样影响失败判断，以及结构变化时怎样保留旧数据。这些问题决定数据库接入以后能否继续独立开发和维护。

本篇按实际研发顺序展开：准备和诊断数据库环境，从已有需求推导关系和约束，直接写 SQL 查看结果，再引入 Prisma 管理访问与结构演进。贯穿过程的要求是保留已经写入的数据，不能每增加一个字段就重新建库。

本篇重点是学会设计：解释一行代表什么、事实归谁、为什么拆表、哪些重复必须拒绝，以及历史、查询成本与旧数据怎样影响方案。数据库原理和建模模式随这些判断展开，可视化工具用于观察和验证选择；SQL 与 ORM 是落实模型的手段。

起点沿用第十四章主线，也就是第十三章的 2000 单元创建规则、三个记录接口和 Map。第十四章的 1200 单元限制与数组存储是隔离练习，不作为数据库接入的前置变更。日常开发继续使用带 Inspector、自动编译重启和保存的 Postman 请求的默认流程；数据库作为独立进程运行。日常数据库实践使用 DBeaver Community：在 SQL 编辑器执行并保存脚本，在对象属性和 Data 页查看结构与数据；psql 保留为备用复现工具。

本篇会建立最小用户和记录表，先用固定开发用户说明归属，再保存原文、ID、创建时间；之后给已有记录追加中文意图。固定用户只承担当前建模与查询的前置条件，身份认证和用户隔离另有后续实现。修订、候选、采纳和并发事务在后面的实际需求中继续展开。

按顺序推进：第十五章得到一个可以确认身份、解释故障的数据库环境；第十六、十七章得到表与数据；第十八章整理结构管理方式；第十九章才形成从 HTTP 到持久化存储的完整业务链。各阶段分别核对环境、SQL 行为、迁移历史和接口契约，保留可以回到数据库侧排错的依据。
