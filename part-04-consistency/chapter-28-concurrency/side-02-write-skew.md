# 支线 28B：两人各改自己的一行，为什么还是会无人值班

28A 的版本号已经能辨认“这行从我看到以后又改过”。这次有两位值班员，规则是同一班次至少一人在岗。101 和 202 各自只申请自己离岗。两个人都没有改过对方那一行的意图，给每行加版本号还能守住这条规则吗？先从任何一种合法的**逐笔执行**推答案：第一人可以离开；第二人检查时剩下的是自己，所以不能再走。也就是说，无论谁先来，若两个动作都允许通过，就有某个前提没有受到保护。

阅读约 18～24 分钟，两轮双会话和一次重试另需约 15～22 分钟。使用已经准备好的独立 VERIFY，在 DBeaver 打开 A、B 两个空闲 SQL 编辑器，先在两边执行 `SELECT current_database(), pg_backend_pid();`，确认库名相同、PID 不同。平时保持自动提交，下面由显式 BEGIN、COMMIT 控制事务。在第 28 章配套打开 `database/chapter-25/07-roster-snapshots.sql`，按标签交替执行选中的块。文件里的两次“双方”都指两个编辑器各执行一次。整份连续执行无法产生所需时序。

## 在动手前，圈出读取范围和修改范围

A 至少要读 B 是否在岗，却只需要写 A；B 同理。两支画向对方的读取箭头就是关键：A 作决定时假设 B 会留下，B 作决定时又假设 A 会留下。值班表的主键可以保证一个成员在同一班只有一行，却没有哪一行能单独写出“全班至少一人”这个事实。

只在 A 执行配套的第 0 块，建立并提交独立命名空间和四条初始行。班次 1 与班次 2 各有 101、202 两位在岗，留作两轮相同起点。若命名空间已存在，就停止并核对是谁建立、上一轮停在哪里。不要把既有实验覆盖成初始状态。双会话要读同一张表，所以这里不能换成只对当前会话可见的临时表。

先把 A 的决定读成 SQL。UPDATE 定位自己的在岗行，EXISTS 寻找**同一班、另一位、仍在岗**的行。把“另一位”删掉，最后一人会拿自己作留下的证据，顺序执行已经错误；任何隔离级别都不会替产品补回这个条件。

```sql
UPDATE ch28_roster_lab.duty AS me SET on_duty = false
WHERE me.shift_no = 1 AND me.member_no = 101 AND me.on_duty
  AND EXISTS (
    SELECT 1 FROM ch28_roster_lab.duty AS other
    WHERE other.shift_no = me.shift_no
      AND other.member_no <> me.member_no AND other.on_duty
  )
RETURNING me.member_no;
```

## 第一轮，各自稳定地看见旧名单

在两个编辑器分别执行 1a。两边都用 REPEATABLE READ，看见班次 1 的两位在岗。先让 A 执行 1b，看到返回 101，暂不提交。再让 B 执行 1c，观察结果能否在 A 提交前就返回。在这套夹具上 B 返回 202。它改的是自己的另一行，自己的快照中 101 仍在岗。不要沿用 28.1 争同一候选时“后写者一定在同一行上等”的预测。

现在分别在 A、B 执行 COMMIT。用空闲编辑器执行 1e，对照两个班次。班次 1 是零，尚未参与实验的班次 2 是二。两个参与者都依据本事务可见的合法名单决定离岗，每笔修改各自完整提交，组合结果却不符合任何一种合法的逐笔执行。这种依赖对方旧值、修改不同行而共同破坏条件的情况叫**写偏斜**。如果把两次 UPDATE 都改成写同一个成员，你已经换了问题，无法再说明跨行条件何时失守。

也可以检验为什么“在提交前多读一次”无法从根本上修好它。在同一个可重复读事务中，重读会看到自己的变动，其他事务已提交的新版本则不会因此取代已有快照。两个人各自查到“我已离开，对方仍在”，恰好仍会以为规则满足。把读数写到日志能解释当时怎样作出决定，本身不会把两次决定排成合法顺序。

## 第二轮，成功提交的结果必须能排成一个顺序

这次用班次 2。A、B 分别执行 2a，隔离级别改为 SERIALIZABLE。确保两个 SELECT 都已结束才继续；如果先让 A 做完整笔再启动 B，B 天然会看见一人已经离开，那是串行的另一组实验。A 执行 2b，B 执行 2c，再依次结束事务。每次 UPDATE 的返回值和每次 COMMIT 的结果要分开观察。

一笔事务可能在执行语句或尝试提交时得到 `40001`。若客户端仍显示失败事务，在那个会话执行 ROLLBACK 回到空闲；另一位正常完成自己的事务。数据库会追踪会影响串行解释的读写依赖，在这组交错中不能让两笔都成功。它没有把两个事务从头到尾排成单线程，也没有承诺“第二个点按钮的人必输”。对照 2e：班次 2 应有一人仍在岗；两笔都声称成功、或者只看到了两次 UPDATE RETURNING，都需要回头核对各自最后的事务结局。

为什么数据库不能只命令失败者再提交一次？它原来的检查来自双方均在的名单，拿这个结果原封不动去提交，还是同一个矛盾。第 3 块要求在**新事务**重新读班次 2，并替仍在岗的那位值班员重作决定。若留下的是 101，就把第 3 块 UPDATE 中的值班员编号换成 101。此时没有其他人在岗，UPDATE 返回零行，这笔事务可以正常提交。把这两个结果分别记下来：第一次是数据库无法接受该次并发执行，要求丢弃旧的工作；重新计算后是业务前提不满足，已经得到确定结论，继续自动重试不会创造另一位值班员。

## 带着这个反例回到 EPP

同一个候选的两次采纳都要修改候选行，主线的条件写入已找到共同竞争点。值班问题则是两个决定依赖同一班的成员集合，恰好可以给班次建立一条稳定的父行，让**所有改变在岗数的入口**都先在事务中锁住它，在 READ COMMITTED 下取得锁后用下一条语句重读并决定。优点是能明确指出大家在等哪一班；代价是同班的修改需要排队，漏掉的维护入口依然会破坏前提。另一条路是让所有有关决策在 SERIALIZABLE 下执行，并能从头重算被中止的整笔事务。哪条路更适合，要看能否找到稳定的共同对象、写路径有多少、失败后能否重复执行，不能只比较两种写法的 SQL 行数。

执行配套第 4 块得到两行，分别为“1 / 0”“2 / 1”。保留这两行和两次事务结局。两位参与者都结束事务之后，如需收尾，只运行第 5 块删除本轮自己新建的实验对象。回到 28.5，试着用一句话指出下一条业务规则实际依赖哪些行，所用机制能守住的范围到哪里为止。

## 附录：本支线必要技术点速查

| 观察量 | 怎样解释 |
| --- | --- |
| 两个写入更新了不同主键 | 仍需检查它们是否分别依赖对方的旧值 |
| 固定快照 | 能稳定重读已有事实，跨行写入能否并存还需单独判断 |
| SQLSTATE 40001 | 从新事务重做读取、判断和写入，原事务没有成功结果可提交 |
| 重算后影响零行 | 新状态下不再满足产品条件，应返回对应业务结论 |
