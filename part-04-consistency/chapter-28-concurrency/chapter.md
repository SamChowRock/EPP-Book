# 第28章 并发控制：两个请求同时到来怎么办

上一章保证一次采纳的状态、表达、形式和学习记录一起提交，也已经在更新候选时带上pending条件。本章不撤掉这条保护来制造故障，而是先在隔离表中重建一个很容易写出来的版本：查到pending，就认为自己可以采纳。把两个请求交错运行以后，再回到当前实现，判断每条保护到底承担什么责任。

从 `part-04/chapter-27` 继续，完成 `part-04/chapter-28`。本章为学习记录增加单候选唯一约束，为采纳设置有限锁等待，只对数据库明确中止的事务做有上限的重试。接口仍确认具体candidateId，历史候选仍可采纳；两个不同候选即使文字相同，目前仍各自建立表达。语义身份与结果重放分别由第31、29章接续。

实践沿用PostgreSQL 18、Prisma 7.10.1、固定开发用户，以及DEV／VERIFY／SHADOW三种配置。DBeaver负责观察两个真实连接，Postman保存接口请求，VS Code观察事务边界。配套入口为 `database/chapter-25/README.md`，六份SQL按编号保存；不要把需要交错执行的文件整段运行。先读完28.1的前提，再开始隔离实验；正式库的迁移在28.2处理。

## 28.1 两次都读到pending，为什么不能两次都采纳

### 先找竞争对象

同一个候选被双击采纳，与两个不同候选都写着 `I'm not much of a cook.`，并不是一种重复。前者有同一个candidateId，已有规则可以直接判断：这个候选只能完成一次确认。后者只有内容看起来相似，还没有证明它们属于同一含义、同一用法或同一个正式表达。

再加一种情况：一个请求采纳，另一个请求放弃同一个候选。两者都以pending为前提，最终只能有一个决定成立。它们争的是候选状态，与表达的文字是否相同没有关系。设计并发控制前，先把这三种输入区分开，才知道该在哪一行、哪一列或哪一个身份上建立保护。

Node.js在一个线程中执行JavaScript，也不能保证两个请求的数据库过程连续完成。第一个请求await查询时，第二个可以继续；连接池允许它们使用不同连接。即使这个进程自行排队，另一个API实例、管理脚本或数据库客户端仍能写入。进程内的Set与Promise队列只能协调遵守它的当前进程，不能成为数据库事实的最终保证。

把“同时到来”翻成一个能算出答案的问题。甲乙各发一笔创建，正常情况下两笔都要有结果，这是两件不同的事；甲乙各确认同一份候选，两笔请求都有资格进入入口，但同一个决定只能成立一次。如果只记有几次 POST 或收到几条日志，你无法分辨是哪一种。先给每笔请求写上它选中的候选标识，再写上允许成功的起始状态，就能判定哪些决定必须相互排斥。这里竞争的是从待决定出发的那一次转移，处理器可以同时运行，只有获得那次转移的处理器可以继续留下采纳结果。

再画一个相邻需求：同样的用户依次点两条不同修订里的第一个候选。它们的候选序号可能都为一，英文甚至可以一模一样，标识却不同。若页面用“用户加序号”判定正在处理某个决定，就可能把第二次正常采纳也挡掉；若用原文作防重复键，还会碰上内容相同但含义不同的情况。页面暂时禁用同一个按钮可以避免正在操作的人多点，另一个标签页、另一条合法入口仍不知道按钮的状态。把请求放在哪条记录上判断，会直接决定谁被允许继续，不能从界面组件的生命周期推出这条规则。

在看实验前先写出一个顺序执行的参考答案。若两人都采纳，先执行者成功，后执行者读到已采纳后停止，学习关系只有一条；交换顺序仍只有一条。若一个采纳一个放弃，则先采纳时有一条关系，先放弃时没有关系，但都不能既接受采纳又接受放弃。之后遇到某种交错，若最后结果不可能用上述任何一种先后解释，就已经知道程序有问题，不需要等系统出现损坏的字段才开始排查。这里说的是成功提交的决定顺序，发送按钮的时间和返回页面的时间都未必按这个顺序排列。

### 在两个窗口中保留同一个过期判断

沿用第19、27章的隔离练习库，在DBeaver建立A、B两个SQL编辑器。每个编辑器先运行：

```sql
SELECT current_database(), current_user, pg_backend_pid();
```

库名必须相同，PID必须不同。两个标签不一定对应两个连接；若PID一样，使用连接上的“新建SQL脚本”，或复制同一连接配置再开编辑器，重查PID后才继续。保持Auto-commit模式，实验仍用明确的BEGIN、COMMIT、ROLLBACK控制范围。

在A空闲时执行 `02-races.sql` 的setup块。这里的decision代表候选决定，result代表采纳生成的关系，只保留复现所需字段。它们位于专用chapter25_lab，绝不替换正式candidates和learning_records。

```sql
CREATE SCHEMA chapter25_lab;
CREATE TABLE chapter25_lab.decision (
  id integer PRIMARY KEY, status text NOT NULL
);
CREATE TABLE chapter25_lab.result (
  id integer PRIMARY KEY, candidate_id integer NOT NULL
);
INSERT INTO chapter25_lab.decision VALUES (1,'pending'),(2,'pending');
```

先在A执行BEGIN并查询id=1，再到B执行同样两句，确认两边都看见pending。A接着无条件把状态改成accepted，插入result(101,1)，COMMIT。B保留刚才读出的判断，也无条件更新id=1，插入result(102,1)，COMMIT。查询result会得到同一candidate_id的两行。

![两个过期判断写出同一候选的两条结果](images/dbeaver-race.jpg)

实拍中candidate_id=1的records为2；每笔事务都提交成功，业务上的单次确认规则却已经被破坏。

```mermaid
sequenceDiagram
    participant A as 请求A
    participant DB as 数据库
    participant B as 请求B
    A->>DB: 读候选1：pending
    B->>DB: 读候选1：pending
    A->>DB: 无条件更新＋插入结果101
    A->>DB: COMMIT
    B->>DB: 按旧判断更新＋插入结果102
    B->>DB: COMMIT
    Note over DB: 每笔事务都完整，却违反只能确认一次
```

A已经提交，并不意味着B的应用变量会自动变成accepted。数据库接受B的UPDATE，是因为WHERE只有id，没有声明“只有仍为pending才能改”。两笔事务内部没有半次成功，最终业务规则仍然错了。这里缺少的是对竞争前提的保护，不能靠再套一层事务解决。

如果B的UPDATE在A提交前到达，它会先等A的行锁；但A提交以后，B的无条件UPDATE仍能继续。等待保证写入不会同时撕裂同一行，不保证第二个写入符合产品规则。看到请求排队，不能就认定竞争已经处理。

先从两张实验表手算出异常到底藏在哪里。甲提交后，决定一只有一行，状态已采纳；结果表有一行，结果主键是一零一，来源是一。乙提交后，决定一仍然只有一行，状态看起来没变，结果表却有了主键一零二，来源也是一。只看决定表，改前和改后的截图几乎相同；只看结果表的主键列，两项又完全不同。需要重复出现的是来源列，而这列没有被本实验的主键约束成唯一。因此先查原始明细，按来源和结果主键排序，再试着从这个网格推出能自动找到问题的汇总。

```sql
SELECT candidate_id, id AS result_id
FROM chapter25_lab.result
ORDER BY candidate_id, id;

SELECT candidate_id, count(*) AS result_count
FROM chapter25_lab.result
GROUP BY candidate_id
HAVING count(*) > 1;
```

第一条查询里一个结果主键占一行，第二条里一个来源占一行。手算第二条只该剩一行，来源一、数量二。若把结果主键也列入分组，每一组就又只有一行，最后会得到空网格，恰好把真正的问题藏掉了。若还想把尚无结果的决定二也列出来，起点应改成决定表向结果表做左连接，计数改用结果主键；仅从结果表分组，无论怎样排序都无法凭空生成一个尚未出现的来源。这是三类实际会用到的查询：取证读明细，扫异常按重复键分组，盘点全部决定则保留零值那一侧。

前面两次 SELECT 都是真的，不存在一个客户端“读错了状态”。错误发生在更晚的时刻：乙的操作实际提交时，数据库拿到的条件只问编号是否仍然存在，答案确实为真。等数据库报告写入成功再到应用里检查之前那个变量，变量还是旧值，已经不可能验证此刻的前提。也不能用“甲已经比乙早返回”来修复这段逻辑；即使乙一直等到甲完成才发出写入，它仍沿用甲开始前那次读取。要改变的是写入当时交给数据库判断的条件。

### 把有效前提和修改放在同一条语句里

现在使用未动过的id=2，按脚本A3、B3、A4、B4顺序执行。A先BEGIN并运行：

```sql
UPDATE chapter25_lab.decision
SET status='accepted'
WHERE id=2 AND status='pending'
RETURNING *;
```

A先不要提交。B也BEGIN，运行相同条件、但将目标状态改为discarded的UPDATE。B会等待；切回A执行COMMIT以后，B的结果网格应是零行。最后在B单独ROLLBACK，查询decision确认id=2仍为accepted。

![B等待后重新检查pending条件，返回零行](images/dbeaver-conditional-zero.jpg)

这里的No data来自UPDATE的RETURNING结果，表示B没有改到任何行；不是说decision表为空。

在本章READ COMMITTED下，B等待的行被A提交更新后，数据库会针对更新后的行重新判断WHERE。status已经不满足pending，因此B没有取得改变这行的资格。不是B“失败后也可以继续插入结果”，而是应用必须检查影响行数：零行立即结束这次业务决定，只有一行才往下建立表达和学习关系。

当前代码的 `updateMany({ where: { id, status: 'pending' } })` 正是这个位置。前面的findFirst负责读取不可变内容、检查归属并给出不存在／已结束的结果，不能取代条件UPDATE；后面的 `claimed.count !== 1` 负责阻止竞争失败者继续写入。若A回滚，B就有机会在仍为pending的行上成功；不能把“第一个发到服务器”当成承诺的胜者。

这也解释了为什么本章不另外给候选增加version：pending只能走向终态，不允许重新打开，状态本身已经表达当前更新所需前提。如果未来允许重新编辑、回到pending或基于旧页面覆盖内容，就需要判断“还是不是那一版”；章末的支线28A用具体的丢失更新和ABA过程展开这个差别。

自己写这条条件更新时，可以先只写一条定位目标的 SELECT，确认编号二存在，再把“当前允许改变”写进同一个 WHERE。然后只把读取动作换成设置目标状态的 UPDATE，最后加 RETURNING 输出实际改到的编号与新状态。这样的推导并不需要先执行一次 SELECT 才能运行 UPDATE；前面的读只是设计条件时核对样本，真正有裁决力的是最后一次写入。若把状态条件写成目标状态，第一次操作在待决定行上就会落空；若把起始状态写进 SET 而遗漏 WHERE，两次竞争仍然只按编号决定资格。让读者自己用一句话读出“把什么改成什么，前提是什么”，很容易发现两者写反。

在两窗口操作时，把结果网格的时间也记录下来。甲已经看到返回一行，此时乙的窗口正在等待，没有网格结论；其他连接普通读取仍可能看到旧的待决定。只有等甲结束，乙才会有最终的影响行数。若甲提交，乙返回零行，这条语句本身执行成功，并没有使乙的事务进入错误状态；示例选择回滚乙以结束工作，而不是修复一条失败的 SQL。如果乙等得太久被取消，得到的则是错误，事务状态与正常零行不同。把窗口上“还在执行”“已执行没有匹配”“执行被拒绝”三种反馈区分开，才能决定要不要继续发后面的插入。

还可以在原实验结束后验证另一半推导，而不改动已经观察过的两行。在空闲的练习连接向 decision 新增一条未使用的编号三、状态 pending；若三已存在，选一个新的空闲编号。甲乙仍在各自的显式事务中，只把 A3、B3 的编号改为这一行。甲收到一行后暂停，乙发出放弃的条件修改。在乙仍等待时，这次让甲回滚。到了乙，仍然有效的待决定行应返回一行、状态为 discarded。再回滚乙，第三个普通查询就应读回 pending，说明之前乙能取得资格与乙最后有没有提交也是两个问题。此变式只操作隔离表；后面锁实验仍用原来的编号一、二，清理时随实验表一起收尾。

## 28.2 唯一约束守住关系，迁移先面对已有事实

### 条件写入与唯一约束不是二选一

条件UPDATE防止当前采纳路径的两个竞争者同时通过，但未来新增的脚本也可能绕过它，直接向learning_records插入。我们已经决定一个候选只对应一次采纳关系，就应该让这项可用列精确表达的规则落在数据库里：candidate_id必须唯一。

这个约束不是 `(user_id, candidate_id)`：candidateId在整个表中已有唯一身份，并且它通过修订归属于一个用户。加入user_id反而允许两个不同用户引用同一个candidateId各插入一次，弱化了本次规则。权限仍要由带用户范围的查询保证，唯一约束本身不核对候选真正属于谁。

learning_records的id主键解决“这一行是谁”，candidate_id唯一解决“这种业务关系最多出现几次”。两者不能互相代替。相反，不能在expression_forms.text上直接加唯一来解决“相同英文”：文字相同不保证义项相同；当前也没有规定大小写、空格和形式归一化规则。数据库可以严格执行我们声明的相等，却无法替我们决定业务身份。

唯一性检查还会参与并发等待。两个事务插入同一个唯一值时，后者可能需要等前者提交或回滚，才能知道这个值是否最终被占用；提交后产生23505，回滚后则可能成功。所以“先查没有，再插入”仍不能替代约束，也不能把一次没查到理解为预订了这个值。

从关系的一行里找两个不同的“相同”。甲采纳候选丙，生成一份新的学习记录。过一会儿若有人想为同一丙再记一条学习关系，即使给它一个全新的学习标识，也是在重复表达“这份候选已经被收入学习”这个事实。主键回答能否准确点开其中一行，业务唯一键回答同一来源能否同时有两行。如果把主键和来源一起放进联合唯一约束，前者每次生成都不同，两项组成的元组几乎不会重复，真正要阻止的那一对关系反而可以共存。判断候选键时，先在纸上构造一对产品明明要拒绝的行，再问所选的列值是否真的相等。

同样的方法可用来检验有没有管得过宽。用户甲依据丙采纳一次，又依据另一个候选丁采纳一次，按本章产品规则可以有两条学习记录。只把用户列设唯一会把第二次正常学习也拒绝；把表达的中文含义设唯一，会把不同来源、同样文字的两笔确认硬拼成同一个结果。合适的约束要经得起两种反例：应当拒绝的一对必然撞在同一个键上，应当允许的一对不会仅因为无关字段相同就发生冲突。先用这样的成对事实缩小选择，再去写模型比先搜索 ORM 的一对一写法踏实得多。

还可反方向检验“恰好一次”这个容易说大的承诺。空的学习记录表当然满足唯一约束，里面甚至没有一行。若仅检查约束存在，没有检查业务提交过程，就无法推出某个已采纳候选一定找得到结果。条件更新负责争取本次转移，事务保证这次转移不会撇下必需的结果，唯一约束又限制同一来源的结果最多一个。这三处证据合起来才能解释正常路径为何恰好有一条；只对结果表做分组，零次的候选从一开始就没参加计算。

### 收紧之前，逐条解释重复数据

停止全部旧写入口，包括API和会写入的脚本。在DBeaver运行 `01-inspect.sql` 的重复检查：

```sql
SELECT candidate_id, count(*) AS record_count,
       array_agg(id ORDER BY id) AS record_ids
FROM public.learning_records
GROUP BY candidate_id
HAVING count(*) > 1;
```

零行说明这个库当前没有违反新规则的记录，不说明所有来源永远正确；迁移成功后才由数据库持续防守。若有行，继续查看这些学习记录的user_id、expression_id、候选状态和来源修订。先判断它们是同一次错误复制、不同表达被错误挂到同一候选，还是旧需求允许多次学习却没有另建事件表。

这三种情况会导向不同处理。纯实验复制行可在核实引用后删除那一条；真实错误关系需要保留来源、调整引用并记录修复；如果它本来代表多次学习事件，就不能删到只剩一行，应先重新设计“采纳关系”和“学习事件”的粒度。没有哪个通用的 `DELETE ... MIN(id)` 能替代这个判断。UUID与created_at也不足以证明谁是正确记录。

审核和迁移之间保持停写，避免刚检查完就又插入重复。当前数据量与操作窗口允许常规ALTER TABLE；它需要较强的表锁，会与正常访问冲突，因此不是零停机方案。以后数据量大到扫描和持锁不可接受时，应另行设计并发建索引、校验与接管约束的发布过程，不能只把超时改成无限。

如果独立写迁移前的第二条调查查询，别急着把所有表合成一条长语句。先只投影重复来源的 candidate_id，即可得到一个待查集合；再从学习记录表中选出 candidate_id 在这个集合里的全部明细，不要在外层再做分组。每一行仍要有它自己的学习标识、用户标识、表达标识，这是随后整理事实所需的最小单位。接着用来源候选的 revision_id 找修订，再用修订的 capture_id 找素材，从素材行取真正的归属用户。把这个用户与学习记录上的用户分成两列，不能在连接条件里先要求两人相等，否则恰好需要解释的不相等明细会被你自己过滤掉。配套的第二条明细查询可以在写完后用来比列和连接路径。

假设原始明细有三行：甲来源的两笔分别指向两个表达，乙来源只有一笔。按候选分组后得到甲二、乙一，HAVING 应留下甲一组；回到明细应该重新看见两行。如果你的第二张结果只剩甲一行，多半是把汇总行当成待修复的实体；如果显示三行，可能漏了回到问题集合的条件。如果明细接上多个英文形式后从两行变成四行，要先回到学习记录粒度才可谈重复次数。手算三种预期结果，能让一条看起来很像对的调查查询暴露出关键错误。在真实库检查没有重复时，可用前面的 result 实验表验证分组逻辑，不必给业务表人为塞入坏数据。

分析留存行还需要时间方向。若先导出当前明细、继续让旧接口运行、过一阵才迁移，即使你保存的那一页完全没有重复，也不能证明后来的写入没有改变结论。数据库建立约束时会对当时的数据重新检查，正常情况下不会静默接受违反规则的行；问题是你曾承诺的部署窗口可能被一次本可提前解释的冲突耗尽。停写的作用是使业务判断与迁移所检查的事实尽量一致。已在途的写事务也要结束；仅关浏览器页面不会自动清掉 DBeaver 里一个显式 BEGIN。先核对目标连接和现有事务，再决定何时可以把“检查过”交接给执行迁移的人。

还有一个容易漏掉的地方：本章没有新增列，上一章那些findMany启动探针在旧结构上也能成功。因此DatabaseService在连接就绪前增加pg_constraint检查，要求名为learning_records_candidate_id_key的即时、已验证单列唯一约束存在；否则记录安全错误码ACCEPTANCE_CONSTRAINT_MISSING并退出。启动不自动加约束，部署与运行的职责继续分开。在 `src/database.service.ts` 原有learningRecord读取探针之后、database.ready之前加入：

```ts
const constraints = await this.client.$queryRaw<{ definition: string; condeferrable: boolean }[]>`
  SELECT pg_get_constraintdef(oid) AS definition, condeferrable
  FROM pg_constraint WHERE conrelid = 'public.learning_records'::regclass
    AND conname = 'learning_records_candidate_id_key' AND contype = 'u' AND convalidated
`;
const constraint = constraints[0];
if (constraints.length !== 1 || !constraint || constraint.definition !== 'UNIQUE (candidate_id)'
  || constraint.condeferrable) throw Object.assign(new Error('Acceptance constraint is missing'), {
    code: 'ACCEPTANCE_CONSTRAINT_MISSING',
  });
```

这里检查的是本章迁移建立的具体结构，不是通用数据库审计器。异常继续进入原有启动catch，关闭连接并拒绝就绪；错误码提取器同时保留ACCEPTANCE_CONSTRAINT_MISSING，避免日志只剩不明原因的DATABASE_FAILURE。

在**已部署本次迁移**且有一条成功采纳的隔离练习库中，可以用普通的重复关系验证数据库校验。若目前只完成迁移、尚无这类样本，把本段留到 28.4 首次采纳成功后，在该练习服务实际连接的库上做。把下面 UUID 替换为已采纳的候选 ID，先单独执行 BEGIN，再执行 INSERT；新主键使冲突明确落在 candidate_id 上：

```sql

SELECT gen_random_uuid(),user_id,candidate_id,expression_id
FROM public.learning_records
WHERE candidate_id='00000000-0000-4000-8000-000000000000'::uuid;
```

![直接插入重复候选关系被23505拒绝](images/dbeaver-unique-error.jpg)

错误点名learning_records_candidate_id_key。随后单独ROLLBACK，再用01-inspect.sql查询该候选，确认原有关系仍为一条。若INSERT没有报错而影响零行，先核对样本ID是否确实已有采纳关系，不把零行当成约束生效的证据。

从验证者的角度，可以把唯一性的证据排成三层。第一层是模型：打开 schema 可以知道编译后的客户端将如何导航到这条关系，但并不知道某个库真的执行过迁移。第二层是数据库目录：约束行的 contype 是唯一，定义中只有 candidate_id，并且已经验证、不可延迟，说明库接受的结构和新程序预期一致。第三层是实际写入：在有原关系的隔离库中，新主键引用同一个来源，得到的错误要点名那条约束；回滚后原主键及指向的表达仍在。每层都有独立的反例，模型已改而连接开错库、库里只有相似名称的普通索引、用不存在的来源结果做了零行插入，单看某一层都会造成误判。

为什么探针连约束定义都要看？设数据库里有一个名字看起来合适、却约束“候选加表达”的联合键。给同一候选生成另一个表达就能有两条关系，名称匹配显然不够。反过来，若手工建立了功能相近但名字和部署约定不一致的索引，仅用日常读取请求也很难发现这次迁移缺失。此处启动检查验的是当前交付承诺的具体结构，遇到拒绝应先查 API 实际连接的库、迁移版本和目录定义，再决定部署是否漏做。不应因为在自己的编辑器里成功展开过一张表就把检查删掉。

## 28.3 需要保护一段判断时，锁住什么

### 行锁保护现有对象，普通读取仍能进行

当前状态竞争用条件UPDATE已经足够。如果后续决定要基于一行的多个字段、做几步检查再写回，`SELECT ... FOR UPDATE` 能先锁住读到的行，使其他不兼容写入等待到当前事务结束。关键是随后检查与修改仍在同一个事务、同一连接里；自动提交的一条FOR UPDATE刚执行完就释放，保护不到下一条语句。

保留28.1的实验表，打开 `03-locks.sql`。A执行BEGIN和id=1的FOR UPDATE，不结束事务。B普通SELECT仍可读到已提交的行；B若试图UPDATE，则要等待。它读到旧值并不违反行锁：MVCC普通读取不需要先取得这种写锁，锁定也不等于让其他人看不见这行。

先预测 B 在三种读法下分别能获得什么。普通查询的任务是展示某一刻可见的状态，它可以直接读已提交版本；锁定读取除了要看行，还要求获得后续修改的排他资格；而实际更新既要获得写入资格，也要重新检查自己的更新条件。三者可能用相同的 WHERE 和同一个编号，返回速度和结果却截然不同。若 A 只是取得锁、还没改值，B 的普通读甚至会看见跟 A 完全相同的文字。两个人看见同一行的同一个值，不表示两人都拥有修改资格；这就是先看见再决定的程序为什么不能靠显示正确来证明并发正确。

给实验选择两个明确的观察点。第一处是 A 的锁定读取成功后、事务尚未结束，看它返回的编号确实是一；第二处是 B 的限时修改真正开始后，看结果是否长期停在“执行中”。如果第一处其实是零行或编辑器把语句作为独立事务自动提交，第二处不发生等待恰好是正确的。反过来，若 B 从一开始连普通的读取也无法返回，先看是否用了带锁的读取、是否连接到目标库、是否有别的表级操作，而不要假定 A 的普通行锁能解释一切阻塞。下面的一秒更新专门用来制造可判别的反馈，在 B 的普通 SELECT 后不要额外先运行一条无期限等待的 UPDATE。

在B用单独的事务设置一秒等待，再尝试写入：

```sql
BEGIN;
SET LOCAL lock_timeout = '1s';
UPDATE chapter25_lab.decision SET status='pending' WHERE id=1;
```

应得到55P03。随后单独执行ROLLBACK，恢复连接；A仍持有原锁，B的超时不会替A提交或回滚。此时A继续保持原事务，供后面的NOWAIT与SKIP LOCKED对照使用；不要提前释放。SET LOCAL只在本事务有效，不把这个实验配置遗留给连接池的下一位使用者。

![锁等待超过限制后得到55P03](images/dbeaver-lock-timeout.jpg)

同一对象上可以选择不同等待策略：NOWAIT不等冲突行，立即失败；SKIP LOCKED直接跳过被锁行，可能返回空集合。脚本分别给出操作。对于“采纳指定candidateId”，空结果不能被解释为不存在；对于从许多任务中任选一项的队列领取，跳过正在被处理的行才可能符合含义。选择取决于请求是否允许换对象，而不只是想让错误少一些。

![NOWAIT立即报告无法取得行锁](images/dbeaver-nowait.jpg)

![SKIP LOCKED跳过被锁住的指定行](images/dbeaver-skip-locked.jpg)

两图中的请求都指向A仍锁住的id=1。NOWAIT与等待超时都可能使用55P03，但触发方式不同；SKIP LOCKED则正常返回零行，不能据此断言id=1不存在。

要知道谁在等谁，按03脚本让B重新BEGIN，设置 `lock_timeout='30s'` 后再次UPDATE被A锁住的行；这次留出手工观察窗口。在B仍等待时，到第三个空闲连接查询：

```sql
SELECT pid, state, wait_event_type, wait_event,
       pg_blocking_pids(pid) AS blockers
FROM pg_stat_activity
WHERE datname=current_database() AND pid<>pg_backend_pid()
ORDER BY pid;
```

先按记下的A/B PID定位。B出现Lock等待、blockers包含A，说明证据指向锁链；A若是idle in transaction，说明它已经没有执行语句，却仍保留事务。不要先加连接池容量：更多请求只会一起堵在同一个持锁者后面。在30秒内先回到自己的A窗口ROLLBACK，B的UPDATE完成后也ROLLBACK；若B先超时，同样先回滚它，再结束A。对不认识的会话先查来源和业务影响，不直接终止。查询不输出SQL文本，避免把原文或参数带入截图和常态日志。

![第三连接观察B等待A的事务锁](images/dbeaver-blocker.jpg)

本次A的PID为76794，B为79056；图中按已核对的两个PID筛选，并把blockers列命名为blocked_by。B的Lock／transactionid与blocked_by中的76794连成了等待关系；你的PID应以自己当前连接为准。

FOR UPDATE锁的是实际读到的行。查询id=99没有结果，就没有锁住未来可能插入的99；“查不到所以加了行锁”不能保护不存在的关系。唯一约束适合阻止同一个确定键被插入两次；如果需要在对象尚未存在时协调一整段创建流程，才需要考虑一个所有参与者事先都能计算的锁身份。

从空白写等待查询时，先决定输出中一行代表一个后端连接，因而从会话活动视图开始。选择后端进程号供对照，执行状态回答这个连接眼下是否在执行语句，等待类别回答它是否在等锁，再把该进程号传给查询阻塞者的函数。最后才加上数据库名和本次两个进程号收窄输出。不要靠“正在执行”筛掉全部空闲会话：持锁者完全可能已经把结果交回 DBeaver，正在等你按下提交。这时正是它还没有结束的事务挡住别人，若把它从结果中提前过滤掉，你只能看到被挡的一半。

试着把网格翻译成一条有方向的句子：若 B 这一行的阻塞者列表中有 A，表示 B 等待 A 取得释放条件；并不能反向推出 A 同时也在等 B。A 可能只是在等你切回它的窗口。当你在 A 回滚后，那条等待边就会消失，B 更新成功并持有自己的行锁，直到 B 也回滚。观察者若只在两人都结束后才点执行，会看到两个空数组，这只能说明取样时没有这段阻塞，不能证明刚才的请求从来没有等待。要有意捕捉这个中间状态，先在第三个连接准备好只读查询，确认 B 已发出更新后再执行，并在期限内回到 A 放行。

还有一个看似省事的选择是在等待者窗口里另写一条查询问“我在等谁”。同一个后端正在执行那条更新，不能同时接收下一条观察查询并返回结果。若界面把新标签页绑在同一连接，第二条语句也会排在后面。第三个空闲后端是这次观察真正需要的工具条件；反过来，如果为了看锁在观察者那里又对业务行执行锁定查询，就会给原来的等待关系加进一个新的参与者。只读取会话号、状态和阻塞者列表，能在不改变争用对象的前提下回答问题。

### 事务级建议锁保护约定，而不是表

PostgreSQL的advisory lock可译为建议锁：数据库提供锁管理，应用约定某个整数键代表什么。它不会自动附着某张表，正常INSERT／UPDATE也不会因为那个键存在就被阻止；所有竞争入口必须先遵守同一个取锁协议。

在 `05-advisory.sql` 中，我们只用固定整数演示机制，2501代表实验命名空间，1代表实验对象。A、B分别BEGIN后执行：

```sql
SELECT pg_try_advisory_xact_lock(2501,1) AS acquired;
```

A先得到true，B得到false。false不是SQL错误，B事务仍可执行语句；应用若忽略它继续写，等于没有协调。A执行ROLLBACK后，B在自己的事务里再次调用得到true，然后也ROLLBACK。这里回滚既撤销业务写入，也结束事务级锁的持有；不要再调用会话锁的unlock去处理它。

![A持锁时B取得建议锁失败](images/dbeaver-advisory-false.jpg)

![A回滚后B取得同一建议锁](images/dbeaver-advisory-true.jpg)

两张图都返回一行：acquired中的空框是false，勾选是true。这与SKIP LOCKED没有返回行是两种不同结果。

`pg_advisory_xact_lock`会等待，try版本把“暂时拿不到”交给调用者决定；锁对象仍相同。我们选择事务级而非会话级，是因为连接池中的会话会被复用，业务函数结束不代表会话结束。会话级锁甚至不会因为事务回滚自动释放，漏掉unlock可能影响下一个请求；事务级锁的生命周期与当前业务事务更容易对齐。[PostgreSQL 18锁文档](https://www.postgresql.org/docs/18/explicit-locking.html)列出了二者差别与冲突方式。

锁键必须从被保护的稳定身份推导。随机生成键会让同一对象的两个请求拿到不同锁，完全失去互斥；不同路径使用不同大小写、前缀或命名空间，也有同样问题。本章业务ID是UUID，不能把示例整数直接替换成截取的一小段UUID：生产方案需要统一的编码／映射规则，明确整数空间、碰撞和所有入口的一致性。哈希碰撞通常会让无关对象额外排队，但同一个对象被编码成不同键会直接漏锁。

本章正式采纳尚不复用现有表达，也没有账号状态变化要协调，因此不增加一个全局建议锁把所有用户排成一队。先保留唯一约束与候选条件写入；等出现跨对象前提，再根据下一节的顺序和28.5的边界选择真正需要的锁。

建议锁返回的布尔值很像一个业务查询结果，实际表示的却是一次获取资格的尝试。两人都处于事务内，甲取得键后，乙收到假，它的事务仍然可以正常执行下一条语句。甲释放以后，乙若什么都不再调用，那个假值不会自动变成真；它需要再次向数据库申请，再根据新的布尔值决定能否进入受保护的工作。若程序无论真假都继续创建对象，相当于只记录了一次锁竞争日志，没有约束谁能往下走。若在锁失败时选择退出，应结束这个事务；若产品允许稍后再试，也要明确何时才会有新的判断。

与行锁对比，最容易搞错的是把键的第二个整数当成数据库已经帮你找到的记录编号。这个调用没有表名，也没有读取任何业务列。即使碰巧有编号一的决定行，数据库仍不会凭数字相同就把这两件事连上。反过来，正因为它可以在关系行尚未存在时取得，所有参与者若事先能计算同一身份，就能保护从查找直到创建的一整段选择。代价是这条约定必须被维护，包括名称范围、取键方式、锁的共享模式与释放位置。这里用两组明确的整数做有限实验，没有把正式候选的 UUID 随意截成整数，更没有假定处理任何两段相似文字都能自然算出相同的键。

如果一个窗口得到真，另一个本应得到假却也得到真，依次沿三个条件排查：是不是处于同一个数据库、是不是两个不同后端、第一次成功之后是不是还在同一个显式事务。一个后端再次申请自己已持有的锁，结果不能代表另一个参与者；使用自动提交而未先 BEGIN，第一条语句结束时事务锁已释放，后来者当然还能取得。最后比对键的两个分量及调用的模式；两个共享持有者可以同时成功，正是后面生命周期实验需要的行为。这样即使界面只给你两个勾选框，也能推断出下一步该在哪个位置验证。

## 28.4 等待、死锁与重试，分别在哪里结束

### 从单向等待变成循环等待

A占着候选1、B等候选1，只是等待；只要A结束，B就有机会继续。死锁需要形成一个环：A持有1再申请2，B持有2再申请1，两边都在等对方先结束。

```mermaid
flowchart LR
    A[事务A 已持有1] -->|等待2| B[事务B 已持有2]
    B -->|等待1| A
```

打开 `04-deadlock.sql`，先在A执行A1锁住id=1，在B执行B1锁住id=2。接着A2申请2会挂起，不要等它完成，立即切到B执行B2申请1。数据库检测到环后会中止其中一方，报40P01；另一方通常随之继续。被选中的不一定是后发请求，业务不能依赖谁被牺牲。

![数据库检测到两个事务相互等待并报40P01](images/dbeaver-deadlock-victim.jpg)

实拍中79056等待76794，下一句又指出76794等待79056，两个方向合起来才是环；这一次B成为中止方。错误里的ShareLock on transaction表示等待对方事务结束，不表示实验改用了FOR SHARE。

脚本设置的statement_timeout=10秒只是实验兜底。若切换太慢、先出现57014，那是语句超时，本轮没有证明死锁。两边分别ROLLBACK，重新按顺序操作。成功复现后，两边也都ROLLBACK：未被中止的一方仍有自己的事务和锁，不能只关闭报错窗口就离开。

避免死锁首先靠一致的取锁顺序。无论请求参数给的是[2,1]还是[1,2]，都先锁1再锁2；不要让“来源表达先、目标表达后”形成两条相反路径。对本例不可变的id，可用：

```sql
BEGIN;
SELECT id FROM chapter25_lab.decision
WHERE id IN (1,2) ORDER BY id FOR UPDATE;
ROLLBACK;
```

顺序必须覆盖所有协作入口与所有相关对象，不是只给一条查询加ORDER BY就万事大吉。若排序字段本身会变化、锁在多个查询中获取，或触发器又访问其他表，还要重新检查实际锁序。外键检查和唯一索引也会引入等待；代码里没有FOR UPDATE并不代表不会死锁。

遇到持续死锁，先记录安全错误码、操作名和requestId，结合等待链定位相反顺序；修复后用原交错再试。短事务、统一顺序会减少冲突，但无法许诺数据库永不报告可重试中止，因此应用还需要一个有限的恢复出口。

一条等待边怎样变成环，可以先只盯住两人的下一步。甲持有第一行、准备取第二行，乙持有第二行。如果乙此刻只想提交，它并没有任何动作依赖甲，只要让乙运行就能唤醒甲；再等几秒有意义。如果乙必须先拿第一行才肯提交，甲在等乙走完、乙也在等甲走完，此时就算两边都获得再多计算时间也走不到释放锁的那一句。死锁检测需要解除的是后面这种循环依赖。把错误理解成“数据库觉得太慢了”会把两种故障混为一谈：一边最终会主动放行的慢操作可以超时，却不必发生死锁。

如果决定改为统一锁序，不能只把两笔请求里的数组各自排序后又分给不同的异步任务随意发出。要能从实际执行的数据库语句推出：对于需要一和二的任何事务，取得一的动作都在尝试取得二之前。这样甲乙至多在第一行的入口相遇，先等待的人尚未拿着第二行，便不能构成刚才的环。这个推导对两条都已存在、身份稳定的行成立；如果将来某条路径先锁别的表再回来取第一行，必须把那个对象画进图重新检查。可以把“谁已经持有、谁还要取得”列成两栏，逐条检查是否存在回头路，不必从某个固定错误码反推一条想当然的锁序。

读死锁错误里的两组进程号时也要核对操作阶段。如果第一个窗口拿完行一就一直显示等待，说明它甚至没到申请行二的阶段，或实验开始前这行已被别的未结束事务占用。此时第二个窗口即便报错，也不能沿用两人互相等待的故事。先结束本轮自己的事务，检查实验对象和进程号，再从两边第一步都返回一行的状态出发。把明确取得第一把锁看成必要前提，才不会将上一次忘记回滚带来的等待误算作这一次有意设计的环。

### 回滚已确定，才考虑自动重新执行

PostgreSQL的40P01表示死锁中止，40001表示为避免序列化异常而中止。它们与“连接断了，COMMIT到底到没到数据库”不同。前者可以从新的事务重新读前提，后者可能已经提交，需要查询事实与操作身份。服务器内部事务重试和客户端重新发送HTTP请求，也不是同一层动作。

本章使用的Prisma 7.10.1对生成查询中的事务写冲突／死锁提供P2034。采纳仅对此已知错误类型重试；不能见到一个带code属性的任意对象就认定事务已经回滚。原生SQL经适配器包装后的错误层次可能不同，不能把pg的40P01直接填到Prisma判断里就假定会命中。

在 `src/prisma-candidate.store.ts` 引入Node标准库delay，把上一章完整的$transaction放进有限循环。下面保留重试与事务边界，中间的采纳写入仍是27.2的原实现：归属查询、pending条件更新、表达及形式、学习记录、响应投影都必须留在回调内。

```ts
import { setTimeout as delay } from 'node:timers/promises';

// accept通过validId后；database.run仍负责最终错误分类与安全日志。
return this.database.run('acceptCandidate', async () => {
  for (let attempt = 0; ; attempt++) {
    try {
      return await this.database.client.$transaction(async tx => {
        await tx.$executeRaw`SET LOCAL lock_timeout = '1s'`;
        // 原有采纳主体：所有查询与写入使用tx，不能使用根client。
        // 按 27.2 保留候选检查、条件更新、表达及形式、学习记录和投影。
      }, {
        isolationLevel: Prisma.TransactionIsolationLevel.ReadCommitted,
        maxWait: 2000,
        timeout: 5000,
      });
    } catch (error) {
      if (!(error instanceof Prisma.PrismaClientKnownRequestError)
        || error.code !== 'P2034' || attempt >= 2) throw error;
      await delay(25 * 2 ** attempt + Math.floor(Math.random() * 25));
    }
  }
});
```

attempt从0开始，所以最多执行三次，只有两次退避，分别为25～49、50～74毫秒。少量随机抖动避免两个失败者每次在同一时刻重新冲撞；等待放在事务外，不占着上次的锁睡觉。次数限制使持续冲突能够明确结束，不能用无限重试掩盖错误锁序。

每次重试都重新执行读取、判断和写入，不能复用上次查到的candidate，或只重试最后一个INSERT。acceptedAt和新行UUID也在新事务里重新生成；前一次确定中止，它们没有成为已提交事实。重试时若其他请求已经采纳，新的读取会得到冲突，最终409是合理结果，不必强求每次重试都返回201。[PostgreSQL的重试说明](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)特别强调重跑完整决策过程；[Prisma事务文档](https://docs.prisma.io/docs/orm/v7/prisma-client/queries/transactions)给出了P2034对应的客户端边界。

这段回调现在只有数据库操作。若以后把发邮件、扣费、调用AI放进去，第一次事务虽然回滚，那些外部副作用也不一定撤销，再次执行可能重复发生。不能为了复用重试循环把外部网络调用塞进来；第27章划出的本地事务边界继续成立。

把循环按一次真实的业务决定摊开，会看到 catch 的位置很讲究。数据库拒绝这次事务，拒绝先越过事务回调，事务层结束本次尝试，外面的捕获才有机会判断要不要重新开始。若把重试移到回调里面，当前连接可能已处在失败事务，继续下发语句只会报告前序错误没有处理；即使上一条错误来自应用自身，沿用前半段已写的状态也未必还能代表一次干净重算。外层的 database.run 包住整个过程，面向上层的是一次采纳业务；多次获取事务和两次退避都属于其中可能发生的工作。日志里一次存储调用与数据库实际开始过几轮事务，不保证是一一对应。

从零写出循环的终止条件时，先在纸上编号，而不要从“重试三次”这个含混的需求直接翻译成代码。若第一次直接成功，总共一次，没有睡眠；第一次明确中止、第二次发现候选已经由别人决定，第二次以冲突正常返回，总共两次，一次睡眠。若头两次明确中止，第三次也以相同原因抛错，次数已经用光，此时必须抛出去，不能再等第三次退避。由于判断发生在当前尝试的 catch，编号零、一起初都可以继续，编号二要结束。若写成大于二才结束，实际就让一次请求多占了一次事务机会。

配套的有限重试测试还能帮我们判断“通过”到底证明了什么。测试用一个可控的事务入口在指定次数内抛出同一类已知错误，随后正常返回冲突。检查的是调用次数以及结果是否能交还给上层；正常返回冲突同样代表事务入口成功完成判断，不表示采纳生成了新对象。这个测试没有启动真正相互等待的两个会话，所以不证明某种数据库交错必定包装成指定错误。双会话脚本则正好相反，能让一个数据库事务因等待环而中止，但没有经过生产 Store，不能证明应用真的只重试两次。想解释一次线上行为，要把数据库原因、驱动交给程序的错误以及程序作出的决定逐段对上。

### 几种超时不能合成一句“最多五秒”

本章一秒的锁等待可能先于死锁检测触发，因此同样的循环等待也可能先报55P03，而不是P2034；不要把所有死锁场景都想成必然进入自动重试。04脚本不设置这个一秒限制，用于单独观察数据库检测到环的结果。

SET LOCAL lock_timeout的1秒限制每一次获取锁时的等待；maxWait的2秒限制Prisma开始事务的等待；timeout的5秒限制每次交互式事务的执行。重试会重新申请事务，还包括事务之间的退避，所以整个HTTP请求不能据此声称最多五秒。若产品要求严格的请求总预算，还需在外层统一分配剩余时间，不能把三个配置名称当成同一计时器。

锁等待55P03在本章不进入重试循环。它可能只是某个编辑器忘了结束事务，连续重发只会继续占用连接。`src/database-errors.ts`把55P03与重试耗尽的P2034纳入临时不可用，最终映射503；捕获适配器内层55P03时优先记录这个安全码，不记录消息、SQL、参数或连接串。实际锁超时外层可能是P2039，不能只看外层就按普通500处理，也不能把全部P2039都认作锁超时。沿用第22章已收集外层与适配器内层codes的函数，只修改这些位置：

```ts
// transientCodes原有条目全部保留，再加入：
'P2034', '55P03',

// databaseFailure内code的选择：先保留明确的启动与锁错误码，
// 然后沿用原来的格式白名单和DATABASE_FAILURE兜底。
const code = codes.includes('DEV_USER_MISSING') ? 'DEV_USER_MISSING'
  : codes.includes('ACCEPTANCE_CONSTRAINT_MISSING') ? 'ACCEPTANCE_CONSTRAINT_MISSING'
  : codes.includes('55P03') ? '55P03'
  : codes.find(value => /^(?:P[0-9]{4}|[0-9A-Z]{5}|ECONNREFUSED|ECONNRESET|ETIMEDOUT|ENOTFOUND)$/.test(value))
    ?? (unavailable ? 'POOL_TIMEOUT' : 'DATABASE_FAILURE');
```

可用一个最小断言核对 `{ code: 'P2039', meta: { driverAdapterError: { cause: { originalCode: '55P03' } } } }` 得到 `{ code: '55P03', unavailable: true }`；它验证错误提取，不代替真实持锁请求。

唯一冲突P2002不重试。对本次candidate_id约束，它更可能说明有人绕过了状态协议或已有异常事实，换一个学习记录id再试仍然撞同一个candidate_id。当前通用出口保持500并记录安全码，不能把所有P2002自动说成用户重复点击；正常重复采纳已经在状态检查处得到409。P2028事务期限错误、断连与未知错误也不进入循环，先按前章路径判断实际结果。

```mermaid
flowchart TD
    E[采纳事务抛出错误] --> K{已知Prisma错误且P2034}
    K -->|是| N{还剩重试次数}
    N -->|是| W[事务外退避 再开事务重新判断]
    N -->|否| U[503 保留安全日志]
    K -->|否| T{内层55P03}
    T -->|是| U
    T -->|否| F[沿原错误分类 不自动重试]
```

给每个计时器各画一条起跑线。请求在服务器上等待进入事务，尚未取得回调时，不可能已经执行回调第一行设置的锁等待限制；拿到事务以后开始查询，找到候选并尝试更新，才可能遇到某个具体行锁的一秒等待；事务结束后如果需要退避，客户端仍在等响应，刚才那个事务的本地锁超时却不再生效。一次调用可能在其中某段很快结束，也可能前段已经消耗了时间，到后段才失败。把浏览器网络面板的总毫秒数与数据库的一个配置值逐字比对，得不出故障发生在哪一段。

假设两个请求都在大约一秒多后返回临时不可用。第一个请求的包裹错误里有明确锁等待码，同时练习连接持有那一行，放行后同一候选能正常采纳。第二个请求甚至没有进入事务回调，连接池当时无法交出连接。前者应该找占锁者和事务范围；后者先看可用连接、服务实例的目标和池内任务。即使两个响应正文完全相同，也不能从统一的公开错误倒推出同一种数据库原因。用请求编号回到服务日志拿本次安全错误码，再与实验期间的会话状态对照，才有理由缩小范围。

同理，若只取最外层的一串 Prisma 码作自动重试条件，驱动把锁错误包装进去时，程序可能漏记真正能说明等待类型的内层码；反过来把所有外层包装错误都重试，又可能把结果未知的故障重复执行。这里有两个独立的问题：是否向调用者表达暂时不可用，以及服务器是否有充分根据自动再做一次。前者允许合并多种内部失败，后者只接受范围很窄的明确中止。调试时记录两个判断各自用了哪个值，不用向用户公开底层对象，也不用把所有临时失败都塞回循环。

## 28.5 用户与表达边界，为什么不能只锁候选

### 同一个用户不等于同一个竞争对象

现在候选1和候选2互不依赖，各自采纳可以并行。若给整个用户加排他锁，虽然容易把所有操作串起来，也会让一个慢采纳阻塞该用户所有无关候选；给全表或全应用一把锁，影响范围更大。只有业务真的共享一个可变化前提，扩大范围才有理由。

改变一个条件：以后用户进入“处置中”就不能新增学习记录。若采纳只在开头读取一次用户状态，处置流程可能在它检查后关闭账号并清理数据，而采纳随后又插入一条。候选自己的行锁保护不到用户生命周期；普通SELECT看见active也不会阻止另一个事务改变这个前提。

一种简单方案是双方先锁同一个用户行，读完状态后在同一事务里完成各自修改，代价是该用户相关写入更容易串行。另一种方案是协调共享／排他的事务建议锁：普通操作拿共享门闩，处置拿同一键的排他门闩；普通操作彼此可以并发，处置必须等它们结束，再在锁内改变状态。反过来，处置先完成后，新操作取得共享锁，还必须重新读取状态并拒绝写入，不能把“拿到锁”当成active。

05脚本后半段让A、B分别取得 `pg_try_advisory_xact_lock_shared(2502,1)`，都应为true；B先结束自己的共享事务，再开事务尝试同键排他锁，此时false；A结束后B重试才为true。这组对照说明普通操作可并行、处置要等待，但未加入当前HTTP。选择这种协议必须同步所有写入口和处置入口；漏掉一条路径，锁就无法维护承诺。真正处置的数据范围、状态与恢复由后续账号章节建立，本章不虚构一个已存在的账号开关。

从空白设计这项未来规则，可以先把两类业务各自必须说的一句话写出来。采纳说“我已经确认这个用户仍可新增学习关系，现在要把它写入”；处置说“从现在起不能再新增，接下来我按确定的范围处理已有关系”。若两句话各自都在独立事务里说，但一个只看候选、一个只看用户，它们没有共同要取得的资格。甲先读到用户活跃，乙完成处置，甲再插入学习记录，这个次序就仍然可能。把采纳的读取挪近插入只能缩短窗口，不能消除窗口。能改变答案的是两方围绕同一用户的关键步骤互相协调，并在取得资格以后看实际状态。

共享与排他的取舍可以算出四种配对。两个正常采纳都要共享，同一用户的不同候选仍能各做各的；一个处置已持有排他，后来的普通操作暂时不能进；反过来已有正常操作持有共享，处置也不能抢先越过它；两个处置同时操作同一用户，同样只能由一个先进行。换成两个不同用户，对应键也不同，这张配对表不应无缘无故挡住另一人。拿它解释为什么不能在“先读活跃”后马上释放共享资格：那样读完到写入的空档里，排他处置就能进入，刚刚修好的交错又发生了。

要独立迁移这条判断，可以把问题改为两份学习关系分别属于甲、乙，但产品只要求“甲开始处置时不要再添甲的关系”。此时全局排他虽然也能使甲的操作停住，它还会使乙无法正常学习，范围明显过宽。相反只锁甲已有的学习记录，若甲尚无记录，读不到行就没有任何可以与第一次采纳相遇的锁。稳定存在的用户对象或双方预先约定的用户键才与问题同范围。现在的固定开发用户没有上述生命周期状态，所以这些推导只用于评价方案；要验证当前接口，仍该看候选的条件更新和真实存在的学习关系约束。

### 表达被复用或合并时，锁范围又会变化

当前采纳每次创建全新expressionId，两个不同候选没有共同的现有表达需要锁。第31章建立规范化身份后，两个候选可能同时认领同一个逻辑表达；此时应先确定唯一身份如何表达，再决定是否需要协调“查找—复用／创建”。不能先对英文字符串加一把锁，就宣称已经正确识别同义关系。

以后合并表达A、B，会同时影响它们的形式和学习引用。若采纳正准备引用A，而合并已经把A迁到B，仅锁candidate也不够。参与者需要对相同表达身份协调，并在取锁后重读它是否仍可引用；合并锁多个表达时按稳定ID排序，不能按调用参数顺序。若合并是跨用户的共享表达，锁键也不能带上不同的userId，否则两人处理同一表达会拿到不同锁。

可以据此为未来扩展约定一个统一方向：先用户生命周期，再候选，再按稳定ID排序的现有表达。路径只取自己需要的对象，不能先锁表达又回头等用户；批量涉及多个用户时也先统一排序。若后续业务无法遵守这个方向，应先重画依赖和锁序，不靠增加重试次数糊过去。它目前是设计约束：正式代码只落实本章已有的候选条件更新、关系唯一约束与有限事务重试，没有偷偷引入未来表和锁管理框架。

锁范围、锁顺序和唯一约束一起决定结果，但没有任何一项代替权限。当前固定用户的归属条件继续保留；真实身份接入后仍由服务端身份限定范围，不能因为数据库串行执行，就信任请求传来的userId。

“想复用一个表达”和“知道应该复用哪一个表达”之间还有一道不能由锁解决的题。假设文本栏里都是同一个短词，第一笔学习记录指一个动作，第二笔指一个名词。若按字符串计算出同一个锁，两笔确实可以先后执行，后来者仍可能错误地复用前一种含义。相反，如果两种输入在产品语义上应当复用，但双方按不同大小写或不同语言范围计算键，两把锁也不会互相等待。锁协议所用的身份，要先经过业务上可说明、在所有参与者中一致的定义。先把“哪两个例子应当合并、哪两个应当分开”用具体输入写清楚，再谈数据库怎么排队。

若身份已经确定，仍需区分“有一条现成的表达可锁”和“此刻根本没有表达行”。对于现存对象，按它的稳定标识锁住并重新读取，才能确定它仍可接受引用；对于待创建的对象，按条件做一次锁定查询返回空，无法占住将来那一行。确定的唯一键能在两个插入真正冲突时作最后裁决，某些更长的判断还需一个所有协作者事先都能得到的资格。今天的采纳特意为每一笔决定创建新表达，因而这两个选择都还没有变成正式代码。看到两条内容相同的表达时，先按各自来源解释它们，不能因它们“本应复用”就把当前成功行为诊断成竞态。

合并时还会有一个更细的顺序问题。假设一次操作要把旧表达甲迁往乙，另一项正好反方向整理，若按“来源、目标”依次取锁，第一项的顺序是甲乙，第二项的顺序是乙甲，两人都照着同一段业务代码仍然可能形成环。先把两项实际需要的标识组成集合、去重、按稳定键排序，再在取得资格后按原来的来源与目标分别解释业务意义。排序只决定先保护谁，不会把迁入和迁出的含义颠倒。这个分离还适用于两人都操作同一对象的情形：先明确是否允许来源等于目标，再决定是无需动作还是业务拒绝，不应靠重复申请同一把锁来做参数校验。

### 保留能恢复的交付状态

本章没有改公开响应字段，OpenAPI更新版本与采纳说明，补明锁等待和重试边界。全部旧查询继续识别accepted。迁移成功后，第27章正常采纳代码仍与新唯一约束兼容，但切回它会失去本章等待、重试和约束就绪检查；第26章不认识accepted的读取限制也没有消失。恢复程序要按真实数据与行为能力选择，不能只看表是否还在。

交付按前章独立目录方式验证：构建dist，连同package.json、package-lock.json、.npmrc复制到独立运行目录；在那里npm ci --omit=dev，运行环境提供DATABASE_URL后npm start。确认docs默认404、没有Inspector和源码监听，读取已有accepted；停止再启动，同一候选及关联结果仍在。新代码在缺少本章唯一约束时应拒绝就绪，这与“接口打开后才偶然撞到错误”是不同的恢复入口。

离开实验前，A、B和观察连接都结束事务。做支线28A后按06脚本清理专用对象；不做支线则只清理result、decision和chapter25_lab。保留正式候选与采纳数据，保存ID；再次继续先核对连接目标、迁移状态与候选结果，不从Postman第一项重新创建。

最后可以把交接材料压缩成一笔可以重新调查的正常事实。选取已完成的那份候选，保存其来源修订、候选、学习记录与表达的标识；在对应修订的列表核对状态，再用关系查询核对学习记录数为一。接班人在新进程里按原标识再读，并比对原学习关系仍指向同一个表达。若只看相同的英文，重新创建的另一条候选一样可能给出那句文字；若只看成功状态码，一个指向其他库的列表也会返回成功。记录同一组身份，使“换了程序仍读到原结果”成为可以由别人独立核对的说法。

若启动没有就绪，先把上一个问题换成“这套程序能在目标库安全提供服务吗”。旧版在缺约束的库里能列出已采纳候选，恰好说明只做读取不足以验证新版前提。要在启动日志里区分连接不可用、固定用户缺失、单候选约束缺失，再回到相应连接查迁移及真实结构。若新版已经就绪只是一次写入临时不可用，才进入锁等待、重试与业务对账的调查。两个问题可能出现在同一次发布中，却不能靠重发同一个 HTTP 请求一次性得到答案。

我们现在可以解释同一个candidateId为何只能有一份采纳关系，也知道等待、死锁与数据库中止如何处理。但如果采纳已提交，响应在网络中丢失，客户端再次发送时仍只能得到409，而不是原来的结果。下一章会为这次操作建立独立身份，让恢复不再只依赖人工拼接状态与日志。
