# 支线 26A 什么时候拆开状态，什么时候保留事件

主线把pending与discarded放在候选上，却没有加一个expired状态。这个选择不是“状态越少越好”，而是因为处理决定和来源版本是否仍为当前，回答的是不同问题。把两种事实塞进同一列，会让其中一种信息在另一种变化后消失。

换一个场景，看看怎样自行作出同类判断。阅读约25～30分钟，按约2200个汉字和审批、付款、重新打开三组设计变式估算，非读者实测；无独立操作。

## 从一张报销单的状态失真开始

一张报销单起初是draft，提交以后成为submitted，审批通过以后成为approved。就这段流程而言，单一状态很好理解：三个值描述同一个对象在同一审批流程中的位置，每次转移都有明确的发起动作和允许来源。

接着财务开始付款。若把approved改成paid，查询“已审批通过的报销单”时，paid是不是也算？可以把它们都列入查询，但接下来出现付款失败、部分支付、退款，审批事实便需要从越来越长的状态列表里推断。更明显的矛盾是：一次付款失败不等于审批被撤销；若统一写成failed，用户和运维都不知道到底失败在哪里。

这说明新需求引入了第二个有独立生命周期的对象。审批记录表达是否批准这笔申请，付款记录表达一次具体资金执行结果。它们关联，但不是同一条状态轴。审批已经通过、付款尚未完成，是完全合法的组合，不应该为了“只能有一个状态”而造出approved_but_payment_pending这样的枚举。

拆开不是盲目增加两个status字段。先问一次审批能否对应多次付款：若支持分期或失败后重试，付款应有独立ID和自己的行。此时一个payment_status列连付款尝试的行粒度都装不下。模型要从事实数量推导，而不是从界面想显示几个标签推导。

## 拆开以后，哪些组合仍然非法

两个维度独立，并不表示所有组合都能成立。例如产品规定未经批准不得付款，付款创建时仍须校验对应审批。若审批撤销与付款提交可以竞争，还要定义已经付款时能不能撤销、要不要转入退款流程，以及谁协调这个边界。

因此把字段拆开只解决表达能力，没解决写入正确性。需要同时成立的事实可能要在事务中改变，跨外部系统的动作还需要保存执行意图和结果；不能因为ER图上有两张表，就推断竞态和网络失败自然消失。本书的事务、后台任务与外部调用章节会分别建立这些能力。

回到候选：pending/discarded回答用户是否对这份建议作出决定；“属于旧修订”通过candidate.revision_id与当前版关系得出。追加一版输入会改变后者，不应伪造前者。如果未来界面希望显示“旧版，已放弃”，可以组合两个事实展示，而不新增old_discarded状态。

再改变一个实质条件：产品明确要求旧版建议不能再参与任何后续动作。此时“不可操作”仍可由来源版条件推导，不一定要批量修改每条候选。若产品还要求记录“何时、由谁执行了整批作废”，那才出现一个必须保存的事件或批次状态；动态关系不能独自回答这个历史问题。

## 当前状态回答不了所有过去问题

设一张报销单被退回两次，第三次才批准。如果只存当前status与updated_at，我们知道它现在approved，却不知道每次退回的原因和顺序。增加三个时间列也不够，因为次数不固定，审批人也可能不同。

这时可以新增审批事件：每行保存事件ID、报销单ID、动作、操作者、服务端记录时间和必要的原因。当前状态仍留在报销单上供日常读取；事件记录支持追溯。一次状态转移与对应事件要一起提交，否则会出现状态改变而无历史，或事件说批准但实际未批准。下一章讨论的事务就在这里有了明确责任。

事件也不是把HTTP日志复制入库。HTTP请求可能因输入失败而未形成业务事件，可能超时但后来成功；日志保留策略和敏感信息规则也不同。业务事件应描述需要长期解释的决定，运行日志帮助定位请求经过。是否保存被拒绝的尝试，另由审计需求决定，不能让所有异常自动成为正式业务事件。

还有另一种设计：只保存事件，通过重放得到当前状态。它能让事件成为事实来源，但也引入事件版本、顺序、重复处理、投影重建和迁移责任。若只是想知道谁退回过报销单，普通状态表加事件表已经够用，不必因此采用完整事件溯源。第二十五章的快照支线讨论过相同取舍：保留历史的需求不自动要求最重的一套架构。

本章的discarded_at只记录最终放弃时间，足以解释现有接口的一次单向转移。未来开放撤销、再次确认、后台自动处理后，这个字段就无法表达多次动作。届时应新增事件或决定记录，并明确旧数据只能知道最终状态；不能把原有一行时间拆成几条想象出来的历史。

## 终态能不能重新打开

“终态”始终属于某份业务约定。报销单被拒绝后允许修改并重新提交，可以让同一张申请回到draft，也可以保留被拒版本，再创建新一轮申请。两者都可能成立，关键是旧决定到底指向什么内容。

若直接修改被拒单的金额，再把同一对象改回submitted，而审批记录只引用这个可变对象，历史上的“拒绝100元申请”就可能被展示成“拒绝了后来改成1000元的申请”。解决办法需要版本引用或决定快照，而不是单纯在状态图上多画一条返回箭头。

EPP已经在前章建立修订身份，所以候选可以指认一版固定输入；本章又让候选内容通过API保持不变。将来需要撤销放弃，应先明确撤销针对同一份建议还是另一个内容版本，是否保留原决定和新的决定，是否影响已有学习结果。只有这些事实说清楚，才知道该增加哪条转移、哪张表和哪些约束。

把这组判断用于新业务时，可以沿同一条因果线展开：先确定一行代表哪个对象；再看状态是否描述同一生命周期；出现独立进度时检查是否需要新的对象；需要回答过去时设计历史；最后把每个动作所依赖的事实和产生的事实放到实际写入边界。这样才不会把数据库设计简化成一张不断加值的枚举表。

## 附录：本支线必要技术点速查

| 概念 | 解决的问题 | 容易遗漏的条件 |
| --- | --- | --- |
| 状态归属 | 哪个对象的生命周期发生变化 | 父对象的进度不代替所有子对象的决定 |
| 独立维度 | 同时表达审批、付款等不同进度 | 拆开后仍须约束非法组合 |
| 相对关系 | 判断来源是否仍是当前版本 | 动态推导不等于保存了变化历史 |
| 业务事件 | 保留某次决定、原因和操作者 | 与状态一起提交，敏感信息按需要保留 |
| 事件溯源 | 由事件重建当前事实 | 需要顺序、版本和投影责任，不因要历史就采用 |
| 重新打开 | 允许新的处理轮次 | 旧决定必须仍指向当时内容 |

关系约束能力可回查[PostgreSQL 18约束](https://www.postgresql.org/docs/18/ddl-constraints.html)；状态与多个事实一起保存的机制接下一章事务。本文的报销规则是用于推导的示例，不代表EPP新增审批或付款功能。
