## 7.1 第一篇结束后，怎样理解自己对 Node.js 的掌握

第一篇的成果，是能够脱离逐行照抄，建立一个与当前记录服务规模相近的内存服务：安排输入校验、写入和响应的顺序，解释字节怎样成为业务数据；换目录、换端口或重启时，能判断程序的配置、资源和状态发生了什么；请求变慢时，能先区分异步等待与 JavaScript 阻塞；交付时，能把类型检查、模块解析、构建和产物运行串起来。前面的正文和支线负责建立这些理解，下面的实践负责检验它们能否用于改变后的条件。

如果仍然解释不清为何输入非法却已经写进 Map，或为何源码能运行、产物却找不到模块，就需要回到第三章或第六章补足推导。当前承担的基础，应当在当前讲透；不能把这些疑问一律留给后面的框架解决。完整的服务关闭、内存增长排查和大文件传输则需要加入新的机制与约束，下面用已有实现说明后续为什么继续展开。

以停止服务为例。第四章通过有限任务解释了停止接收、等待已有工作与释放资源，已经让我们知道“收到信号”和“可以退出”是不同的时刻。但记录服务仍采用默认信号处理。等服务需要协调正在处理的 HTTP 请求，就要进一步决定停止接受请求的时机、已有请求的等待期限和关闭失败的处理。第十四章会围绕应用生命周期展开；第三篇接入数据库后，再把连接的初始化与释放纳入同一套判断。到独立 Worker 和管理命令出现时，还要分别处理长期工作与一次性工作的结束条件。

文件处理也是如此。第三章针对有明确大小上限的小段 JSON，采用收集字节后统一解码的方式，这让我们看清了消息完整性和字符编码。后面接收文件时，输入规模、处理速度和中断位置都会改变。第 59～60 章会继续展开流、背压、文件处理及失败清理，解释哪些场景可以缓冲，哪些场景需要边读边处理，以及接收方跟不上时怎样控制资源。前面的实现有明确适用范围，后面的内容负责说明条件变化后如何选择。

第五章的执行模型也会继续使用。知道长计算阻塞主线程，是判断延迟的起点；在实际系统中，还需要结合请求耗时、事件循环、内存、连接和任务积压的证据定位瓶颈。第 65 章会把这些判断接到已有服务的性能与资源诊断上，第 70 章再接上进程托管。第六章建立的模块和产物边界，则会在第 64 章的多入口构建、第 78 章的发布更新，以及第 102 章的共享契约中继续接受检验。

进入 Nest 以后，请求仍由运行中的程序处理，阻塞仍会影响响应，资源仍有自己的寿命。框架改变职责组织，不会替应用决定输入边界、执行成本或交付范围。下面就先用现有程序改变运行条件，再实现一个带兼容约束的小需求，核对这些判断是否已经能独立运用。

可以从一张很普通的故障单开始检验这些能力：“我在客户端看到创建成功，同事打开详情却说找不到。”先别猜 Map 的实现有错。创建返回的 Location 是一个以斜杠开头的路径，里面没有主机和端口。两个人把它接在不同的 baseUrl 后面，请求可能都抵达了正常运行的记录服务，却询问了不同的 Map。反过来，即使两人用的是同一个地址，中间若恰好保存过源码，开发监听器可能已经换过服务进程。地址相同不保证此前写入的数据仍然存在。这个现象只靠读创建函数无法解释，需要把客户端目标、监听进程以及状态的寿命放在同一条时间线上。

从创建响应往后推一遍。收到服务器发来的二百零一时，按现有代码，字段检查已经通过，服务已经为这次创建生成标识，记录也已经放进当时进程的 Map。稍后详情读取同一个标识，需要的是当时那份记录还在当前 Map 里。第一个结论并没有包含第二个结论所需的所有条件。要缩小范围，先请两人保留实际请求地址，再核对启动日志里的端口与进程号，然后在相同服务上用那个标识同时查列表和详情。若列表中有这一项而详情查不到，才值得比较复制的标识和最后拼成的路径；若列表已经整体变空，优先查中间是否重启。观察一个症状后能提出两种解释，再设计一次结果会分叉的读取，比说“可能是后端问题”多走了一步。

还有一类问题方向恰好相反：“我改了接口，可同事仍看见旧字段。”前端经验很容易让人先去看页面缓存。这次同事用的是 Postman，读哪段程序由监听地址背后的进程决定。编辑器中的源码、开发监听生成的文件、普通构建输出和同事手里的运行副本可以同时存在，处在四个不同的时刻。新源码通过检查，只能排除一类编译错误；自己本地出现了新字段，也还没有证明同事的副本已经更新。下面几节会刻意保留这些差异，每次只把一个条件换掉，直到能回答“究竟哪一次写入、哪份文件、哪个进程产生了我现在看到的结果”。

用这种方式回看此前各章，交接的话也会变得具体。与其告诉同事“运行没问题”，不如留下能重复的一笔事实：从哪个目录启动哪一个入口，终端报告的监听地址是什么，用什么原文创建，返回的标识在哪次详情里又出现。如果自己已停进程，交给对方的就应是重做这笔创建的方法，而不是要求他用已经失效的旧标识。这里的交付目标很小，但它要求你能分清哪些东西能随文件交出去，哪些只能在接手人的运行现场重新取得。

## 7.2 不先改代码，先说明程序依赖什么

假设同事只拿到你提供的运行目录，要从另一个 cwd 启动服务，使用端口 `3001`，并接收包含中文与表情的原文。你需要说明应交给对方哪些文件、怎样启动、收到不合法输入时应发生什么，以及重启会保留什么。

先独立写下自己的判断，再对照第六章的独立目录操作。不要把整个开发项目连同 `node_modules` 复制过去；那会保留许多本次要排除的偶然条件。也不要提前把数据库或 Docker 加进来，当前问题由已经建立的能力解决。

最小的推导从消费者开始：Node 执行编译后的入口，因此需要产物 JavaScript 与正确的模块分类；配置按模块相对地址读取，因此需要保持 `dist/src/` 与 `dist/config/` 的布局；启动端口由环境提供，因此进程应继承 `PORT=3001`；运行依赖需要按清单与锁文件准备，本章没有第三方运行实现。类型声明与开发执行器不参与普通产物启动。

这说明交付的对象是一组满足关系的文件与环境，不是「某个能双击的 server.js」。如果交付后从另外一个目录失败，要把入口定位、模块定位、配置定位分别拆开看，不能把三个问题都归为相对路径。

在 VS Code 的资源管理器里并排打开第六章的项目和此前准备的运行副本。从副本的 package.json 找到 start，把实际入口定位到 dist/src/server.js；在这个文件里沿着 config.js 的导入打开同级文件，再由配置模块所在地址向上找一级、进入 config 目录找到 service.json。这样走一遍，会发现这里有两次看起来一样的“从这里往下找”：脚本由工具在包目录运行，所以脚本里能写相对入口；入口加载配置模块以后，配置模块以它自己的文件位置为起点定位资源。两种定位碰巧都成功，是目录结构满足了两套条件，并非进程只有一个默认的路径基准。

把当前目录移到副本外，分别推算两个文件名。若在新终端直接输入相对的 dist/src/server.js，Node 会先在当前目录找入口，还没读到导入声明就可能失败。若给出副本入口的绝对路径，第一步已确定，后面的相对导入仍从那个产物文件所在处解析，配置也从配置模块的位置推算。此时在新的当前目录里再摆一份同名配置不会修复缺失的副本资源。实际启动时，用第六章记录的 release_dir 绝对路径；若换了终端，先在 Finder 找到自己交付的那一份，再填写路径。这样做能明确区分“我要从哪儿发起启动”和“我要启动哪一个包”。

再想一遍端口覆盖。默认端口在 JSON 里，覆盖端口是进程环境里的字符串。可以想出两种实现，一种先看见 PORT 就直接使用，另一种先读取并校验默认文件，再考虑覆盖。它们对正常输入给出的监听地址可以完全相同，但在交付漏了配置时，第一种还能用覆盖值启动，第二种连监听都到不了。打开本章配套的 loadConfig，看第一个 await 在读取什么，再看检查 process.env.PORT 在它前面还是后面。顺序清楚以后就知道，即使交接单上明写“启动时总会提供端口”，配置文件仍然是这份产物的必要组成部分。设置运行模式也没有替它复制文件。

想核实这个判断，不需要改开发项目。只对自己那份已停止的练习副本，在 Finder 的 dist/config 里临时把 service.json 改名为 service.saved.json，先确认新名字没有被使用。保持入口绝对路径、当前工作目录和有效端口都相同，按下节的跨目录命令试启动一次。应看到配置读取失败以及 ENOENT，没有本次进程的监听成功日志。原样改回文件名再执行同一条启动命令，这次才能开始发请求。若第一次就成功，先对照终端里的入口路径与你改名的那份副本；若日志变成端口被占用，则说明配置读取已经走通，下一步要处理的是监听资源。把这次改名恢复后再进入正常请求核对。

给同事的说明还得把“构建的人要准备什么”与“运行的人要准备什么”分开。编译时需要 TypeScript 理解类型和生成 JavaScript，启动交付副本时 Node 直接读取已生成的 JavaScript。这个版本的执行路径只导入内置模块与包内文件，所以按锁文件只装运行依赖后，没有第三方业务包可供调用也能正常工作。若在开发目录做演示，身边的开发工具恰好全在，启动成功并不能区分究竟靠了哪一些。隔离目录的价值就在这里：去掉偶然可见的文件，给必须成立的依赖关系留出一次可以失败的检验。

## 7.3 用一条有效输入和一条无效输入确认边界

在第六章准备运行副本的终端确认 release_dir 仍是它的绝对路径；换了终端就先用记录的路径重新赋值。若 7.2 恢复配置后已经用下面的方式正常启动，可以直接使用该进程。否则先正常停止已有的 3001 练习服务，再执行下面的命令。括号内切到副本的上级目录，停止后 shell 仍在原处。记下新启动的监听地址和进程号。

```bash
(
  cd "$(dirname "$release_dir")" &&
  NODE_ENV=production PORT=3001 node --enable-source-maps "$release_dir/dist/src/server.js"
)
```

看见监听成功，再打开 Postman。复用第六章的“EPP 产物核对”Postman 集合，确认 `baseUrl` 为 `http://127.0.0.1:3001`。把创建请求的 raw JSON 替换为下面的正文，点击 Send；列表与详情继续使用已保存的请求。下面的 curl 保留同一输入的终端表示，选择一种客户端完成即可：

```bash
curl -i http://127.0.0.1:3001/captures \
  -H 'Content-Type: application/json' \
  --data '{"originalText":"  I want to explain this clearly. 我想表达清楚。🙂  "}'
```

核对 `201`、生成的 ID、创建时间和 `Location`，再读取列表与该条详情。返回原文应保留两端空格，中文和表情不应被拆坏。第三章已经解释过 UTF-8 字节与块边界，这里不要求网络恰好按某个字符分块；要知道实现为什么先收集字节、再合并解码，而不是把某一次正常显示当成所有分块情况都正确的证明。

先在 Postman 的产物集合发送一次列表 GET，记下当前全部标识。保留成功创建的进程和端口，依次发下面两次拒绝请求，再发一次列表 GET；两次 GET 之间不要保存源码、重启服务或再次点击创建。对应的终端写法如下。

```bash
curl -i http://127.0.0.1:3001/captures \
  -H 'Content-Type: application/json' \
  --data '{"originalText":42}'
curl -i http://127.0.0.1:3001/captures \
  -H 'Content-Type: application/json' \
  --data '{"originalText":"   "}'
curl -sS http://127.0.0.1:3001/captures
```

两次错误输入都应返回 `400`，列表只保留此前那条有效记录。能够解释这一结果，要同时说明三个边界：JSON 语法正确不等于字段正确；类型声明不会改变网络输入；拒绝发生在 Map 写入之前。若列表新增了错误记录，即使错误响应看起来正确，写入顺序也仍有问题。

请求体限制是字节数，原文长度限制则沿用 JavaScript UTF-16 代码单元，两者不能互换。把原文全部换成表情后，代码单元数与视觉字符数可能不同。如果业务以后要求按用户看到的字符计数，需要重新定义契约和实现，不能只是把现有常量从 `2000` 改大。当前已能指出规则的位置和单位，并说明修改会影响什么。

不要用页面里“看起来差不多的那一段话”当作读回证据。拿这笔创建来说，原文前后各有空格，响应在 Postman 的 Pretty 视图里显示为带引号的 JSON 字符串，外围格式化用的缩进不属于原文。先复制响应 id 到这份集合的 captureId，再发详情，逐项比较 id、originalText、createdAt。列表外层还有 items，进数组后才是要找的对象。假如把完全相同的合法正文发了两次，两笔都应各自得到新标识；不能因为文字相同就只核对第一笔。业务此时接受的是独立的两次创建，既未按原文去重，也没有让相同请求只生效一次的约定。

在 Postman 里把两条失败输入各存为创建请求的副本，保留 raw、JSON 和相同的 Content-Type，只换值。数字四十二经过网络时仍然是一段 JSON 文本，解析后才成为一个 JavaScript 数字。三个空格则会解析成字符串，类型检查能通过，接着才因去掉首尾空白后为空而被拒绝。两者到不了写入，但走到的最后一个判断不完全一样。在开发服务用断点比较时，应看判断表达式执行到哪一项，而不是只在错误处理处比较相同的四百状态。实际发往产物的请求不需要调试器，前后两次列表里的标识足以验证这两笔请求有没有留下数据。

字节和长度不一致也可以在发送前先算一步。取一个“学”和一个“🙂”连成原文，在 VS Code 的集成终端执行下面一行。字符串长度是三，因为表情占两个 UTF-16 代码单元；原文单独编码后是七个 UTF-8 字节；整份紧凑 JSON 加上花括号、键名、引号和冒号，共二十六字节。这三个数里，字段长度上限用第一个，读取正文的上限用最后一个。第二个数可以说明编码成本，但读流的一层不会专门剥掉键名再累计字节。

```bash
node -e 'const t="学🙂"; const body=JSON.stringify({originalText:t}); console.log(t.length, Buffer.byteLength(t), Buffer.byteLength(body))'
```

换个条件检验自己写在表单上的提示。若界面显示“还可输入一个字符”，最后一个表情是否一定可以提交？把原文设为一千个相同的上述表情，在本章规则下恰好用完两千个代码单元；再追加普通字母 a 就越界。两份精简的 JSON 都远小于十六 KiB，故后一笔应在字段长度检查处被拒绝，不应得到正文过大的状态。要精确构造，可以沿用下文生成标签边界 JSON 的办法，以 `"🙂".repeat(1000)` 作 originalText，先发成功样本、保存它的标识，再追加 a 发拒绝样本，回读列表核对只多了那一次成功创建。这个对照也解释了为什么不能用输入框里肉眼数出的图形数向使用者承诺服务器一定接受。

在错误请求后读列表，要刻意避免两个会掩盖失误的动作。一个是切到另一个集合，那个列表虽然返回二百，却属于另一个进程；另一个是先修源码再回看，监听器可能已经重新创建了 Map。先在当前服务里取得错误发生后的列表，再决定是否进入调试。若需要修复，重启以后重新创建一条带辨识度的基线记录，再重做同一对照。这样“错误请求没有改变旧记录”来自同一进程内的前后比较，不能被中途重启后的一份空列表冒充。

## 7.4 把进程寿命、配置寿命与产物寿命分开

先在 3001 的运行实例上保留一条刚读回的记录。这次要把两个问题分开验证：同时运行同一份产物，两个进程会不会互相看见记录？停止其中一个、再在原端口启动，它能不能读回上次的标识？下面按此顺序交叉读取，两次都保留另一个实例作对照。

另一个容易混淆的现象是配置修改。第六章构建把默认配置复制到 `dist/config/`，因此修改开发目录的默认文件不会自动改变已经交付的副本；即使修改运行目录的配置，当前进程也不会自动重新读取，因为第四章只在启动时加载一次。重新构建、更新文件、重启进程是三个不同的动作，应当知道当前需要哪一个。

将一次启动的 `PORT` 改为 `3001oops`，应在监听前失败并返回非零状态。若另一个进程已经占用端口，应在监听阶段报冲突。这两类错误都使服务不能提供接口，但发生的位置不同：前者是配置不满足程序条件，后者是操作系统资源申请失败。定位时应从诊断信息沿对应阶段检查，而不是先修改请求处理代码。

第六章还让构建先清理旧产物再编译。遇到类型错误时，不能把上一版程序仍能启动当成新代码已经通过。把失败构建的输出交给同事也不成立：应当在构建完整成功后再建立运行目录。这是交付事实与开发状态之间的边界，后面的发布篇会在此基础上加入版本与回退。

把“两个实例”变成一次能反驳自己的观察。让第一份服务监听 3001，在另一终端沿用同一个绝对入口，把 PORT 只改成空闲的 3003。记下两份监听日志的进程号。给 3001 的集合创建原文“左边的校样”，把 Location 的路径粘到两份 GET 请求，分别发往两个端口。左边应读回二百和原标识，右边应返回查无记录。然后在右边创建“右边的校样”，反向核对。两次写入读取的是同一份磁盘程序，得到的两个 Map 却各自增加一项。若第二个终端提示端口冲突，先选一个空闲端口，并同步改请求地址；端口是否已经有人监听和 Map 里有没有某条记录是两个问题。

接着只停左边，右边保持运行。先在右边读回右侧标识，确认这一次停止没有让右侧的记录消失；保持右边不动，再以原端口启动左边，用同一个左侧标识查详情。同一个端口现在能接通，但回的是查无记录，新列表也应为空；此时右侧标识在右边仍能读到。停止期间的连接失败与重启后的四百零四对界面都可能表现为“看不到这条素材”，诊断含义却很不同：后者说明有服务接了合法的详情请求并完成了一次查找。此时再创建同样文字，只会得到新记录，不能靠原文相同来恢复原标识。做完这轮，正常停止这两个产物进程，再进行端口失败的对照时只保留自己明确需要的监听者。

配置寿命可以用同样的办法分解。假定交接时约定“下次运行用另一端口”，先判断交接的是一份默认配置，还是启动命令里的覆盖参数。只改默认 JSON，而沿用显式 PORT 的同一条有效启动命令，新进程仍会监听覆盖值。相反，只改当前终端下一条命令打算传的 PORT，却继续向已经运行的旧进程发请求，旧监听也不会移动。若希望核实默认文件本身，在已停止的运行副本中把默认端口改成一个确知空闲的值，记好原值；从未设置 PORT 的进程直接启动同一入口，观察新监听地址。在 macOS 的终端可以只对这一笔启动用 `env -u PORT node "$release_dir/dist/src/server.js"`，免得先前导出的变量悄悄参与选择。停止后将副本里的默认值恢复，再按原交接方式启动。这里检验的是该副本读哪份默认文件，源项目无需修改。

两种启动失败也要有各自的对照物。测试非法端口时，即使机器上没有其他进程，字符串也会在配置阶段被拒绝。测试端口冲突则先在一个终端保持健康服务，再从另一个终端用相同的合法端口启动第二份。失败的那份没有取得监听权，随后发到这个端口的 GET 仍可能成功，因为处理它的是先到的进程。在 macOS 的 shell 里，失败的启动命令结束后立即执行 `echo $?` 可读到非零退出值；若先执行了别的命令，取到的就是那条命令的结果。用两份日志区分哪一个报告监听成功、哪一个报告 address already in use；不要因为 Postman 还通，就把第二个进程也登记成“启动成功”。结束时只停自己刚才启动的服务，不必向其他未知进程发信号。

最后把一个构建失败放在这条时间线上：先前成功交出的副本在目录甲，开发者正从目录乙重新构建。乙的 clean 会清掉乙的旧输出，如果随后编译失败，就不能从乙取得一套经过本次构建的完整产物。甲若仍能正常提供服务，说明上次交付仍可用，与这次源码有没有通过类型检查是两件独立的事。反之，重启甲也不会让乙的新源码突然出现在甲的文件里。交接时保存成功构建后的副本，失败时回到源码修正并重新构建，比让接手人反复重启一份内容未知的目录更容易定位。

## 7.5 需求变成批量处理时，先判断成本再选执行方式

现在暂时离开文件布局。假设有一项新需求：对一批原文做分析，单次分析是约半秒的纯 JavaScript 计算，希望期间查看列表仍能获得响应。不急着给记录服务添加一个演示路由，先用第五章的 `/block`、`/slice` 与 Worker 例子说明可选方案为什么不同。

把函数写成 `async` 不能把半秒计算搬离主线程。在循环里 `await Promise.resolve()` 也不能保证 I/O 有机会推进，因为连续的微任务仍可能占住处理时机。分段配合 `setImmediate()` 让事件循环在片段之间推进，可以改善交错响应，但没有减少总计算量，也没有把计算并行到另一个核。

如果确实需要把计算移出主线程，Worker 可以提供另一个 JavaScript 执行环境，同时带来输入复制、结果消息、失败与退出的责任。每个请求随手创建一个 Worker 也不能自动解决容量问题；工作到达过快仍然会争用 CPU 与内存。当前有限示例能支持执行位置的判断，持续服务的线程复用与容量安排在后面的性能章节继续展开。

再把需求改为等待外部 I/O，判断又变了：异步等待本身不需要另一个 JavaScript Worker 来「帮忙等」。应关注等待是否有期限、真正的操作是否支持取消、失败由谁接住，以及已经接受的工作如何收尾。第五章的 `Promise.race()` 与合作取消实验已经给出了这种差别。

这里没有增加一个大作业。目标是面对改变后的成本来源，能够解释为什么选择不同，不把「后台」「异步」「多线程」当成可以互换的词。如果解释卡住，返回第五章对应的执行实验；若只会列出工具名称而无法预测探针与结果顺序，就还需要对照实际输出重建判断。

把“期间列表仍能响应”变成可观察的问题，要问的是另一笔短工作能不能在长工作结束以前得到执行机会。只量分析请求本身，会发现阻塞版本和分段版本都大约需要六百毫秒，很容易得出“分段没有作用”。可是用户关心的是这段时间旁边有没有机会处理别人的事。第五章配套在长操作开始时安排了一个一百毫秒后到期的定时器，每笔实验都有自己的开始时刻。它的回调与处理 GET 的 JavaScript 同样需要主线程；只看这一处的先后，就能先判断长操作是否让出过执行机会，再决定是否需要用第二笔请求进一步观察。

要在图形客户端重看，在项目根目录单独运行 `node examples/event-loop-server.js`，等终端显示三〇〇二端口，在 Postman 打开第五章的事件循环集合，逐条发 wait、block、slice，每笔都等它的定时器消息出现，再开始下一笔。wait 的逻辑先安排等待，主线程可以处理别的回调，探针有机会在六百毫秒的等待中间打印；block 的循环一直占着主线程，哪怕探针已经到期，它也得等循环结束才能打印。slice 把计算拆成约十毫秒一段，每段结束让事件循环再推进，所以探针能插到两段之间。定时器到期表示有资格运行，具体数字随机器与负载变化；拿这些输出比较“在工作中途还是工作末尾”，不要求恰好第一百毫秒打印。完成后正常停止这个演示服务，记录接口仍沿自己的端口启动。

分段的代价可以用六十个小片段来推。一个片段若做十毫秒的忙计算，六十段累计仍有约六百毫秒的主线程工作；中间允许其他回调先走，会让这笔分析完成的墙钟时间再长一点。若把每段扩大，其他请求可插入的间隙变少；若缩得极短，频繁安排后续回调本身也有成本。因此实际需要的是一个能兼顾短请求的片段大小，而非只追求长请求尽早结束。用同一条原文预测两个结果：分析最终是否完成，分析中途探针能否运行。两问可以有不同答案。在单独脚本里得到了一百毫秒附近的探针，也还不能由此给实际服务写下响应时间保证。

换到第五章的 `node examples/worker-boundary.js worker`，父线程先准备输入、启动工作线程，之后等待消息。工作线程改变自己接到的 note 并带着结果发回，父线程打印的原始 note 仍是原值。这告诉我们，计算虽然被移走，父线程手里的记录不会随着工作线程的局部赋值而改变。如果将来真要把分析结果挂回记录，父线程至少得知道结果属于哪个记录，并决定何时接收、写入和回应。本章没有把 Map 交给 Worker，也没有现成的写回协议。一次独立脚本能验证执行位置与消息边界，不能说明多请求服务已经具备后台任务能力。

若这批工作改成等待外部响应，可以先用六项、每次接受两项来手算，而不把整批都启动。在 `examples/bounded-batch.js` 中，第一批一号与二号都结束后才接受三号四号；第三项失败时，第四项已经开始，所以本批要等第四项也结束才汇总结果，第五与第六项没有启动。运行 `node examples/bounded-batch.js` 看最后的 active 和 peak。结束时 active 为零，表示已经接受的工作都走完了收尾；peak 为二，说明同一时刻最多有两项在途；进程仍会因本批失败退出非零。三个事实可以同时成立。若把它改写成对六项直接 map 再等待，外层再怎样按两项展示结果，也挡不住六项已经开始。这是“限制接受工作的位置”带来的差别，和 CPU 是否能并行是另一笔账。

回到记录服务决定是否实现这项需求时，先把最小证据带回来。若任务确实一直使同进程的探针推迟，继续比较切段与移动计算；若任务本身只是在等数据，首先盘点有多少项已经开始、失败后还有谁继续工作。等结果的 Promise 提前结束，并不代表计算、计时器或外部调用都已释放资源。这样取舍，就不会为了看起来“异步”而多建一个线程，也不会把主线程一直在算的循环误写成一个改函数签名就能解决的问题。

## 7.6 如何确认这一篇已经形成可迁移的能力

### 先独立实现一个改变规则的小需求

换目录说明运行关系可以成立，但还不能证明自己会把新需求接进程序。现在给记录增加一个**可选来源标签**：记下这段原文来自哪里，例如 Podcast。这个实验只改变一项输入规则与记录形状，不增加路由、依赖、数据库或身份功能。

需求先于实现。旧客户端只发送 originalText 时，创建、列表和详情仍返回原来的三个字段；不能为了新功能要求旧客户端补字段。新客户端可以发送 sourceLabel，它必须是字符串；去掉两端空白后，长度须为 1～80 个 UTF-16 代码单元，保存和返回去掉两端空白后的值。字段缺失表示没有标签，显式的 null、数字、空字符串或纯空白都不是“没有填写”，应返回 400。长度也按去掉两端空白后的结果判断。原文沿用现有规则，仍保留两端空格；16 KiB 请求上限及其他接口行为保持不变。此前未声明的其他字段继续按原服务忽略。

完成的依据不能只是一条带标签请求返回 201：不带标签的旧请求必须继续成功，失败输入不能增加 Map 里的记录，列表与详情必须和创建结果一致。最终运行的还应是独立目录里的新产物，而不只是开发入口。重启仍丢失全部记录，不需要为这个临时内存模型设计历史数据迁移。

先只阅读需求，自己说明准备修改哪些边界；按下一节建立隔离目录后，再实现第一版。特别要自行决定：怎样区分字段不存在与字段值非法，在哪一步转换标签，何时才能写入，以及怎样发现“错误响应正确但记录已经写入”。先选择自己的输入与观察位置，遇到不符预期的结果，用 6B 的请求和断点方法追踪；不要先把下面的参考代码贴进去，再用同一份代码解释自己为什么这么做。实现后再读分析参考，对照遗漏的前提。

先把“可选”落实到旧表单的两个具体动作。旧表单从来没有来源输入框，提交出去的对象只有原文。新表单可以有一个空着的来源输入框，当用户没有选择提供标签时，应省略这个键。如果表单序列化代码固定发一个空字符串，服务器收到的就是“显式提供了不合格的值”。契约约定这种输入应当被拒绝，所以不要一边写着空串无效，一边让界面在不填写时始终发送空串。若产品另有要求，要让显式空串也等同于缺失，应先改需求与核对样本，而不是在实现末尾给所有假值加默认值。

再换一个方向问兼容性：旧客户端访问新服务时，旧的三字段结果应该保持；新客户端访问旧服务时，会发生什么？第六章服务只读取 originalText，其他键允许出现并被忽略，因此第二种组合也可能得到二百零一，却根本没有存储来源。甚至把标签填成数字，旧服务也无须按新协议拒绝它。判断某次发布是否交付了新功能，必须找到能区分新旧版本的证据。使用带外围空格的合法标签，检查创建、列表、详情都显式给出裁过空白的值；再用一条合法原文配非法标签，确认没有产生新身份。只看 URL 没变、状态成功、原文读得回来，对这个需求都没有区分力。

在动代码之前，还可以把数据经过的三个对象画在纸上。第一个是外部传来的对象，标签可能缺失，也可能是任意 JSON 值。第二个是通过检查后准备写入的记录，若标签存在就应已经是满足长度条件的字符串。第三个是调用方收到的公开结果，需要与以后同标识读到的记录一致。当前服务让后两个对象共享同一份字段来源，工作量很小。如果自己的实现只往第三个对象附上一个显示标签，创建会看似成功，下一笔详情就会揭露第二个对象没有它。这个推导告诉你为何要读回，也指明了第一次实现时改动应该落在哪一行附近。

### 给实验一个不会影响主线的位置

无论此前各章是自己从空目录写成，还是从配套代码克隆，都先保留当前目录，另取一份本章资料。自己跟写的项目不需要已有 Git 提交或章节分支；普通克隆、`--single-branch` 克隆也不保证前章有本地分支。下面把这两个前提直接建立出来。

在当前项目根目录记录返回位置，再克隆到一个尚不存在的资料目录；命令失败就停在这里处理原因，不继续 cd。若目录已存在，先按下文恢复已有练习，或者为新一轮选择另一组目录名。

```bash
main_dir=$(pwd)
git clone --single-branch --branch part-01/chapter-07 \
  https://github.com/SamChowRock/epp-public.git ../epp-chapter-06-materials
```

克隆成功后进入资料目录，明确取得第六章快照：

```bash
cd ../epp-chapter-06-materials
git fetch origin refs/heads/part-01/chapter-06:refs/remotes/origin/part-01/chapter-06
git worktree add -b practice/chapter-06-source ../epp-chapter-06-source origin/part-01/chapter-06
```

`origin/part-01/chapter-06` 是下载到本机的远程分支记录，不要求存在同名本地分支。fetch 中冒号左边指定远端章节，右边指定本机保存位置，因此只克隆一个分支也能补取前章。fetch 成功后才执行 worktree add；认证、网络或分支不存在时不能跳过。`git worktree` 为同一个仓库另建工作目录，`-b` 在明确的第六章快照上创建个人实验分支，原项目不会被切换或覆盖。

只有最后一条命令成功后，才进入新目录：

```bash
cd ../epp-chapter-06-source
nvm use
npm ci
```

`-b` 创建个人实验分支，末尾参数指定起点；这些名字不是要求新增一条全书主线。若分支或目录已存在，先判断它是否就是上次未完成的实验：在资料目录执行 `git worktree list`，按其中的路径与分支找到已有实验目录，进入后用 `git status --short` 和 `git diff -- src/server.ts` 回看进度；执行 `nvm use` 后继续修改，不重新创建目录或覆盖已有成果。只有确实要另做一轮实验时，才选择另一组未使用的名字并同步修改 cd 路径。不要用强制参数、删除目录或重置分支来腾位置。原工作目录与实验目录各有自己的依赖和 dist，因此需要在实验目录安装与构建；同时运行时也要选择不同端口。

进入实现时，先停止原目录的 dev 和上一轮 3001 产物服务，释放 Inspector 9229 与业务端口。用 VS Code 打开实验目录，在这里执行 `PORT=3001 npm run dev`，按 6B 连接调试器。这样可以沿保存、自动编译与重启、重新发送请求的流程完成自己的实现，再阅读下面的分析参考。

### 分析参考：缺失、规范化与写入是三个决定

下面给出一种实现，用来对照自己的选择。它不是唯一合理的代码组织方式，但必须满足相同的完成条件。

首先，sourceLabel 是可选的，不能把 Capture 改成“每条记录都必须有一个字符串”。在实验目录的 `src/server.ts` 中，将 Capture 类型改为：

```typescript
type Capture = {
  id: string;
  originalText: string;
  createdAt: string;
  sourceLabel?: string;
};
```

可选属性表达内部允许缺失，不能验证外部输入。`if (body.sourceLabel)` 也不够：空字符串、null、数字 0 都会被当成没填，违反已声明的拒绝规则。第六章已经先把 body 收窄成非 null、非数组的对象，因此这里可以用 `in` 判断属性是否存在，再单独检查其值。当前 body 来自 JSON.parse 的普通 JSON 对象，不是在接受任意带原型行为的对象。

在 POST 分支中，保留原有 originalText 校验，将以下代码放在其长度校验之后、构造 capture 之前：

```typescript
let sourceLabel: string | undefined;
if ('sourceLabel' in body) {
  if (typeof body.sourceLabel !== 'string') {
    throw new HttpError(400, 'sourceLabel must be a string when provided');
  }
  const normalized = body.sourceLabel.trim();
  if (normalized.length === 0 || normalized.length > 80) {
    throw new HttpError(400, 'sourceLabel must contain 1 to 80 code units after trimming');
  }
  sourceLabel = normalized;
}
```

这里的 trim 与原文校验中的 trim 用途不同。原文只借它判断“是否全空白”，写入仍用原值；标签的需求明确要求规范化，因此判断与保存都使用 normalized。若判断规范化后的值却保存原值，就会出现“检查通过的内容与实际保存的内容不是同一个”的偏差。先看需求究竟要求判定还是转换，再决定是否复用转换结果；不是所有字符串都应该一律 trim。

随后把构造与写入片段改为下面这样；原有 Location 和状态码继续保留：

```typescript
const capture: Capture = {
  id: randomUUID(),
  originalText: body.originalText,
  createdAt: new Date().toISOString(),
  ...(sourceLabel === undefined ? {} : { sourceLabel }),
};
captures.set(capture.id, capture);
sendJson(response, 201, capture, {
  Location: `/captures/${capture.id}`,
});
```

条件展开让缺失标签的记录确实没有该属性，而不是给它填一个虚构的默认值。当前列表和详情直接返回 Map 中保存的记录，所以它们自然取得同一个规范化结果，不需要各自再写一遍 trim。若自己改成了响应对象投影，就要在三个入口分别核对字段，不能因为创建响应正确便假定读取也正确。

为什么把全部检查放在 captures.set 之前？若先保存再检查标签，即使最终返回 400，非法记录仍已进入 Map，下一次 GET 会读到它。catch 负责错误响应，不负责回滚。当前检查和写入之间没有 await，不需要为这一段引入事务或锁；以后若判断依赖异步读取的共享状态，则需要重新分析交错，这里不能替未来作保证。

用一条带空格的原文和一条带空格的标签来单步读自己的实现。在 VS Code 的变量窗口里，先看刚解析出来的 body：这时两段值都应该带着用户原先的空格。进入标签检查后再看 normalized，只有标签的外围空白消失。构造 capture 时，originalText 仍取自 body，sourceLabel 取已经通过检查的那个局部值。这里故意选了两种不同的保留规则；若先给 body 的所有字符串统一执行一次清理，后面就算把代码写得很像参考实现，也找不回原文原本有几个空格。把一次不可逆的转换放在约定它的那个字段上，就不必再给其他字段设计例外。

长度上限也要想清楚是在量哪一个值。设标签是四十个相同的笑脸表情，头尾各加一个普通空格。原始字符串有八十二个代码单元，通过 trim 得到八十个，应当接受。若在这四十个表情中间再加一个普通英文字母，裁完后仍有八十一个，应当拒绝。若按 UTF-8 字节数校验，第一笔会过早失败；若按展开字符串后有几个 Unicode 码点来数，第二笔又会被错误接受。两个相邻输入就能将这些实现区别开。可以在已有的 Node 终端生成它们：`" " + "🙂".repeat(40) + " "` 和 `" " + "🙂".repeat(40) + "a "`，把结果作为 sourceLabel 用 JSON.stringify 输出完整对象。检查的单位与原文相同，检查前要不要裁剪却不同。

再看拒绝以后该检查哪一个旧值。一份错误实现可能在判断标签之前先生成并保存记录，错误响应里又没有返回标识。客户端无法猜出随机标识去请求那条详情，却仍然有办法判断写入是否发生：用本轮独有的原文提交错误样本，在同一进程取得完整列表，比较请求前后的标识集合，并在新增项中检查这段原文。若条数没有变化，还可抽查先前合法记录的标签和时间，确认没有误改已有对象。相反，若只是校验前生成了一个随机标识，却没有把对象写入 Map，那不会使列表多一条；真正改变业务状态的是 set。断点应把“准备了对象”和“已可被另一笔 GET 读到”分开。

### 用外部结果和内部事实核对自己的实现

准备核对产物时，先停止实验 dev，依次完成 `npm run typecheck`、`npm run build`，两步成功后用 `PORT=3001 npm start` 启动，确保此前占用 3001 的服务已停止。

在 Postman 复制“EPP 产物核对”集合并命名为“第七章来源标签实验”，保留 3001 地址。把旧、新、非法标签保存为不同请求，避免为改 Body 而覆盖原有案例。先读取列表并记录条数，再发送一条旧请求和一条新请求；对应终端表示为：

```bash
curl -sS http://127.0.0.1:3001/captures
curl -i http://127.0.0.1:3001/captures \
  -H 'Content-Type: application/json' \
  --data '{"originalText":"  old client  "}'
curl -i http://127.0.0.1:3001/captures \
  -H 'Content-Type: application/json' \
  --data '{"originalText":"  new client  ","sourceLabel":"  Podcast  "}'
```

两次都应返回 201，原文两端空格均保留；第一条没有 sourceLabel，第二条的标签恰好为 Podcast。分别复制返回 ID，读取 `/captures/<id>`，再读取列表；核对实际字段，而不只看状态码。重复运行会创建新记录，因此对照开始时的条数与本次 ID，不假定 Map 永远从零开始。

再选择纯空白、null 和数字等非法标签发送请求，例如：

```bash
curl -i http://127.0.0.1:3001/captures \
  -H 'Content-Type: application/json' \
  --data '{"originalText":"must not be stored","sourceLabel":null}'
curl -sS http://127.0.0.1:3001/captures
```

把 null 分别替换为 `"   "`、`0` 后再观察；这些请求都应返回 400，列表条数不增加。长度边界也要自己构造：去掉两端空白后恰好 80 个代码单元可接受，81 个拒绝，外围空白不计入这项上限。不要仅测试特别短和特别长的输入，否则无法区分“先检查长度”与“先去空白再检查长度”。可以用 `node -e 'console.log(JSON.stringify({originalText:"length boundary",sourceLabel:" "+"a".repeat(80)+" "}))'` 生成明确的 JSON，再按第三章的文件请求方式发送；将 80 改为 81 得到相邻失败输入。

若错误请求返回 400 但条数增加，需要回到开发进程定位：先停止产物服务，在实验目录执行 `PORT=3001 npm run dev` 并重新 attach，再在 sourceLabel 校验和 captures.set 两处分别暂停，找出先发生的动作。`npm start` 没有打开 Inspector，不能直接沿用开发调试连接。若开发入口正常而产物仍没有标签，先核对构建结果与目标进程；若创建有标签而详情没有，追踪保存的对象与响应投影。这里每种故障对应的观察边界不同，重新安装依赖不能代替这些证据。

完成核对和必要修复后，停止仍在运行的实验开发或产物服务。把 7.3 已核实的旧副本绝对路径单独记为甲，保留它；在实验源码目录重新构建，以第六章的方法把这次的 dist、清单、锁文件和项目安装配置复制到**另一个新目录**，在新目录按锁文件只装运行依赖。把这个新目录的绝对路径记为乙。它应该有 dist/src/server.js 与 dist/config/service.json，包根下没有开发用的 src 目录。若在同一 shell 重用 release_dir 来创建乙，务必先另存甲的路径，否则两条命令可能都在启动乙。

现在用 7.3 的跨目录命令逐个启动，入口指向各自的绝对路径。先只启动甲，用同一个 Postman 请求提交原文“版本交接比较”、标签“  Podcast  ”。保存实际创建响应，并在甲仍运行时用甲的标识查一次详情，预期两份响应都只有旧字段。停甲、在同一端口启动乙，先读一次空列表，再原样发送已保存的请求。这次创建和详情都应出现规范化后的标签。不要拿甲的标识去给乙做详情验证，两份进程本来就各有自己的 Map。这一轮的比较依据是输入相同、运行产物明确、各自写入的记录在各自实例里能读回。

若两边都看见标签，先核对所谓甲是不是已经被新一轮复制覆盖；若两边都没有，看看乙是在实验目录构建、从相同的 dist 复制，还是在没有改过的资料目录构建。若乙的创建有而详情没有，则入口很可能确实已是新代码，接下来应该查构造和写入的是不是同一个对象，或者读接口是否另行挑选了字段。每一个判断都来自响应间的具体差别，不能只凭新进程的启动时刻说它必定加载了新功能。目录与进程的责任分清后，这个实验就可以收好；没有必要为了让旧版“也能认出标签”而去改第八章的起点。

在乙继续发送省略标签的旧请求和显式传 null 的错误请求。先读回刚刚的带标签记录，再看列表是否只增加了旧请求创建的那一条，两条合法详情仍各有原值。最后正常停止乙，从同一目录重启一次，列表应为空。停止这次重启的服务，才有空闲端口供下文的完整参考使用。

将来若让别人接手这次改动，留下两笔相邻的请求会比留下某个随机标识更有用。一笔省略标签，说明客户端不必一次全部升级；另一笔显式提交带空白标签，要求返回和读回都等于裁剪后的值。接手人可以在自己的空实例重放这两笔，现场取得属于自己的标识，再用非法标签核对不写入。把运行目录、有效端口和停止后数据会失去的条件写在请求旁边，这样即使你的终端已经关闭，对方仍能独立得到与需求对应的证据。
