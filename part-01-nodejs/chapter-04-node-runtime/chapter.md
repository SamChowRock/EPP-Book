# 第 4 章 Node.js 程序究竟运行在哪里

第三章的记录服务已经能接收原文、生成 ID，并通过列表和详情读回数据。调试时我们还见到了几个不属于业务规则的问题：第二次启动占用了同一个端口；停止服务后，Map 里的记录消失了；同一份 JavaScript 在浏览器控制台和 Node 中承担着不同工作。

先看第三章留下的两个现象：同一个程序再次启动会争用端口，却不会读到第一个进程的 Map；源码中的最后一行已经执行完，服务仍然可以接收新请求。前者涉及状态与资源归谁持有，后者涉及运行时还在等待什么。如果只记住启动和停止命令，这两种现象很容易被笼统归为“Node 的行为”，遇到环境变化时就没有进一步判断的依据。

我们从启动者、进程和操作系统之间的关系开始。启动者提供参数、工作目录、环境变量与输入输出连接；进程执行代码并持有本次运行的状态；访问文件或监听端口时，还要向操作系统申请资源。沿着这几层关系，才有办法解释同一份代码为什么在另一终端、另一目录或另一账号下表现不同。

这一章继续使用第三章的项目。先观察进程的运行上下文，再把端口从源码中移到启动配置，最后复现并修正“换目录后找不到文件”。三个 HTTP 接口与记录结构保持原来的约定，记录仍在内存里；文件读写用于理解运行环境，不在这里临时造一个 JSON 数据库。

**代码起点**：第三章完成状态，代码分支 `part-01/chapter-03`。本章完成状态使用 `part-01/chapter-04`。运行版本沿用 `24.22.1`，命令沿用 macOS、Linux 的 Bash／Zsh，Windows 读者在 WSL 中执行。

从第三章跟写时，在原来的练习目录依次添加本章文件；直接使用第四章完成快照时，打开同名文件对照即可。后面会分别指出何时只观察输入、何时把输入接入服务。从项目根目录执行 `nvm use`，新开的终端也核对一次 `node --version`。版本文件写出了项目选用的版本，具体用哪个 node 启动仍取决于当前终端能找到哪个可执行程序。

## 4.1 进程、工作目录、环境变量与标准输入输出

### 先把文件与正在运行的程序分开

在项目根目录执行 `node src/server.js` 时，shell 先解释命令，按照可执行程序查找规则找到 `node`，再安排一次程序执行。通常可以把结果理解为：一个新的 Node 进程拿到启动上下文，加载入口文件与依赖，然后执行代码。这里暂不展开操作系统创建进程的底层步骤，先看哪些信息已经传了进去、哪些状态需要重新建立。

`src/server.js` 的位置只回答“读哪份代码”。工作目录回答相对文件路径从哪里算起；环境变量与参数给这次运行提供输入；进程的身份决定可以请求哪些资源。它们都不存放在那份 JavaScript 源码中，因此复制源码并不能自动复制整个运行条件。

进程开始执行后，`new Map()` 创建的是本次运行中的对象。修改磁盘上的源码，不会让已经执行过的语句重新执行；结束进程也不会删除源码文件。开发时自动重启工具让这两件事看起来接近同步，但它仍是检测文件变化、终止旧进程、再启动新进程的一组动作。

第三章的 `new Map()` 在每次启动时重新执行。因此，同一份源码可以启动两份服务，但不会因此共享同一张 Map。两份服务争用端口，是在争用操作系统管理的监听资源；两份服务中的记录互不相通，是因为它们各自持有自己的状态。文件相同、程序行为相同和运行状态相同，是三个不同的判断。

先做一个不需要监听端口的观察。在项目根目录新建 `examples/runtime-context.js`，完整内容如下：

```javascript
console.log(JSON.stringify({
  pid: process.pid,
  cwd: process.cwd(),
  node: process.version,
  execPath: process.execPath,
  execArgv: process.execArgv,
  args: process.argv.slice(2),
  port: process.env.PORT ?? '(unset)',
  stdinIsTTY: process.stdin.isTTY === true,
  stdoutIsTTY: process.stdout.isTTY === true,
}, null, 2));
```

运行两次：

```bash
node examples/runtime-context.js
node examples/runtime-context.js
```

两次运行通常会得到不同的 PID。PID 用来识别当前进程，但退出后可能被系统重复使用，不能拿它当业务 ID。`execPath` 表示实际运行的 Node 可执行文件，`node` 表示它的版本；这两个值能帮助判断新终端是否真的使用了 nvm 选定的版本。

`cwd` 是 **current working directory，当前工作目录**。它初始来自启动者，在本例中就是 shell 执行命令时所在的目录。它不等于入口文件所在的目录，更不等于当前执行模块所在的目录。服务从项目根目录启动时，入口在 `src/` 下，工作目录仍然是项目根目录。4.4 会利用这个差异制造一次可解释的失败。

这里只输出与实验有关的字段。不要用 `console.log(process.env)` 收集诊断信息：开发环境里可能已经有数据库密码、平台令牌等内容。输出工作目录与可执行文件路径也会暴露本机目录结构，分享结果时应替换个人路径。

怎样选值得记录的字段？设想同事从编辑器的集成终端运行成功，换到系统终端却失败。先保留两个窗口，各自执行一次观察程序。比较 `execPath` 与版本，可以回答是否用了同一个解释器；比较 `cwd`，可以回答两次从哪里出发；比较 `args`，可以检查点启动按钮时工具有没有追加参数。只比较 PID 没有帮助，两次都成功时 PID 也会不同。也不要只凭编辑器左栏打开了哪个项目来推断 cwd，一个工作区可以开几个终端，每个终端都可以独自换目录。

还有一种失败甚至不会打印这份报告。假如终端本来就在 `examples/`，输入 `node examples/runtime-context.js` 相当于要求在当前目录下面再找一层 examples。先看终端执行 `pwd` 的结果，再看错误消息里找的入口，把这两个位置拼在一起，就知道为什么观察代码没有机会执行。改成 `node runtime-context.js` 可以到达入口，此时报告中的工作目录仍应以 examples 结尾。随后回到项目根目录。这个小对照给排查定了次序，先让运行时找到用于观察的程序，再用程序报告的信息解释它内部的行为。

前端项目里常见的“启动开发环境”可能同时包含打包器、文件观察者和应用。列表里出现几个名字相似的进程很正常。在 macOS 打开“活动监视器”，从“显示”菜单选择按层级查看进程，可按名称搜索 node 并核对 PID；Linux 的系统监视器也可显示用户和进程号。刚才的短命令通常来不及看见，等本章出现长时间运行的服务再对照它自己打印的 PID。看到同名只说明使用了相同的运行程序。要判断一个具体窗口里停掉服务会影响哪一份记录，还需要把它的监听地址与实际创建请求对应起来。

一个很具体的线索是某个窗口能执行 fetch，另一个窗口还没发出请求就报告找不到这个名字。这时并未走到请求地址解析，更没有机会连到服务。让出错的窗口自己报告 node 和 execPath，与正常窗口对照；若版本不同，回项目目录选定版本，再在同一窗口重试。只在第一个窗口重新选择版本，对第二个窗口已建立的环境没有作用。若两边都确实是要求的版本，才继续比较启动选项和执行代码的上下文。

### 环境变量是启动输入，读取后还要解释

第三章为解决端口占用，允许直接修改源码里的 `3000`。这适合最初观察，却不适合同时运行两个实例：每次换端口都改源码，会把“程序做什么”和“这一次怎样启动”混在一起。

端口应当成为启动输入。在修改服务之前，先用刚才的观察程序检查输入到底是什么：

```bash
PORT=3001 node examples/runtime-context.js
node examples/runtime-context.js
```

第一条命令只给这一次命令设置 `PORT`；第二条应恢复原来的值，如果原来没有设置，就显示 `(unset)`。输出中的 `"3001"` 是字符串。shell 不知道这个变量代表网络端口，Node 也不会因为变量名叫 `PORT` 就替我们完成数值校验。

如果执行 `export PORT=3001`，后续由这个 shell 启动的子进程会继承它；用 `unset PORT` 可以从当前 shell 环境移除。继承发生在创建子进程时。之后在另一个终端改变量，或者修改当前 shell 的值，都不会追溯更新已经启动的服务。反过来，子进程修改自己的 `process.env`，也不会修改父 shell。

这种继承更像一次启动时交付的副本，而不是多个进程共同查询的一张动态配置表。可以在子 shell 里验证，避免改变平时终端中的配置：

```bash
(
  export PORT=3001
  node -e 'console.log("child before:", process.env.PORT); process.env.PORT = "3002"; console.log("child after:", process.env.PORT)'
  printf 'shell after: %s\n' "$PORT"
)
```

子进程应先显示 3001，再显示 3002，最后 shell 仍显示 3001。由此可以判断“我已经改了环境变量，为什么服务没有变化”：可能是改在另一个进程里，也可能服务已经把旧字符串解析成配置对象。即使在服务内部修改 `process.env.PORT`，已经建立的监听也不会自动迁移；程序还需要明确实现重新配置的动作。

`.env` 文件也不例外。它只是文本，必须由 Node 的相关启动选项或某段加载代码读取，才会进入配置流程。到这里的命令尚未增加加载步骤，所以仅新建一个 `.env` 文件不会改变服务；稍后再把加载接进开发命令。这是追踪输入来源的方法：从启动命令一路找到读取、解析和使用位置，而不是根据文件名猜测它已经生效。

最直接的配置代码可能是：

```javascript
const port = Number(process.env.PORT || 3000);
```

它很短，却隐藏了两个决定。空字符串会被当成“未配置”而退回默认值；非空的错误值则会得到 `NaN`。换成 `parseInt()` 也不是校验，例如 `parseInt('3001oops', 10)` 会接受前面的数字。调用者以为自己传了一个值，服务却使用另一个解释，出错位置还可能拖到监听阶段。

本章选择明确的规则：未提供变量时使用默认端口；提供了变量，就必须是一串十进制数字，转换后位于 1～65535。空字符串、空格、小数和混入字母的值都拒绝。`0` 在 Node 监听时可以让系统分配端口，但本章需要一个读者可以直接请求的固定端口，所以也拒绝它。数字字符串允许前导零，转换后的数值仍按范围检查。

这不是 Node 规定所有项目都必须这样配置，而是我们给服务建立的输入契约。4.4 会把这组规则写进 `loadConfig()`，并在真正监听之前执行。若以后需要支持随机端口，应明确改变契约，再从监听结果读取实际地址。

把规则从调用者这一侧再算一次。要同时满足“不填就跟随项目交付的端口”和“填错要告诉我”，第一问应是调用者有没有提供值。读取不到变量，才有资格走默认值的分支；读取到空字符串，说明值存在，可以告诉启动者这一项没有数字。若先做数值转换，空串与单个零都会变成数字零，程序丢掉了区分两个原因的信息。校验中间值的意义就在这里，出错的人应当能分辨需要补一个值，还是需要选一个允许的数。

比如操作者提供 `03001`，第一步得到五个十进制数字，第二步按十进制转换成整数三千零一，第三步发现它在范围内，才可以交给监听层。若需求改成“端口必须使用没有前导零的规范写法”，数值相同的两个输入就要得到不同结论，只能在转换之前检查原字符串。相反，两个不同字符串只要转换后都超过上限，就可以由同一个范围分支解释。需求决定哪些信息要保留到哪一步，选择正则表达式或数值函数是后面的事。

容易漏掉的调用者是维护服务的人。在前端表单里，输入框旁能显示错误，被拒绝以后用户可以当场修改。启动配置的调用者可能是一个只会看退出状态来决定是否继续的脚本。服务若悄悄换回默认端口，后续请求仍发到指定端口，会把一次配置错误表现成连接错误；如果指定端口恰好有另一份服务，还可能得到看似正确的响应。因此错误应该带上字段名、期望的写法和允许的范围，在进入监听之前结束本次启动。不需要把这次进程收到的整套配置打印给操作者。

### 让本机配置可重复，又不混进交付目录

每天启动都手写同一组变量容易遗漏，也不方便确认项目默认值。在根目录添加 `.env.example`，内容为 `PORT=3000`，只保存无秘密的示例。首次准备且还没有 `.env` 时复制一次；已有本机文件就保留它，只记录并临时调整练习用的 PORT 那一行：

```bash
cp .env.example .env
```

在 `.env` 修改本机端口。文件本身不会被 Node 自动读取：把 package.json 的 dev/debug 命令中 `node` 后加上 `--env-file-if-exists=.env`，仍保留第三章的 NODE_ENV、watch 与 Inspector 参数。第四章完整脚本如下：

```json
{
  "dev": "NODE_ENV=development node --env-file-if-exists=.env --watch --inspect=127.0.0.1:9229 src/server.js",
  "start": "NODE_ENV=production node src/server.js",
  "debug": "NODE_ENV=development node --env-file-if-exists=.env --inspect-brk=127.0.0.1:9229 src/server.js",
  "check": "node --check src/server.js && node --check src/config.js"
}
```

不存在 `.env` 时继续使用公开默认配置；存在时由 Node 读取，已有进程环境变量优先。例如 `PORT=3001 npm run dev` 优先于文件中的 3000。NODE_ENV 则由 npm 脚本明确指定，不能靠修改 `.env` 把 dev 变为生产入口。当前配置只在启动读取，改 `.env` 后手动重启；自动监听源码不会替你重新加载启动环境。

第三章的忽略规则已经排除 `.env` 并允许 `.env.example`。实际秘密不写进示例、请求集合或 Git，交付时也不复制开发文件。`npm start` 不带 env-file 参数，由目标环境提供 PORT；配置仍经过本章稍后建立的格式与范围校验。文件加载成功和配置值有效是两件事。

先把加载文件和服务接线分开验证。现在的开发脚本已经能把文件里的值交给 Node，但第三章的服务本身仍固定监听 3000；而刚写进 check 脚本的 `src/config.js` 要到 4.4 才创建。此时合适的观察对象是 runtime-context。用编辑器将练习用的 `.env` 暂时设为 `PORT=3002`，保存后从项目根目录运行下面三行。第一行的括号让取消变量这件事只影响本次实验。

```bash
( unset PORT; node --env-file-if-exists=.env examples/runtime-context.js )
PORT=3001 node --env-file-if-exists=.env examples/runtime-context.js
( unset PORT; node examples/runtime-context.js )
```

依次只看报告里的 port 字段。第一份得到字符串 3002，说明提供了文件名、文件也被读取；第二份得到字符串 3001，说明同一文件仍在，也可以由启动者覆盖。第三份显示未设置，说明把工作目录放在项目根目录，只让这个文件有机会被找到，还需要有谁明确去读它。用编辑器把练习文件恢复成原先的值。这三个结果中没有一个能单独证明端口已经可连接，因为三个程序都只打印了它们收到的输入。

如果第一、二次都读到 3001，先看执行的是不是含有括号和 unset 的完整第一行，再看自己改的是本机文件还是带 example 后缀的模板。复制只是从某一时刻的模板生成一份文件，以后保存模板不会同步更新副本。编辑器里可以同时打开两份，比较标签名和内容；到文件树确认它们都位于含有 package.json 的目录。把这两项分开检查，就能解释别人从相同提交新建工作目录时为什么能得到不同值，也能判断应该把默认值改在公开配置，还是只改这一台机器上的覆盖值。

### 日志为什么出现在终端里

环境变量传入的是启动信息，输入输出通道则承担运行过程中的数据交换。进程通常获得三个约定好的通道：标准输入 stdin、标准输出 stdout、标准错误 stderr，对应文件描述符 0、1、2。

文件描述符可以先理解为当前进程用于访问已打开资源的编号。编号不是文件路径：程序经由编号 1 写出内容，操作系统再把内容交给该编号关联的资源。启动者可以把它关联到终端，也可以关联到文件或管道，所以 `console` 并没有一个固定不变的“显示窗口”。这也解释了为什么同一段代码可以在终端显示日志，也可以由进程管理器收集日志。

在 Node 中，`console.log()` 通常写入 stdout，`console.error()` 写入 stderr。两者直接连接终端时都显示在同一个窗口，看起来没有区别；把输出分开后，区别就出现了：

```bash
node examples/runtime-context.js > runtime-output.txt
cat runtime-output.txt
```

这一次，JSON 进入文件，`stdoutIsTTY` 应为 `false`。`>` 是 shell 的重定向操作，不是 JavaScript 语法，也不是 Node 的日志配置。它会创建或截断目标文件，实验请使用这里专用的文件名；`>>` 才是追加。这个输出文件可能包含本机路径，不需要提交到仓库。

这里还有一个能用两列结果检验的判断。观察程序为 stdin 和 stdout 分别报告是否连接到终端，说明两者可以由启动者独立安排。先在编辑器的普通交互终端直接运行它，一般两项都为 true；把 stdout 重定向到文件，stdin 仍接终端，文件中的这两项应分别为 true、false。接着在同一终端运行 `printf '一行备注\n' | node examples/runtime-context.js`，此时 stdout 仍接终端，两项应变为 false、true。如果两端都像前面的命令那样分别接入管道和文件，就应得到两个 false。不同终端宿主可能把输出接到自己的捕获通道，应以实际报告为准。它检查的是进程眼前的连接，编辑器最后也许仍把捕获结果画成一块很像终端的面板。

再看这个管道的正文去了哪里。观察程序只读取 stdin 的连接属性，代码中没有读取正文的循环，所以那行备注不会出现在观察结果里。能判断输入从哪来，不等于消费了输入。假如要做一个工具，遇到终端就提示用户输入，遇到管道就不显示提示，TTY 能帮助决定怎样提示；它不能告诉程序管道里有几条记录、数据有没有到齐，或者下一次读取会不会成功。决定何时开始计算结果仍要依赖读取步骤。下面换一个真正消费 stdin 的程序，才能把输入内容和所见输出逐字对上。

接下来新建 `examples/echo-stdin.js`，观察输入也可以来自另一个程序：

```javascript
process.stdin.setEncoding('utf8');
for await (const chunk of process.stdin) {
  process.stdout.write(chunk);
}
console.error('stdin ended');
```

在项目根目录执行：

```bash
printf 'EPP runtime\n' | node examples/echo-stdin.js > echo-output.txt 2> echo-error.txt
cat echo-output.txt
cat echo-error.txt
```

前一个文件应只有 `EPP runtime`，后一个应有 `stdin ended`。`printf` 写出的字节通过管道成为 Node 的 stdin；输入流结束后，循环才结束。`setEncoding('utf8')` 让流处理跨块解码，避免把任意字节块直接当作完整字符。这里沿用第三章已经讲过的流，不假设一次循环就是一整行。

这里结束循环的依据是输入流结束，不是“暂时读不到内容”。前面的 `printf` 结束并关闭写端后，读者才能在读完缓冲内容后看到输入结束；如果上游仍持有写端而暂时不输出，等待就是正确行为。把这两个条件混淆，文件导入程序就可能只读到一部分便宣告完成。

这是小输入的通道观察示例。它没有处理慢速输出的背压，大文件转发的资源控制在第 59～60 章展开。当前先把两个独立判断建立起来：输出去了哪里，要看通道连接；命令成功与否，要看退出状态。stderr 可以输出进度，stdout 也可能包含错误文本，文本放在哪条通道并不会自动决定进程成败。4.3 会把这个区别用于启动失败的处理。

前端读到一个响应时，开发工具会把状态、响应头和正文放到同一个请求条目里。终端没有这种配对关系。记录服务接收一次创建请求，会由服务进程经 stdout 输出请求方法，同时经客户端的 HTTP 连接返回包含 ID 的 JSON。把服务的 stdout 改接到文件，只会移动前一份输出。如果在服务日志里搜不到刚创建的原文，先看配套记录了哪些字段；本章只记事件与方法，正文要去 Postman 的响应 Body 看。这也解释了同一条创建请求为什么能在没有终端窗口的环境里工作，客户端需要的是一个可达的监听地址。

把 echo 示例换成一条常见的中文备注，可以检验“保留输入”具体指什么。在终端执行下面的命令，再用编辑器分别打开两个输出文件。这里重新使用前面的练习文件名，覆盖的是那两份演示输出。

```bash
printf '第一段\n第二段' | node examples/echo-stdin.js > echo-output.txt 2> echo-error.txt
node -e 'const b = require("node:fs").readFileSync("echo-output.txt"); console.log(b.length, JSON.stringify(b.toString("utf8")))'
```

输出文件里是两行正文，第二行末尾没有额外的换行。第二条命令用带引号的显示方式把不可见的换行显出来，应该看到 `19 "第一段\n第二段"`。六个汉字在这份 UTF-8 输入中各占三个字节，加一个换行字节共十九个；诊断文件另有结束提示。若把转发语句改成按块调用 console.log，每次调用还会附加换行，即使窗口里看着差不多，下游拿到的内容也已经变化。比较字节数和可见的转义形式，比数屏幕上出现了几行更能检验“原样转发”。

还可以不向它交付任何正文，用 `printf '' | node examples/echo-stdin.js` 看它仍能报告输入结束。写端正常关闭且总共交付零字节，和交付了半条备注后暂时停顿，对读取者是两种不同的事。将来若用同一段流读取逻辑导入文件，文件为空是否属于业务错误由导入格式决定；流层只报告它已经读完。接收 HTTP 请求时，数据又来自请求对象，不能把终端的 stdin 当作所有请求共享的正文入口。

## 4.2 浏览器与 Node.js 的全局对象、文件访问和权限边界

### 同一个 API 名称，不代表同一个运行上下文

从前端转过来，最容易混淆的不是语法，而是把浏览器提供的环境一起带进服务端。例如，第三章在列表页面里调用 `fetch('/captures')`，相对地址可以借用当前页面的来源；Node 中没有那个页面，也就没有一个隐含的 `location` 替它补全地址。

把浏览器 Network 面板里的两个地址，和本机编辑器显示的文件路径放在一起看。请求地址里有协议、主机、端口和路径；创建响应的 Location 只有从斜线开始的一段路径；本机项目文件也有一个以斜线起头的绝对路径。人能凭上下文理解这些写法，程序要看谁来解释。交给浏览器的 URL 解析器，开头的斜线回到这个来源的根；交给文件系统，它从本机文件系统的根出发。两者之间没有自动映射。服务能返回素材，来自请求处理函数在 Map 中查找 ID，项目目录里并没有一个名为 captures 的对应文件夹。

浏览器替应用省去的条件可以用一个不联网的计算找回来。把下面的表达式放在本机 Node 的交互环境里，或在 Chrome 的 Console 中逐条计算。若进入了 Node 交互环境，算完输入 `.exit` 回到 shell。两个地址只用于字符串解析，实际服务无需启动。

```javascript
new URL('/captures', 'http://127.0.0.1:3001/practice/').href
new URL('captures', 'http://127.0.0.1:3001/practice/').href
```

第一条保留了协议、主机和端口，结果直接以 `/captures` 收尾；第二条从基准的目录继续，结果以 `/practice/captures` 收尾。两者都能算出完整地址，但配套只实现了前一种列表路径。这样就有了一个分界：URL 能构造出来只说明目标表达清楚，服务器是否监听、有没有这条路由，要等发送请求才能观察。平时用开发服务器的代理功能时，浏览器先把相对地址解释为页面所在的来源，开发服务器之后要不要转发则由它自己的配置决定。本章的服务里没有那一层转发。

先在终端观察当前 Node 提供的对象：

```bash
node -e 'console.log(typeof globalThis, typeof window, typeof document, typeof fetch)'
```

在本章普通 Node 运行环境中，应得到：

```text
object undefined undefined function
```

`globalThis` 是访问当前环境全局对象的标准入口。浏览器页面有 DOM，Node 默认没有页面 DOM；但现代 Node 已提供 `fetch`、`URL` 等不少 Web API。因而“浏览器有的 Node 都没有”并不成立，“有 fetch 就拥有浏览器页面环境”也不成立。

从第三章跟写的读者先在项目根执行 `node src/server.js`；使用第四章完成快照的读者用 `PORT=3000 node src/server.js`。已有自己的练习实例在监听 3000 时直接用它。看到监听成功的地址后，留着这个服务终端，在另一终端用 Node 调用列表接口：

```bash
node --input-type=module -e 'const response = await fetch("http://127.0.0.1:3000/captures"); console.log(response.status, await response.json());'
```

这里写完整 URL，明确连接目标。`--input-type=module` 用于把 `-e` 中的代码按 ESM 执行，从而使用顶层 `await`；普通项目文件已经由第三章的 `"type": "module"` 声明模块格式。模块系统的完整比较留到第六章。

还有一个容易误判的边界：浏览器同源策略约束网页脚本，不能当作服务端的访问权限。Node 中的请求不会自动继承某个浏览器页面的 Cookie 与登录状态，也不依靠浏览器的 CORS 检查决定能否发送请求。以后服务是否允许读取某条记录，要由身份与权限机制决定。当前绑定 `127.0.0.1` 只是把监听限制在本机网络接口，并没有给记录接口增加登录校验。

在浏览器地址栏打开刚才的完整地址，Network 面板打开后刷新，选中 captures，比较 Request URL、Status 和 Response。两次读取命中同一个进程时，中间没有新建记录就应当读到相同的 items。浏览器展示的缩进和终端打印对象的样式可以不同。对照完在服务终端按 Ctrl+C，留出端口给后面的实验。

读请求还能帮我们找出究竟缺了哪个条件。在这里如果把 Node 命令中的完整地址换成单独的 `"/captures"`，默认环境里的 fetch 无法解析目标，调用在取得 HTTP 状态之前就会拒绝。若地址完整，端口上却没有服务，同样拿不到状态，但原因已经移到建立连接这一步。再看第三种情况，服务正在该地址运行，客户端读一个尚无对应记录的详情，会收到带状态的响应，当前服务在正文中说明找不到素材。此时应用还有机会读 `response.status` 和 `response.json()`。前两种失败要观察调用抛出的异常及其原因，后一种要检查已获得的响应；三种情况都归为“接口没数据”，就会把精力花在错误的位置。

写一个既供页面又供命令行使用的详情链接生成函数，可以顺着这个例子决定参数。输入应包含创建响应中的 Location 和本次创建实际发往的地址，输出一个完整 URL。页面端能从这次响应的 `url` 获得基准，独立客户端也记录了目标。两者都可以复用 `new URL(location, base).href`。若函数内部自行读取 window.location，测试时就非得造一个页面才能计算本来很简单的值。如果写死第三章的 3000，改端口后两个不同实例的资源路径再相像，也会把详情读到另一份 Map 上。把基准当成调用方要交付的输入，才方便在两个端口之间独立检验。这里只讨论本机服务自己返回的详情路径。

### 能调用文件 API，不等于拥有任意文件的权限

浏览器页面的文件访问受到浏览器提供的能力与授权机制约束，例如由用户选择一个文件再交给页面。Node 的 `node:fs` 则允许程序直接提出按路径访问文件的请求，操作系统再根据运行身份、路径与访问方式决定是否允许。

这里有两层不同的问题：运行时有没有提供某个 API，以及调用者有没有访问目标的权限。Node 提供文件 API，并不能让一个没有访问许可的进程读到目标文件；反过来，程序属于自己的项目，也不代表它的依赖只能访问这个项目目录。通常运行在同一进程里的依赖代码使用相同的进程权限，所以不应把安装依赖理解成只引入了一组没有外部影响的纯函数。

一次文件访问可以顺着“定位目录—查找名字—检查访问条件—打开资源—读写—关闭”来理解。目录权限控制能否沿路径到达目标，文件权限与打开方式决定能做哪类操作。比如读取默认配置和新建日志文件需要的条件不同：前者需要到达并读取既有文件，后者还要允许在输出目录创建名字。只知道某个账号“能访问这个目录”还不足以作出判断。

不要把这种差异理解为“后端天然有更高权限”。普通 Node 进程不会因为运行 JavaScript 就自动成为管理员；把程序从终端挪进受限环境，也可能让原来可访问的路径失败。更不能为了绕过 `EACCES` 就直接把整个服务改成管理员运行，这会扩大它能够改动的范围。

对照前端的文件上传交互，可以更具体地看出两边各自拿到了什么。页面里的文件选择框让用户选中一份文件，脚本拿到可读取的 File 和一个文件名。把名字字符串写进 JSON 发给服务，只会传输这个名字。服务即便能按名字调用 readFile，查的也是运行服务那台机器上的目录；开发时浏览器恰好和 Node 在同一台电脑，容易掩盖这一点。本章的创建接口接收的是原文字符串，因此要保存编辑框中的文字，就把文字作为 originalText 发送；若未来需要上传文件，必须另约定如何传输内容以及由服务如何存放。把前端文件名当成服务端路径同时混淆了数据位置与操作权限。

现在把“读不了”落到一次具体操作上。编辑器的文件树能展开项目目录，说明编辑器这个进程在它的打开位置能列出一些名字。要让服务读一份配置，还要确认它选中了哪份代码，传给 readFile 的实际目标是什么，以及服务进程的身份能否沿途查找到文件并读取内容。若读取成功而 JSON 解析失败，已经取得了字节，继续修改目录的权限无助于解释内容。相反，若连打开都失败，先去给 JSON 补一个逗号也无从验证。定位的依据是最后完成的那一步；先写出这一步，再选能观察下一步的工具，通常能省掉一轮无关修改。

先把文件内容的寿命和访问操作的寿命分开。下面的例子在独立临时目录创建文件，完成写入后再读回；不修改已有项目文件。新建 `examples/file-note.js`：

```javascript
import { mkdtemp, readFile, writeFile } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import { join } from 'node:path';

try {
  const directory = await mkdtemp(join(tmpdir(), 'epp-note-'));
  const filename = join(directory, 'note.txt');
  await writeFile(filename, 'EPP file example\n', { encoding: 'utf8', flag: 'wx' });
  console.log(await readFile(filename, 'utf8'));
  console.log(`Saved example: ${filename}`);
} catch (error) {
  console.error(`File example failed (${error.code ?? error.name})`);
  process.exitCode = 1;
}
```

运行：

```bash
node examples/file-note.js
```

这里先让系统选择临时目录，再由 `mkdtemp()` 创建一个独立目录，不猜测本机临时目录一定叫 `/tmp`。`join()` 按平台规则拼接路径。`writeFile()` 默认可能覆盖同名文件，因此显式使用 `wx`：创建新文件，若目标已存在就失败。这个选择把“不覆盖已有文件”交给实际打开文件的操作，不先用“检查不存在，再写入”的两步流程制造竞争窗口。

`writeFile()` 接收路径时会组织打开、写入与关闭；`await` 等待这次操作完成，后面的读取才建立在这个完成条件上。去掉 `await`，读取与写入就可能交错，不能再保证文件内容已经可用。传入 `'utf8'` 时，`readFile()` 返回字符串；不传编码则返回 Buffer。它会把整个文件读进内存，因此适合这里的小文件，不是任意大小文件的通用方案。

运行成功时会先看到 `EPP file example`，再看到实际文件位置。程序结束以后，文件不会因为进程退出立刻消失；可以在本机用编辑器打开该路径，再删除这个程序刚创建的演示目录。临时目录可能被系统清理，不能作为业务数据存放位置。若运行受限，观察错误码即可，不必改动系统目录权限来强行完成例子。

如果改为自己调用 `open()` 持有文件句柄，就需要在成功和失败路径中都安排关闭；异常不会自动跳到某个正常路径末尾的 `close()`。关闭释放访问资源，不删除已经写入的内容。这个区别同样适用于后面的数据库连接和其他外部资源：资源收尾与业务回滚需要分别设计。

文件确实比内存活得久，但这仍不足以把记录服务变成可靠的持久化系统。我们还没有处理并发写入、写到一半中断、历史结构变化，也没有从文件恢复 Map。一个文件写入 Promise 成功，也不是所有崩溃与掉电场景下的数据持久性保证。这一章只建立文件访问和生命周期的直觉，第三篇会从数据库开始处理业务持久化。

从 file-note 的返回值还能推导出另一个容易漏掉的单位问题。示例写入的英文后面本来就有一个换行，随后 console.log 又为显示附上一行结束符。屏幕上多出空行不意味着磁盘上也多写了一个换行。将输出里的绝对路径复制到编辑器的“打开文件”框中，可以看到一行正文；要检验写入协议，可以另开终端运行下面的读回命令，把带引号的参数替换为刚才打印的完整文件路径。若前面已经清掉演示目录，先重跑 file-note 取得一份新的文件。这里 `node -e` 没有脚本文件占用参数位置，第一个用户参数在 argv 的下标一。

```bash
node -e 'const b = require("node:fs").readFileSync(process.argv[1]); console.log(b.length, JSON.stringify(b.toString("utf8")))' "/替换为本次目录/note.txt"
```

应显示十七个字节和一个以 `\n` 转义结尾的字符串。用一个全新的进程也能得到这十七个字节，证据比仅看到写入程序打印的同一段文字更强，因为读取的对象是外部文件。连续运行两次 file-note 会得到同名的 note.txt，却各有不同的父目录；在第二个窗口打开第一份路径仍会读到第一份。若想让下一次启动读取指定的上一份笔记，光知道固定的文件名还不够，必须保留那次返回的目录或给调用方一个明确的位置约定。

再想想这里的“新建”究竟保障了哪一步。独立目录避开了两次练习之间的干扰，排他创建把同一个位置已有文件时的结果定为失败。假如将来要求“已有导出结果时保持原样”，可以在自己的临时目录先写一份旧备注，再以同一文件名、同一排他方式尝试写新备注。按这个约定，第二次应在打开目标时得到 `EEXIST`，读回仍是旧内容。这里不需要根据两次操作的速度猜谁先写，也不能把收到错误的那次标为成功。换一个需求，“允许替换，但其他读取者只能看到完整的新旧版本”，单凭排他创建就无法把第一份切换到第二份；这已经要求设计整份结果怎样发布。想清楚允许哪些中间状态，再决定打开方式，比笼统地选一个看起来稳妥的文件 API 更可靠。

## 4.3 启动参数、退出码、信号，以及为什么服务能持续运行

### 谁在解释命令中的参数

现在用已经建立的观察程序运行：

```bash
node --no-warnings examples/runtime-context.js --label demo
```

`execArgv` 应包含 `--no-warnings`，`args` 应为 `["--label", "demo"]`。前者在入口文件之前，由 Node 解释；后者在入口文件之后，作为应用参数交给程序。`process.argv` 前两个元素通常分别是 Node 可执行文件与入口文件的路径，因此本例使用 `slice(2)` 只显示应用参数。

观察程序只是展示参数，并没有实现一个 `--label` 选项。第三章的服务也没有实现 `--port`，所以在后面加上 `--port 3001` 不会自动换端口。参数传进来、程序解析它、程序据此改变行为，是三个独立步骤。

同样，`npm start -- --port 3001` 中的 `--` 只负责把后面的参数交给脚本，不会替脚本增加解析能力。第三章的调试命令把 `--inspect-brk` 放在入口之前，是因为这是 Node 的选项。`--no-warnings` 在这里仅用于辨认参数位置，日常运行不要为了让终端干净而隐藏诊断信息。

从一个真实的启动动作还原参数，先把每一段写到它的接收者旁边。以 `PORT=3001 node examples/runtime-context.js --label "两份 记录"` 为例，shell 看到的是一次临时环境赋值和一个要执行的命令。它先识别引号，把引号内的空格留在同一个参数里，交给 Node 时已经没有引号本身。Node 取走入口名，观察程序最后看到的是两个应用参数，一个是双横线开头的标签名，一个是里面带空格的值。端口在 port 字段里，既不占一个应用参数的位置，也不会因为标签有空格而移位。拿掉引号再运行，args 数组会多一个元素，端口与入口均相同。这样从数组就能定位错误发生在文字被拆成参数的时候，没必要修改应用的字符编码。

再把 `--no-warnings` 移到观察程序文件名之后。对于这段观察代码，它会出现在 args 里，execArgv 里没有这项。书写完全相同的一串字符，换位置以后换了接收方。设计自己的命令时也要给参数规定消费规则，比如某个选项是否必须带一个值，值中能不能有空格，遇到多余参数是否报错。观察程序把输入原样展示，足够帮助判断传输；它即使成功退出，也没有验证调用者指定的标签存在。若要让启动命令接受端口参数，还得约定它与环境变量都出现时听谁的，复用端口校验并覆盖这两个来源的组合。当前只保留环境入口，省去了一项会改变结果的优先级。

这也能解释开发工具为何通常把“运行时参数”“程序参数”“环境”放在不同的输入框里。把调试选项填在程序参数框，应用仍可能正常启动，但运行时没有开调试入口；把业务标签填成环境变量，会在另一个通道里留下它，读取 argv 的代码依然找不到。排查时用观察程序临时代替长时间运行的入口，保留相同的启动方式，先看字段归属，再去检查业务如何解释值。若连入口都没执行到，当然也不会有观察报告，这时应先看启动器自己给出的选项或入口错误。

### 打印了错误，为什么仍然算成功

shell 需要用一个结果判断刚才的命令是否成功，这就是退出码。先运行两个不依赖 HTTP 的小实验，每次紧接着读取 `$?`：

```bash
node -e 'console.error("example error message")'
echo $?

node -e 'console.error("example failure"); process.exitCode = 1'
echo $?
```

第一次应为 `0`，第二次应为 `1`。`$?` 是前一条命令的退出状态，中间插入别的命令就会覆盖它。错误说明写到 stderr，表达给人看的原因；非零退出码表达给启动者看的失败结果。部署脚本不应靠搜索日志里有没有英文 `error` 判断启动是否成功。

为什么第三章使用 `process.exitCode = 1`，不直接 `process.exit(1)`？前者设定自然退出时的结果，让已安排的工作按正常机制收尾；后者要求立即终止，可能截断尚未完成的输出或异步操作。二者不能互换。

但设置 `exitCode` 也不等于已经开始关闭服务。如果监听资源仍然存在，进程可以继续运行，只是在将来退出时携带这个结果。第三章监听失败后可以结束，是因为没有成功建立那份监听资源，且没有其他工作需要继续。以后连接数据库、启动后台任务后，必须逐一安排关闭；只赋一个退出码不会释放它们。

退出码的实际消费者可以短到只有一行 shell。项目的检查脚本把两个 `node --check` 用 `&&` 串起来，前一次退出零才会运行后一次。此时服务端口上可以没有任何监听，脚本也能成功，因为它只要求两个文件通过语法检查。反过来，跟写到 4.3 尚未建立配置模块，检查脚本会因找不到文件而失败。等 4.4 写好两个文件再运行它，不能把这个中途状态诊断为 HTTP 服务故障。要证明服务可用，需要启动并观察监听，还要用客户端读到一份预期响应。

可以在任意目录试一次这个条件。先执行 `node -e 'console.error("checking")' && echo next`，会看到 next；再在单引号内的语句末尾加上 `; process.exitCode = 1`，后面的 next 就不会出现。失败的命令已经输出了文字，shell 仍然只根据返回的状态决定是否执行下一段。如果把两段写成换行连续的两条普通交互命令，第二条则会照常运行。第一次验收新项目时，终端最后一句“完成”究竟是上一段真的成功后才可能打印的，还是操作者无条件又执行了一句，用这个办法就能分清。

现在考虑一个还没退出的服务。调用者在原窗口等不到提示符，无法在那个窗口询问这次命令的最终状态；在新的终端执行 `echo $?`，读到的是另一个 shell 自己的上一条命令。要知道一个长时间运行的程序现在是否已经可以用，启动阶段应给出监听成功的通知，运行期间应以访问指定地址的结果为准，结束以后才轮到退出状态。三个时刻分别回答能否接收、当前能否响应以及最终怎样结束。以后用工具托管服务，工具上显示“进程已启动”也只能回答其中一部分。

### 顶层执行结束，不等于没有工作了

观察程序打印完就退出，记录服务却停在终端里等请求。判断这一点时，要分开三件事：JavaScript 对象是否还可访问，操作系统资源是否还被占用，以及运行时是否还有需要等待的工作。

例如，顶层 Map 仍然可访问，并不会单凭这一点让程序永久运行；打开但没有进行异步操作的普通文件描述符，也不一定阻止 Node 自然退出。HTTP 监听不同，它要求运行时继续等待连接。所谓资源“保活”，说的是这种运行时层面的等待责任，不是变量还在作用域中，也不是对象还没被垃圾回收。

`createServer()` 创建对象，`listen()` 才请求建立监听。成功监听后，即使此刻没有请求，这份默认保持引用的活动资源仍要求运行时等待新的连接。顶层语句结束，只表示初始化这一轮执行结束，不能推导出所有工作已经结束。

这里的“引用”指资源是否要求事件循环继续存活。等待网络事件不需要让 JavaScript 不停执行；运行时可以交由操作系统等待事件，再在条件满足时安排后续处理。若用忙循环“保活”，反而会占住处理请求所需的执行机会，第五章会沿这个边界观察等待与计算的差异。

可以用定时器先做一个不涉及端口的对照：

```bash
node -e 'setTimeout(() => console.log("timer fired"), 1000); console.log("top level ended")'
node -e 'setTimeout(() => console.log("timer fired"), 1000).unref(); console.log("top level ended")'
```

第一条先打印 `top level ended`，等待约一秒后打印 `timer fired`；第二条中定时器被取消了“要求进程保持运行”的引用，通常只打印第一行就结束。`unref()` 没有取消定时器：如果还有别的资源让进程活着，它仍可能触发。因此不能把关键写入任务放进一个被 `unref()` 的定时器，再假设程序一定等它完成。

同理，一个普通、未完成的 Promise 本身不一定保活：

```bash
node -e 'new Promise(() => {}); console.log("created a pending promise")'
```

这个命令会结束。HTTP、文件 I/O 或定时器背后可能有实际工作，单独构造 Promise 却没有建立这些资源。这里刻意没有使用顶层 `await`；未完成的 ESM 顶层等待有单独的退出语义，不能把两种例子混成“所有 Promise 都不影响退出”。当前只需抓住判断依据：究竟是谁登记了仍需处理的工作。

把 unref 的结果反过来验证一次。在前面只剩一个可选定时器的命令里，运行时可以直接结束，因此看不到它到期不能证明它被取消。要区分两个解释，只需把“进程还能活多久”改变一次，保留那一份可选工作。下面这条命令安排一个更晚到期、使用默认引用的定时器。

```bash
node -e 'setTimeout(() => console.log("optional"), 50).unref(); setTimeout(() => console.log("required"), 200)'
```

正常运行时先看到 optional，后看到 required。两次等待在同一段顶层代码中登记，后一个定时器使进程活到它的回调有机会执行；前一个的到期条件在此期间也满足了。若真正要求撤销前面的工作，必须持有它返回的标识并调用 clearTimeout。一次操作改变“还有谁需要进程继续运行”，另一次改变“到点后是否还要运行这个回调”。两次实验的输出就能把这两种解释分开。五十和二百的单位都是毫秒，表示等待阈值，不是承诺回调一定在墙钟的那个精确时刻完成。

再回头看记录服务，监听就像那份需要进程持续存在的工作，但它没有约定最后一个到期时刻。发送完一次响应，只结束了这次请求的响应写入，程序还在等下一次连接。想把一个小程序改成“处理一份输入就结束”，应选能表明输入已完结的条件，比如文件读完或 stdin 遇到 EOF；若仍保留一个永久监听的服务器，即使手头这份输入已处理好，运行时仍有留下的理由。判断脚本为什么一直挂着，先画出它要求运行时等待的来源，再找每一个来源本应由谁关闭，这比在最后一个函数里随意添加 return 更容易解释现象。

### Ctrl+C 与关闭资源是什么关系

在终端里前台运行服务时，`Ctrl+C` 通常由终端向前台进程组发送 `SIGINT`。另一个常见停止信号是 `SIGTERM`。在本章使用的 POSIX 环境中，Node 对它们有默认退出行为，第三章没有添加处理器，所以按下 `Ctrl+C` 后服务会结束。进程结束时，操作系统回收它持有的资源，内存记录也随之丢失。

要单独观察 `SIGTERM`，先启动一个临时进程，输出自己的 PID，再用一个十分钟定时器保持活动，给我们留出发送信号的时间：

```bash
node -e 'console.log(process.pid); setTimeout(() => {}, 600000)'
```

在另一终端核对这个 PID 确实属于自己刚启动的演示进程，再执行：

```bash
kill -TERM 实际PID
```

不要照抄示例数字，更不要结束归属不明的进程。`kill` 的名字容易误导：这里是在发送信号，不是任何用法都表示立即强制杀死。原终端紧接着执行 `echo $?`，Bash／Zsh 通常把 SIGTERM 终止表示为 `143`，SIGINT 表示为 `130`。用进程 API 观察时，退出信号也可能独立于数值退出码返回，不能把 shell 的编码方式当成所有工具统一的结果。

现在看一个**不要直接加到服务里**的片段：

```javascript
process.on('SIGTERM', () => {
  console.log('received SIGTERM');
});
```

一旦注册处理器，默认退出行为就改变了。信号不是一个会从调用栈中抛出来、自动触发所有 `finally` 的异常。Node 把这个事件交给注册的回调；回调返回后，如果监听仍保持活动，进程就还需要继续等待。所以上面的日志只能证明“收到了停止请求”，不能证明“停止已经完成”。

由这里可以推导收尾顺序。首先关掉产生新工作的入口，否则等待已有请求期间还会不断出现新请求；然后根据业务要求等待或取消已接受的工作；最后释放这些工作仍依赖的资源。若先关闭数据库连接，再让正在保存的请求继续执行，就破坏了后者的完成条件。对于不会自行完成的工作，还必须有收尾时限和超时处理。

当前记录服务仍保留默认停止方式，数据库连接与 HTTP 请求的完整协调将在第十四章落实。现在需要先掌握这条因果关系：接管停止信号就接过了决定何时退出的责任；函数返回、收到信号、资源释放和业务完成并不是同一个时刻。独立的定时任务例子可以把这些时刻拆开观察，而不必提前给记录服务接入数据库。

`SIGKILL` 无法被捕获，程序没有执行清理代码的机会。由此也能推导：把内存记录的唯一保存机会安排在退出回调中，无法保证数据可靠。处理停止信号和保证数据持久化解决的是不同问题，需要分别设计。

操作停止之前还要选对观察对象。配套有两种常用启动形态，直接执行 node 时，前台那份 Node 就是刚才自己打印 PID 的程序；运行 npm 的开发脚本，前台这组进程里还可能有负责运行脚本和监听文件变化的进程。如果只终止其中一个子进程，留在前台的启动器可能继续等待。为了观察系统默认的信号状态，前面的十分钟命令刻意绕开了 npm 和 watch。可以在第二个终端执行 `ps -o pid=,user=,comm= -p 实际PID`，把输出里的进程号、用户和命令名与第一窗口里刚启动的 node 对上。若原窗口已经回到提示符或第二窗口没有查到进程，就结束这轮对照，用新启动的程序重新取号。

为什么一定要在原窗口读状态？发信窗口里的 kill 返回零，只说明这一次发送信号的调用成功。若接收方装了只打印日志的处理器，同样会收到信号，却可以继续运行。回到原窗口，在看见提示符之后马上取状态，才是在看前台命令的结局。在支线的演示中还可以读另一类证据，每一项工作开始时打印带编号的 start，完成时打印同一编号的 done。停止前已经打印 start 的编号能不能全部配成对，信号之后还有没有新编号，比“最后一行像不像成功”更接近业务对收尾的要求。

把这条时间线套回一个正常的创建请求。客户端发出请求时，服务可能还没读完正文；拿到正文后它验证字段、生成记录并写入当前 Map，最后才写回响应。若在中途结束进程，仅凭客户端没拿到响应推不出服务究竟执行到了哪一行。反过来，客户端已经收到创建成功也只能证明那次内存写入成功，当时的响应没有许诺进程消失后仍可读。判断一次停止的后果，应从服务已经向调用者承诺了什么开始，而不能看见操作系统回收端口，就推断所有业务请求都有可交付的结果。

读到这里可以停下，保留已建的 `examples/` 文件和开发配置即可。此时记录服务还沿用第三章固定端口，4.1 只是准备了环境输入，尚未接入读取它的 `loadConfig()`；因此不能用服务有没有换端口来判断前面的环境实验是否成功。下次回到项目根目录执行 `nvm use`，从下面建立 `config/service.json` 开始，再把输入接到监听。停止过的服务不会保留 Map，后面的接口回查使用新请求即可。

## 4.4 相对路径、文件读写与环境差异：复现换目录后启动失败

### 先给相对路径找出它的基准

现在把端口配置接入服务。为了同时区分“随项目交付的默认配置”和“本次启动的覆盖值”，在根目录新建 `config/service.json`：

```json
{
  "port": 3000
}
```

这个小文件保存公开默认值，可以随代码提交；环境变量 `PORT` 覆盖本次运行的端口。当前只有一个值，继续在源码中保留默认值也完全可行。这里把它单独放到文件，是为了把读文件这一运行条件放进同一份服务，亲自验证路径选择；并不是以后每个常量都必须拆成配置文件。

读取它最自然的写法，是 `readFile('./config/service.json', 'utf8')`。先不要把这个假设藏进启动流程，新建独立复现文件 `examples/cwd-config.js`：

```javascript
import { readFile } from 'node:fs/promises';

try {
  const text = await readFile('./config/service.json', 'utf8');
  console.log(JSON.parse(text));
} catch (error) {
  console.error(`Cannot read config from cwd (${error.code ?? error.name})`);
  process.exitCode = 1;
}
```

在项目根目录运行，应该读到 `{ port: 3000 }`：

```bash
node examples/cwd-config.js
```

再在同一个终端执行：

```bash
(
  cd src
  node ../examples/cwd-config.js
)
```

括号开启子 shell，里面的 `cd` 不会改变外层终端的目录。此时入口文件仍能找到，读取却应失败，得到 `ENOENT`。程序实际上在寻找 `src/config/service.json`，因为文件 API 中这个相对字符串以 `process.cwd()` 为基准，和 `cwd-config.js` 位于哪个目录无关。

还可以把工作目录换到项目父目录：

```bash
(
  cd ..
  node epp-book-code/examples/cwd-config.js
)
```

这里假设实践目录仍叫 `epp-book-code`，且父目录没有别的 `config/service.json`。若父目录碰巧有同名文件，程序可能更糟：不报错，却读入别的配置。因此修正目标不能只表述为“别报 ENOENT”，而应是“无论从哪里启动，都读取这份项目自带的默认配置”。

这与入口查找是两个阶段。从 `src/` 执行 `node src/server.js`，入口本身就找错了；执行 `node server.js`，入口能找到，内部文件仍可能找错。报错时先确认执行到了哪一步，再决定改启动命令还是改程序中的路径。

还有一种比缺文件更难发现的结果，值得亲手核对。假设我们的做法只是“试着从 cwd 读，能够读就返回”，最有区分力的实验是让两个位置各有一份合法配置，而且端口不同。无需在项目上一级碰别人的文件。在项目根目录打开一个终端，下面的变量只保存这次练习的位置。新建目录归本次实验独占，在其中建一份合法的 3017 配置，然后借用项目里的观察程序读取。记下临时目录的位置，后面还会用到。

```bash
epp_project_dir="$PWD"
epp_sample_dir=$(mktemp -d)
printf '本次样本目录：%s\n' "$epp_sample_dir"
mkdir "$epp_sample_dir/config"
printf '{"port":3017}\n' > "$epp_sample_dir/config/service.json"
(
  cd "$epp_sample_dir" || exit 1
  node "$epp_project_dir/examples/cwd-config.js"
)
```

项目配置还是 3000，这一次却读到 3017，退出状态是零。入口使用绝对路径，加载的是同一段观察代码；工作目录换到临时目录，里面确有 config，读文件、解析 JSON 和显示字段都能正常完成。这个反例比单看一条缺文件消息告诉我们的更多，连“文件存在且字段合法”也不足以确认读对了资源。用编辑器分别打开项目与临时目录里的两个文件，给它们各自写下来源，就能决定哪一个值才符合“跟随当前程序版本”的承诺。

如果这个需求相反，命令明确要求读取操作者当前项目的配置，刚才得到 3017 反而正是期望。比如一个通用检查器安装一次，进入两个不同的项目各执行一次，本来就该检查两套文件。此时以程序安装位置为基准会让两次都检查到检查器自己的目录。路径错误之所以不能靠背一个推荐 API 解决，是因为在选择路径之前得先选定资源的所有者。让两处各放一个可辨认的正常值，就能检验自己的实现究竟尊重了哪一份约定。

### 资源跟着模块走，路径就跟着模块定位

这个错误有几种看似能用的修法。要求所有人先 `cd` 到项目根目录，实际上是给启动方式增加约束；把本机绝对路径写死，会让代码只适用于一个安装位置；在程序里 `process.chdir()` 到根目录，则改变整个进程此后所有 cwd 相对操作，可能连用户指定的输入输出位置一起改掉。

本次真正需要固定的只有项目自带配置的位置。它随程序版本交付，应该由代码所在位置决定；无需改变整个进程的工作目录。当前项目使用 ESM，可以通过 `import.meta.url` 获得当前模块的 URL，再定位资源：

```javascript
const configUrl = new URL('../config/service.json', import.meta.url);
```

这行稍后位于 `src/config.js` 中，因此 `../config/` 回到项目根目录下的配置目录。URL 的基准是**写下这行代码的模块**，不是最初入口，更不是调用它的文件。`readFile()` 可以直接接收 `file:` URL，无需自己处理路径里的空格或百分号转义，也不要简单截取 `.pathname` 充当跨平台文件路径。

下面新建 `src/config.js`，这是本章最终使用的完整实现：

```javascript
import { readFile } from 'node:fs/promises';

export async function loadConfig() {
  const configUrl = new URL('../config/service.json', import.meta.url);
  let text;
  try {
    text = await readFile(configUrl, 'utf8');
  } catch (error) {
    throw new Error(`Cannot read config/service.json (${error.code ?? 'UNKNOWN'})`);
  }

  let defaults;
  try {
    defaults = JSON.parse(text);
  } catch {
    throw new Error('config/service.json must contain valid JSON');
  }
  if (defaults === null || typeof defaults !== 'object' || Array.isArray(defaults)) {
    throw new Error('config/service.json must contain an object');
  }
  if (!Number.isInteger(defaults.port) || defaults.port < 1 || defaults.port > 65535) {
    throw new Error('config/service.json port must be an integer from 1 to 65535');
  }

  const rawPort = process.env.PORT;
  if (rawPort === undefined) return { port: defaults.port };
  if (!/^[0-9]+$/.test(rawPort)) {
    throw new Error('PORT must be decimal digits from 1 to 65535');
  }
  const port = Number(rawPort);
  if (!Number.isInteger(port) || port < 1 || port > 65535) {
    throw new Error('PORT must be an integer from 1 to 65535');
  }
  return { port };
}
```

这里保留了两个输入边界。JSON 解析成功只说明文本合法，还要确认顶层是对象、默认端口是范围内的整数。环境变量则先校验字符串，再转换并检查范围。两条路径最终都返回 `{ port: 数字 }`，监听代码不必再次猜测输入类型。

检查顺序也表达了一个取舍：即使传入合法 `PORT`，随项目交付的默认文件仍必须存在且有效。这样遗漏配置文件的发布包会立即失败，不会在某台机器上靠环境变量侥幸运行。如果希望环境变量完整时允许缺省文件，就要重新设计加载顺序和必需条件；不能只是吞掉所有读文件错误，再回退到 `3000`，因为缺文件、没权限和内容损坏需要不同修正。

当前只在启动时读一次，所以修改文件或环境变量后需要重启。每个请求重新读配置会引入额外 I/O，也会让同一进程的行为随文件修改而改变；我们没有这样的需求。第十四章再把配置组织与启动生命周期系统化。

用上面的临时目录回答一个更细的问题：如何证明 loadConfig 真的修正了刚才那次误读？如果给它一个合法的环境覆盖，两份文件最后都会产生同一个 port，单看返回对象就分辨不出来源。本轮先取消覆盖，把当前工作目录留在样本目录，把绝对的配置模块路径当作参数交给一个一次性的 Node 命令。这个命令只导入项目模块并调用加载函数，不启动 HTTP 服务。

```bash
(
  cd "$epp_sample_dir" || exit 1
  unset PORT
  node --input-type=module -e 'import { pathToFileURL } from "node:url"; const { loadConfig } = await import(pathToFileURL(process.argv[1])); console.log(await loadConfig())' "$epp_project_dir/src/config.js"
)
```

现在返回 3000。入口参数指向源码，pathToFileURL 把这个平台路径转换成可用于 import 的文件 URL，模块自己的 import.meta.url 随之确定；从这里沿上一级进入的是项目的 config 目录。刚才那个 3017 文件仍然可以读取，当前目录也确实没变，结果差异只能沿两种读取函数选取基准的过程解释。若隔天回来已经换了终端，先在项目根重新运行建立临时样本的那组命令，再做这个对照。结束后按打印或保存的位置清理自己创建的样本目录。

从空白写一个配置加载器时，先列出每个阶段应交给下游的值。读文件成功得到文本，JSON.parse 成功得到一个 JavaScript 值，确认它是对象才有理由询问 port，再把整数与上下限放在一起判断。即使合法 JSON 也可能只有数字 3000，数值本身满足端口取值范围，文件却没有按约定给出对象。也可能对象有 port，值是带引号的字符串。若此处为了方便也调用 Number，配置文件就默许了另一种格式，配置生成工具把数字写成字符串的错误将无从发现。来自环境的字符串则恰好相反，要先认可它的文字写法再转成数字，因为环境根本没有可直接交付的数值类型。

从头推演一份可正常运行的配置。提供的默认文件是对象，端口为数值 3000，环境中未设置 PORT，于是按对象字段得出数值三千并返回；同一个文件遇到环境输入 03001，关于文件的全部步骤仍发生，后半段改读字符串，最后返回数值三千零一。在调试器里分别看 defaults.port、rawPort、port，就能沿着这一条调用定位，手头拿到的是文件默认值、原始覆盖值还是已经决定的监听参数。没有环境输入时函数会从中途直接返回，后面的局部变量不会经历赋值，单在函数最后一行等断点自然等不到。

若未来允许完全由外部配置启动，还要定义“外部配置完整”的条件。将来多一个必填字段，单有端口就不足以跳过文件读取。本项目先读默认文件的顺序给了维护者一个判断依据：环境端口明明有效，日志却说不能读取默认文件，这两条信息可以同时成立。应先补齐交付资源，再检查覆盖值。

### 先完成启动条件，再宣布服务可用

回到 `src/server.js`。在已有 import 后加入：

```javascript
import { loadConfig } from './config.js';
```

删除原来的 `const port = 3000;`，保留 `const host = '127.0.0.1';`、Map、请求处理函数与 `createServer()`。然后把文件末尾原来的 `server.on('error', ...)` 和 `server.listen(...)` 两段整体替换为：

```javascript
async function start() {
  const { port } = await loadConfig();
  server.on('error', (error) => {
    if (error.code === 'EADDRINUSE') {
      console.error(`Cannot listen on ${host}:${port}: address already in use`);
    } else {
      console.error(`Server failed: ${error.code ?? 'UNKNOWN'}`);
    }
    process.exitCode = 1;
  });
  server.listen(port, host, () => {
    console.log(`EPP listening on http://${host}:${port} (pid=${process.pid})`);
  });
}

start().catch((error) => {
  console.error(`Cannot start EPP: ${error.message}`);
  process.exitCode = 1;
});
```

这份改动让成功日志具有清楚含义：默认文件可读、配置有效，而且监听已经成功。如果先监听再读配置，就可能短暂接收请求，随后才发现启动条件不成立；如果在 `listen()` 之前输出“启动成功”，就无法从日志区分真正启动与端口占用。我们把条件安排在它们应当成立的位置。

还有两条错误路径。读取和解析配置时的拒绝由 `start().catch()` 接住；端口占用等异步监听错误由 `server.on('error')` 处理。`start()` 不会等待未来所有服务事件，把它包进一个 `try/catch` 并不能代替事件监听。第三章对请求失败单独 `.catch()`，也是因为请求拥有自己的异步完成边界。

试着只从启动成功那一行往回推。要打印它，必须先执行监听回调；要进入回调，向操作系统申请的地址必须可用；能发出这次申请，说明 loadConfig 已成功返回。因此这行日志能帮助排除“本次启动时项目默认文件丢失”。它不能证明此后文件一直存在，服务已经把要用的端口读入内存，也不能证明任何一个客户端实际访问了该地址。对照客户端的 Request URL 与一次列表响应，就能把“服务宣告了什么”和“客户端访问了谁”接起来。两者之间的证据不能只靠日志里出现了服务名来补。

也可以从失败端往回读。已经看到了 `Cannot start EPP: …`，说明进入了本项目的 start 拒绝处理；看到了 `Cannot listen on …: address already in use`，说明已经算出了 host 和 port，错误发生在向操作系统申请监听时。第一类可能是读不到文件或转换配置失败，第二类最常见的是上一终端还有进程。若连这些文字都没有，终端只显示 Node 找不到入口或模块，应从执行位置与 import 开始。语法检查更早，只检验输入能否被解析；可以用 `npm run check` 做第一次筛查，随后仍得启动同一份源码才会执行到文件、环境与监听的检查。

看这段启动代码，还有一个容易在自己写日志时做错的选择。若在调用 start 之后立即打印“已准备好”，即使文件还在读取，那句日志也会执行；若把它移动到 await loadConfig 之后、listen 之前，仍不知道同一个端口能不能申请成功。若在业务处理函数里打印，又必须有客户端主动请求才会留下第一次记录。三个位置所能承诺的事实各不相同，本章把“监听成功”放到回调里，把“某个请求到了”留给原有的请求事件日志。以后服务多了数据库等前置条件，也应从希望通知调用者的事实倒推还需要等待哪些条件。

接线完成后可以在 Chrome 实际停在上述两个中间状态。结束前面自己的开发服务，确保本机调试端口 9229 和业务端口 3001 可用。在项目根运行 `PORT=03001 npm run debug`，到 `chrome://inspect` 选择这次的 Node 目标。程序暂停在启动代码时，打开 Sources 中的项目文件 `src/config.js`，分别在 `if (rawPort === undefined)` 和最后的 `return { port };` 两行设断点。点 Resume，第一次停下时在 Scope 看 defaults.port 与 rawPort，前者是数字 3000，后者是带前导零的字符串。再次 Resume，第二处的 port 已经是数值 3001。此时两次都还没有进入 listen，发列表请求并不能检验这份暂停中的服务。

取消这两个断点，再次 Resume，回服务终端等到成功监听日志，才向 3001 发送列表请求。这样就能确定先前看到的 3001 确实进入了监听，而非仅仅存在于配置函数的局部变量里。关闭本次调试连接，在服务终端按 Ctrl+C，等回到提示符再开始下面的双实例实验。若配置阶段过得太快，检查自己启动的是带启动暂停的 debug 脚本；在已经运行起来的 dev 实例上设启动断点，后续普通读请求不会让它重新执行 loadConfig。

### 改变条件，核对刚才的推导

下文用两个空闲的本机业务端口 3000 和 3001。若已经另有用途，开始前就改选空闲端口，并一起替换甲乙的启动配置、请求地址及后面的占用对照。先在项目根目录启动甲；按默认端口跟做时，若此前使用过 `export PORT`，先执行 `unset PORT`：

```bash
npm start
```

应在成功监听后看到 `http://127.0.0.1:3000` 与当前 PID。先保留它，称为甲。在 Postman 使用第三章保存的集合，Variables 中核对本次实际使用的 baseUrl 为这个地址，运行“01 查看列表”，新进程应返回空的 items。只发送一次“02 创建原文”，可以把原文改为“终端甲”，记下响应的 ID 与 Headers 中的 Location，把 ID 填到集合的 captureId。再发“03 查看详情”，应为 200 且原文一致。这里有意先在甲留下一个能辨认的样本，两个全空列表无法告诉我们读的是不是同一份数据。

另开一个位于项目根目录的终端启动乙。两个实例都用普通的服务入口，不使用带有同一 Inspector 端口的两个开发命令，以便只改变业务监听地址：

```bash
NODE_ENV=production PORT=3001 node src/server.js
```

乙应报告 3001 与自己的 PID。复制 Postman 集合用于乙，副本的 baseUrl 改为 `http://127.0.0.1:3001`，captureId 仍填甲刚创建的 ID。点开乙的列表请求，核对实际 URL 后发送，应为 200，items 为空。再发乙的详情，预期为 404，错误正文说明找不到素材。回甲的集合发送同一条详情，仍为 200。两次详情路径相同，变化的是连接目标；甲乙都能解释这条路由，只在各自查 Map 时看到不同结果。若乙也读到甲的记录，先在 Postman Console 对照最终发送的两个完整 URL，检查是否修改了另一个集合或有已选环境的同名变量覆盖了集合值。

到这里还可以分辨“读错实例”和“乙压根没有启动”。两种情况下甲都能继续返回成功，所以反复点甲的列表没有区分力。应看乙的监听回调有没有报告自己的 PID，再直接查看乙的列表；能收到来自乙的空数组及合法详情路由的 404，表明请求已交给了应用。若乙地址根本不能连接，客户端得不到应用层状态，应该回乙的终端查看启动结果。服务日志里的 http.request 只带方法，核对时一次只发一个请求，看哪个终端新增一行；用浏览器观察时，额外的图标请求也可能产生 GET，最好用 Postman 单独发送。

再在乙用“02 创建原文”存一条“终端乙”，把乙集合的 captureId 更新为这次的新 ID，列表与详情均应只看见属于乙的原文。返回甲集合再查列表，仍应只有“终端甲”。这比比较两次返回的 ID 是否不同更有区分力，即使两个请求全发到同一个实例，它也会给不同的新建记录分配不同 ID。真正证明两张 Map 分开的事实，是同一时刻两边对同一个 ID 的判断不同，并且新增乙的数据不会改变甲的列表。把两个窗口各自的地址、样本文字和返回 ID 临时记在一起，就能随时复查而不用凭记忆猜测。

保留两个成功实例时，还能重现第三章见过的端口冲突。在第三个终端且项目根目录执行 `PORT=3001 node src/server.js`，这次使用的是合法端口值，失败的位置应是监听层，终端指出地址已被占用，紧接着读退出状态应为一。乙原来的详情仍能读取。失败的是新实例取得地址的那次尝试；原先持有资源的实例继续工作。

现在到甲、乙各自的服务终端按 Ctrl+C，等两个窗口都回到提示符，再运行下面的启动失败对照。保留甲乙的 ID 供之后比较，端口和内存记录的寿命在这里分开了，停止释放了地址，下一次成功申请同一个地址的进程仍会重新创建 Map。

下面验证错误输入在监听前就被拒绝：

```bash
NODE_ENV=production PORT=3001oops node src/server.js
echo $?

PORT= node src/server.js
echo $?

NODE_ENV=production PORT=65536 node src/server.js
echo $?
```

前两种应输出 `PORT must be decimal digits from 1 to 65535`，最后一种应输出范围错误；退出码均为 `1`，且不出现成功监听日志。空值不会偷偷回退到默认端口，这正是 4.1 选择的规则。

最后，从 `src/` 启动同一个服务：

```bash
(
  cd src
  NODE_ENV=production PORT=3001 node server.js
)
```

这次应成功读取项目默认文件，再按环境变量选择端口。在乙的 Postman 集合对刚才的同一个 ID 再发详情，应得到 404；列表状态为 200 且为空。这里整条请求地址都没有变，上一次成功保存记录的进程已经结束。与刚才甲乙同时存活时的 404 对照，一个要查目标端口，一个要查看同一地址在两次请求之间是否经历重启。核对完在服务终端按 Ctrl+C 回到外层终端，工作目录仍然是项目根目录。需要只检查配置、不占用端口时，也可以在根目录执行：

```bash
node --input-type=module -e 'import { loadConfig } from "./src/config.js"; console.log(await loadConfig());'
```

这里 `-e` 中的相对 import 仍从当前执行位置解析，因而命令明确要求在根目录运行；模块内部的资源定位则已经固定为相对于 `config.js`。修正一种相对路径，不代表所有相对路径都变成同一套规则。

特别留意 npm：npm 脚本通常在包根目录执行。所以从包内子目录运行 `npm start`，可能仍然成功，无法暴露直接 `node` 启动时的 cwd 问题。npm 的便利改变了启动上下文，并没有让 `readFile('./...')` 自动相对于源码。定位故障时应比较真实启动命令、cwd 和文件基准，不能只比较“执行的是同一个 JS 文件”。

### 把路径的选择用到另一种需求

默认配置的问题解决以后，再看一个约束不同的命令：它接受操作者提供的输入文件名，并把导出结果放在执行命令的位置。这里用户希望从自己的数据目录操作，程序却可能安装在另一个目录。若把输入和输出全部改成模块相对路径，就会修好默认配置、同时弄错用户文件。

位置由谁决定，才是选择基准的依据。随程序交付的资源跟着模块；操作者传入的相对文件名按命令约定从 cwd 解析；部署配置还可以指定绝对目录。绝对路径本身没有问题，问题在于是否把某一台机器的位置未经配置写进了通用源码。

新建 `examples/path-report.js`，先只输出解析结果，不读写用户文件：

```javascript
import { resolve } from 'node:path';
import { fileURLToPath } from 'node:url';

const input = process.argv[2] ?? './input.json';
console.log(JSON.stringify({
  cwd: process.cwd(),
  bundledConfig: fileURLToPath(new URL('../config/service.json', import.meta.url)),
  userInput: resolve(process.cwd(), input),
  outputDirectory: resolve(process.cwd(), './exports'),
}, null, 2));
```

`resolve()` 把路径解析成绝对形式；参数本来就是绝对路径时，就以它为准。这个计算不检查目标是否存在，也不赋予访问权限。`fileURLToPath()` 则把文件 URL 正确转换成当前平台路径，处理空格编码等细节，而不是直接截取 URL 的字符串。

从根目录与 `src/` 分别执行：

```bash
node examples/path-report.js ./input.json
(
  cd src
  node ../examples/path-report.js ./input.json
)
```

先预测三个输出，再对照结果：`bundledConfig` 应始终指向同一份项目配置；`userInput` 应分别指向项目根目录与 `src/` 中的 `input.json`；`outputDirectory` 也随操作者的目录变化。这里两次调用选择了不同的输入，符合这条命令的约定。如果操作者想从两个目录读取同一文件，就应传入指向同一目标的路径，而不是要求程序偷偷改变解释规则。

可以不改这份报告程序，再检验一次“同一输入、两个输出位置”的需求。设想团队在根目录统一放一份本地样本，操作者希望分别在两个目录生成导出结果。先从项目根用 `./input.json`，再在 src 里传 `../input.json`，第二次仍执行 `node ../examples/path-report.js`，只是把最后的参数换掉。现在 userInput 应完全相同，outputDirectory 仍不相同。把路径手算一遍，第一次由根目录进入样本，第二次从 src 先上移一级才进入样本；输出参数没有随之变化，两次都从自己的 cwd 进入 exports。两次报告的路径可以相等，即便练习目录里根本没有这个文件，程序完成的是定位，尚未执行读取或导出。

有了这个对照，可以从需求反向审查一种常见改法：有人提议在模块刚加载时切到它自己的目录，再让所有读写都用相对路径。这样随后每一个 resolve 都会看到已经被修改的 cwd，用户从哪一个目录发起导出这条信息也被丢掉了。另一种做法是保留 cwd，只把默认资源的定位封装在读配置的函数里面。即使以后同一个进程既要读默认配置又要导出文件，两种意图也能同时满足。如果未来改成由用户明确传入导出目录，程序还应约定该参数省略时从哪里出发，并把选定的结果交给写文件的代码。那时检验成功的条件也要从“报告里的路径符合预期”进一步变成“在那个位置实际读回本次导出的内容”。

再考虑打包交付：模块相对定位只能稳定地找到“相对当前产物”的位置。如果把源码编译到 `dist/`，却没把配置放到约定的相对位置，文件仍然会缺失。第六章会结合编译产物继续处理交付结构。对于来自不可信请求的文件名，还要另外限定可访问范围并处理路径穿越；路径规范化不等于授权，这部分随文件业务展开。

这样再面对“同一份代码换了启动方式就失败”，可以按阶段缩小范围。先确认实际 Node 与入口，再确认 cwd、有效配置来源和解析出的目标；路径正确后继续判断运行身份、目录与文件权限；文件读到后再判断内容结构。只有已经通过这些条件，才轮到监听端口与处理请求。每一层有自己的证据，也有不同的修正位置。

现在，记录服务启动时会校验配置，也清楚指定了到哪里读文件。从启动到退出，你可以沿同一个进程追踪它读入了什么、哪些状态由它保存，以及何时释放资源。第五章将保持这些运行条件不变，继续分析服务存活期间的执行：一个请求正在等待 I/O 时，为什么另一个请求可以继续；正在占用 JavaScript 执行的计算，又为什么会改变这个结果。

本章完成代码分支：`part-01/chapter-04`，从第三章状态继续演进。`config/service.json`、`src/config.js` 和本章 `examples/` 文件随代码保存；依赖清单与锁文件没有新增第三方依赖。

主线阅读约 76～92 分钟，跟做另加约 60～80 分钟，合计约 136～172 分钟。4.1 建立观察程序、对照环境来源和通道约需 12～16 分钟，4.2 比较调用地址并独立读回文件约需 9～12 分钟，4.3 核对参数、等待与退出约需 9～12 分钟，4.4 接入配置、观察两个启动断点、比较两种工作目录并用两个实例交叉读回约需 30～40 分钟。可以在 4.3 末停下，给需要同时保留两个实例的最后一节单留一段时间。首次安装、逐行手敲和额外排错另计，三条支线各自估时。

### 进程与输入输出

| 名称 | 本章用途 | 必要注意点 |
| --- | --- | --- |
| `process.pid`、`process.version`、`process.execPath` | 识别进程和实际 Node 运行环境 | PID 可重用；分享路径前检查个人信息。 |
| `process.cwd()`、`process.env.PORT` | 读取启动位置与环境输入 | cwd 不等于模块目录；环境变量按字符串解释，缺失与空值分开处理。 |
| `process.argv`、`process.execArgv` | 区分应用参数与 Node 参数 | 应用参数通常从 `argv.slice(2)` 开始；传参不等于实现解析。 |
| `process.stdin`、`stdout`、`stderr`、`isTTY` | 观察输入输出连接到终端、文件或管道 | 通道由启动者连接；stderr 内容不会自动改变退出码。 |
| `setEncoding('utf8')`、异步迭代、`stdout.write()` | 读取小段标准输入并原样转发 | 数据块不等于行；大型转发还要处理输出背压。 |
| `process.exitCode`、`process.exit()` | 区分自然退出结果与立即终止 | 设置退出码不释放监听资源；立即退出可能丢失未完成输出。 |
| `SIGINT`、`SIGTERM`、`process.on()` | 理解终端停止与进程信号 | 注册处理器后应用承担相应收尾责任；`SIGKILL` 不能捕获。 |
| `setTimeout()`、定时器 `.unref()` | 对照资源引用与进程寿命 | `unref()` 不取消定时器，但进程不一定等它执行。 |

### 文件、配置与运行环境

| 名称 | 本章用途 | 必要注意点 |
| --- | --- | --- |
| `readFile(path, 'utf8')` | 读取小文件内容 | 相对字符串基于 cwd；也接受 `file:` URL；整文件进入内存。 |
| `writeFile()`、`flag: 'wx'` | 新建独立演示文件 | `wx` 拒绝覆盖现有文件；等待完成后再读，不等于建立业务持久化保证。 |
| `mkdtemp()`、`tmpdir()`、`join()` | 创建临时演示目录并拼接路径 | 临时目录可能被清理；路径拼接不承担权限校验。 |
| `import.meta.url`、`new URL(relative, base)` | 定位随模块交付的资源 | 基准是当前模块；发布时仍需包含资源文件。 |
| `path.resolve()`、`fileURLToPath()` | 区分调用者路径与模块资源，并将文件 URL 转为平台路径 | 路径计算不检查存在性、不授予权限；不要直接截取 URL 的 pathname。 |
| `process.chdir()` | 比较改变整个 cwd 与只定位一个资源的影响 | 会改变此后 cwd 相对操作，已打开的通道不会随之迁移。 |
| `JSON.parse()`、`Number()`、`Number.isInteger()` | 将配置文本转为受约束的数值 | 文本可解析不代表结构合法；端口还需范围校验。 |
| `ENOENT`、`EACCES`、`EPERM`、`EEXIST` | 分辨路径不存在、访问受限及目标已存在 | 依据发生阶段定位；不要统一吞掉错误或提权重试。 |
| `globalThis`、`fetch`、`URL` | 比较浏览器与 Node 提供的 API | Node 的 Web API 不带来 DOM、页面来源或浏览器会话。 |
| `loadConfig()` | 本项目自己的启动函数 | 默认文件必须有效，`PORT` 可覆盖；不是 Node 内置 API，也不热更新。 |
