## 6.1 第一篇结束后，怎样理解自己对 Node.js 的掌握

第一篇的成果，是能够脱离逐行照抄，建立一个与当前记录服务规模相近的内存服务：安排输入校验、写入和响应的顺序，解释字节怎样成为业务数据；换目录、换端口或重启时，能判断程序的配置、资源和状态发生了什么；请求变慢时，能先区分异步等待与 JavaScript 阻塞；交付时，能把类型检查、模块解析、构建和产物运行串起来。前面的正文和支线负责建立这些理解，下面的实践负责检验它们能否用于改变后的条件。

如果仍然解释不清为何输入非法却已经写进 Map，或为何源码能运行、产物却找不到模块，就需要回到第二章或第五章补足推导。当前承担的基础，应当在当前讲透；不能把这些疑问一律留给后面的框架解决。完整的服务关闭、内存增长排查和大文件传输则需要加入新的机制与约束，下面用已有实现说明后续为什么继续展开。

以停止服务为例。第三章通过有限任务解释了停止接收、等待已有工作与释放资源，已经让我们知道“收到信号”和“可以退出”是不同的时刻。但记录服务仍采用默认信号处理。等服务需要协调正在处理的 HTTP 请求，就要进一步决定停止接受请求的时机、已有请求的等待期限和关闭失败的处理。第十三章会围绕应用生命周期展开；第三篇接入数据库后，再把连接的初始化与释放纳入同一套判断。到独立 Worker 和管理命令出现时，还要分别处理长期工作与一次性工作的结束条件。

文件处理也是如此。第二章针对有明确大小上限的小段 JSON，采用收集字节后统一解码的方式，这让我们看清了消息完整性和字符编码。后面接收文件时，输入规模、处理速度和中断位置都会改变。第 50～51 章会继续展开流、背压、文件处理及失败清理，解释哪些场景可以缓冲，哪些场景需要边读边处理，以及接收方跟不上时怎样控制资源。前面的实现有明确适用范围，后面的内容负责说明条件变化后如何选择。

第四章的执行模型也会继续使用。知道长计算阻塞主线程，是判断延迟的起点；在实际系统中，还需要结合请求耗时、事件循环、内存、连接和任务积压的证据定位瓶颈。第 55 章会把这些判断接到已有服务的性能与资源诊断上，第 57 章再接上进程托管。第五章建立的模块和产物边界，则会在第 54 章的多入口构建、第 65 章的发布更新，以及第 88 章的共享契约中继续接受检验。

进入 Nest 以后，请求仍由运行中的程序处理，阻塞仍会影响响应，资源仍有自己的寿命。框架改变职责组织，不会替应用决定输入边界、执行成本或交付范围。下面就先用现有程序改变运行条件，再实现一个带兼容约束的小需求，核对这些判断是否已经能独立运用。

## 6.2 不先改代码，先说明程序依赖什么

假设同事只拿到你提供的运行目录，要从另一个 cwd 启动服务，使用端口 `3001`，并接收包含中文与表情的原文。你需要说明应交给对方哪些文件、怎样启动、收到不合法输入时应发生什么，以及重启会保留什么。

先独立写下自己的判断，再对照第五章的独立目录操作。不要把整个开发项目连同 `node_modules` 复制过去；那会保留许多本次要排除的偶然条件。也不要提前把数据库或 Docker 加进来，当前问题由已经建立的能力解决。

最小的推导从消费者开始：Node 执行编译后的入口，因此需要产物 JavaScript 与正确的模块分类；配置按模块相对地址读取，因此需要保持 `dist/src/` 与 `dist/config/` 的布局；启动端口由环境提供，因此进程应继承 `PORT=3001`；运行依赖需要按清单与锁文件准备，本章没有第三方运行实现。类型声明与开发执行器不参与普通产物启动。

这说明交付的对象是一组满足关系的文件与环境，不是「某个能双击的 server.js」。如果交付后从另外一个目录失败，要把入口定位、模块定位、配置定位分别拆开看，不能把三个问题都归为相对路径。

## 6.3 用一条有效输入和一条无效输入确认边界

按照第五章建立独立运行目录，并从不同 cwd 用端口 `3001` 启动。复用第五章的“EPP 产物核对”Postman 集合，确认 `baseUrl` 为 `http://127.0.0.1:3001`。把创建请求的 raw JSON 替换为下面的正文，点击 Send；列表与详情继续使用已保存的请求。下面的 curl 保留同一输入的终端表示，选择一种客户端完成即可：

```bash
curl -i http://127.0.0.1:3001/captures \
  -H 'Content-Type: application/json' \
  --data '{"originalText":"  I want to explain this clearly. 我想表达清楚。🙂  "}'
```

核对 `201`、生成的 ID、创建时间和 `Location`，再读取列表与该条详情。返回原文应保留两端空格，中文和表情不应被拆坏。第二章已经解释过 UTF-8 字节与块边界，这里不要求网络恰好按某个字符分块；要知道实现为什么先收集字节、再合并解码，而不是把某一次正常显示当成所有分块情况都正确的证明。

再发送：

```bash
curl -i http://127.0.0.1:3001/captures \
  -H 'Content-Type: application/json' \
  --data '{"originalText":42}'
curl -i http://127.0.0.1:3001/captures \
  -H 'Content-Type: application/json' \
  --data '{"originalText":"   "}'
curl -sS http://127.0.0.1:3001/captures
```

两次错误输入都应返回 `400`，列表只保留此前那条有效记录。能够解释这一结果，要同时说明三个边界：JSON 语法正确不等于字段正确；类型声明不会改变网络输入；拒绝发生在 Map 写入之前。若列表新增了错误记录，即使错误响应看起来正确，写入顺序也仍有问题。

请求体限制是字节数，原文长度限制则沿用 JavaScript UTF-16 代码单元，两者不能互换。把原文全部换成表情后，代码单元数与视觉字符数可能不同。如果业务以后要求按用户看到的字符计数，需要重新定义契约和实现，不能只是把现有常量从 `2000` 改大。当前已能指出规则的位置和单位，并说明修改会影响什么。

## 6.4 把进程寿命、配置寿命与产物寿命分开

停止刚才的进程再启动，列表应为空。把同一份产物同时启动到另一个空闲端口，两边也不会共享 Map。这是两个运行实例分别拥有状态，不是同一个文件只能保存一份内容。数据库篇要解决的正是进程之外的持久状态与一致访问。

另一个容易混淆的现象是配置修改。第五章构建把默认配置复制到 `dist/config/`，因此修改开发目录的默认文件不会自动改变已经交付的副本；即使修改运行目录的配置，当前进程也不会自动重新读取，因为第三章只在启动时加载一次。重新构建、更新文件、重启进程是三个不同的动作，应当知道当前需要哪一个。

将一次启动的 `PORT` 改为 `3001oops`，应在监听前失败并返回非零状态。若另一个进程已经占用端口，应在监听阶段报冲突。这两类错误都使服务不能提供接口，但发生的位置不同：前者是配置不满足程序条件，后者是操作系统资源申请失败。定位时应从诊断信息沿对应阶段检查，而不是先修改请求处理代码。

第五章还让构建先清理旧产物再编译。遇到类型错误时，不能把上一版程序仍能启动当成新代码已经通过。把失败构建的输出交给同事也不成立：应当在构建完整成功后再建立运行目录。这是交付事实与开发状态之间的边界，后面的发布篇会在此基础上加入版本与回退。

## 6.5 需求变成批量处理时，先判断成本再选执行方式

现在暂时离开文件布局。假设有一项新需求：对一批原文做分析，单次分析是约半秒的纯 JavaScript 计算，希望期间查看列表仍能获得响应。不急着给 EPP 添加一个演示路由，先用第四章的 `/block`、`/slice` 与 Worker 例子说明可选方案为什么不同。

把函数写成 `async` 不能把半秒计算搬离主线程。在循环里 `await Promise.resolve()` 也不能保证 I/O 有机会推进，因为连续的微任务仍可能占住处理时机。分段配合 `setImmediate()` 让事件循环在片段之间推进，可以改善交错响应，但没有减少总计算量，也没有把计算并行到另一个核。

如果确实需要把计算移出主线程，Worker 可以提供另一个 JavaScript 执行环境，同时带来输入复制、结果消息、失败与退出的责任。每个请求随手创建一个 Worker 也不能自动解决容量问题；工作到达过快仍然会争用 CPU 与内存。当前有限示例能支持执行位置的判断，持续服务的线程复用与容量安排在后面的性能章节继续展开。

再把需求改为等待外部 I/O，判断又变了：异步等待本身不需要另一个 JavaScript Worker 来「帮忙等」。应关注等待是否有期限、真正的操作是否支持取消、失败由谁接住，以及已经接受的工作如何收尾。第四章的 `Promise.race()` 与合作取消实验已经给出了这种差别。

这里没有增加一个大作业。目标是面对改变后的成本来源，能够解释为什么选择不同，不把「后台」「异步」「多线程」当成可以互换的词。如果解释卡住，返回第四章对应的执行实验；若只会列出工具名称而无法预测探针与结果顺序，就还需要对照实际输出重建判断。

## 6.6 如何确认这一篇已经形成可迁移的能力

### 先独立实现一个改变规则的小需求

换目录说明运行关系可以成立，但还不能证明自己会把新需求接进程序。现在给记录增加一个**可选来源标签**：记下这段原文来自哪里，例如 Podcast。这个实验只改变一项输入规则与记录形状，不增加路由、依赖、数据库或身份功能。

需求先于实现。旧客户端只发送 originalText 时，创建、列表和详情仍返回原来的三个字段；不能为了新功能要求旧客户端补字段。新客户端可以发送 sourceLabel，它必须是字符串；去掉两端空白后，长度须为 1～80 个 UTF-16 代码单元，保存和返回去掉两端空白后的值。字段缺失表示没有标签，显式的 null、数字、空字符串或纯空白都不是“没有填写”，应返回 400。长度也按去掉两端空白后的结果判断。原文沿用现有规则，仍保留两端空格；16 KiB 请求上限及其他接口行为保持不变。此前未声明的其他字段继续按原服务忽略。

完成的依据不能只是一条带标签请求返回 201：不带标签的旧请求必须继续成功，失败输入不能增加 Map 里的记录，列表与详情必须和创建结果一致。最终运行的还应是独立目录里的新产物，而不只是开发入口。重启仍丢失全部记录，不需要为这个临时内存模型设计历史数据迁移。

先只阅读需求，自己说明准备修改哪些边界；按下一节建立隔离目录后，再实现第一版。特别要自行决定：怎样区分字段不存在与字段值非法，在哪一步转换标签，何时才能写入，以及怎样发现“错误响应正确但记录已经写入”。先选择自己的输入与观察位置，遇到不符预期的结果，用 5B 的请求和断点方法追踪；不要先把下面的参考代码贴进去，再用同一份代码解释自己为什么这么做。实现后再读分析参考，对照遗漏的前提。

### 分析参考：缺失、规范化与写入是三个决定

下面给出一种实现，用来对照自己的选择。它不是唯一合理的代码组织方式，但必须满足相同的完成条件。

首先，sourceLabel 是可选的，不能把 Capture 改成“每条记录都必须有一个字符串”。在实验目录的 `src/server.ts` 中，将 Capture 类型改为：

```typescript
type Capture = {
  id: string;
  originalText: string;
  createdAt: string;
  sourceLabel?: string;
};
```

可选属性表达内部允许缺失，不能验证外部输入。`if (body.sourceLabel)` 也不够：空字符串、null、数字 0 都会被当成没填，违反已声明的拒绝规则。第五章已经先把 body 收窄成非 null、非数组的对象，因此这里可以用 `in` 判断属性是否存在，再单独检查其值。当前 body 来自 JSON.parse 的普通 JSON 对象，不是在接受任意带原型行为的对象。

在 POST 分支中，保留原有 originalText 校验，将以下代码放在其长度校验之后、构造 capture 之前：

```typescript
let sourceLabel: string | undefined;
if ('sourceLabel' in body) {
  if (typeof body.sourceLabel !== 'string') {
    throw new HttpError(400, 'sourceLabel must be a string when provided');
  }
  const normalized = body.sourceLabel.trim();
  if (normalized.length === 0 || normalized.length > 80) {
    throw new HttpError(400, 'sourceLabel must contain 1 to 80 code units after trimming');
  }
  sourceLabel = normalized;
}
```

这里的 trim 与原文校验中的 trim 用途不同。原文只借它判断“是否全空白”，写入仍用原值；标签的需求明确要求规范化，因此判断与保存都使用 normalized。若判断规范化后的值却保存原值，就会出现“检查通过的内容与实际保存的内容不是同一个”的偏差。先看需求究竟要求判定还是转换，再决定是否复用转换结果；不是所有字符串都应该一律 trim。

随后把构造与写入片段改为下面这样；原有 Location 和状态码继续保留：

```typescript
const capture: Capture = {
  id: randomUUID(),
  originalText: body.originalText,
  createdAt: new Date().toISOString(),
  ...(sourceLabel === undefined ? {} : { sourceLabel }),
};
captures.set(capture.id, capture);
sendJson(response, 201, capture, {
  Location: `/captures/${capture.id}`,
});
```

条件展开让缺失标签的记录确实没有该属性，而不是给它填一个虚构的默认值。当前列表和详情直接返回 Map 中保存的记录，所以它们自然取得同一个规范化结果，不需要各自再写一遍 trim。若自己改成了响应对象投影，就要在三个入口分别核对字段，不能因为创建响应正确便假定读取也正确。

为什么把全部检查放在 captures.set 之前？若先保存再检查标签，即使最终返回 400，非法记录仍已进入 Map，下一次 GET 会读到它。catch 负责错误响应，不负责回滚。当前检查和写入之间没有 await，不需要为这一段引入事务或锁；以后若判断依赖异步读取的共享状态，则需要重新分析交错，这里不能替未来作保证。

### 用外部结果和内部事实核对自己的实现

准备核对产物时，先停止实验 dev，依次完成 `npm run typecheck`、`npm run build`，两步成功后用 `PORT=3001 npm start` 启动，确保此前占用 3001 的服务已停止。

在 Postman 复制“EPP 产物核对”集合并命名为“第六章来源标签实验”，保留 3001 地址。把旧、新、非法标签保存为不同请求，避免为改 Body 而覆盖原有案例。先读取列表并记录条数，再发送一条旧请求和一条新请求；对应终端表示为：

```bash
curl -sS http://127.0.0.1:3001/captures
curl -i http://127.0.0.1:3001/captures \
  -H 'Content-Type: application/json' \
  --data '{"originalText":"  old client  "}'
curl -i http://127.0.0.1:3001/captures \
  -H 'Content-Type: application/json' \
  --data '{"originalText":"  new client  ","sourceLabel":"  Podcast  "}'
```

两次都应返回 201，原文两端空格均保留；第一条没有 sourceLabel，第二条的标签恰好为 Podcast。分别复制返回 ID，读取 `/captures/<id>`，再读取列表；核对实际字段，而不只看状态码。重复运行会创建新记录，因此对照开始时的条数与本次 ID，不假定 Map 永远从零开始。

再选择纯空白、null 和数字等非法标签发送请求，例如：

```bash
curl -i http://127.0.0.1:3001/captures \
  -H 'Content-Type: application/json' \
  --data '{"originalText":"must not be stored","sourceLabel":null}'
curl -sS http://127.0.0.1:3001/captures
```

把 null 分别替换为 `"   "`、`0` 后再观察；这些请求都应返回 400，列表条数不增加。长度边界也要自己构造：去掉两端空白后恰好 80 个代码单元可接受，81 个拒绝，外围空白不计入这项上限。不要仅测试特别短和特别长的输入，否则无法区分“先检查长度”与“先去空白再检查长度”。可以用 `node -e 'console.log(JSON.stringify({originalText:"length boundary",sourceLabel:" "+"a".repeat(80)+" "}))'` 生成明确的 JSON，再按第二章的文件请求方式发送；将 80 改为 81 得到相邻失败输入。

若错误请求返回 400 但条数增加，需要回到开发进程定位：先停止产物服务，在实验目录执行 `PORT=3001 npm run dev` 并重新 attach，再在 sourceLabel 校验和 captures.set 两处分别暂停，找出先发生的动作。`npm start` 没有打开 Inspector，不能直接沿用开发调试连接。若开发入口正常而产物仍没有标签，先核对构建结果与目标进程；若创建有标签而详情没有，追踪保存的对象与响应投影。这里每种故障对应的观察边界不同，重新安装依赖不能代替这些证据。

完成核对和必要修复后，停止仍在运行的实验开发或产物服务，复用第五章的独立目录复制方法，再次构建并交付这一版，运行目录中不带 src 或开发工具。对这个目录重做一条旧请求、一条带空白标签的新请求、一条非法请求，并从另一 cwd 启动核对配置定位。保留各次响应和实际条数变化，才能说明修改确实进入了交付产物。最后停止这个进程，重启后列表仍为空；新字段没有改变内存寿命。

### 完整参考与自己的成果怎样对照

完成独立实现后，可以查看第六章分支 `part-01/chapter-06` 中的 `examples/chapter-06-source.patch`。它只包含针对第五章 `src/server.ts` 的三处改动，不是另一份复制的项目。也可以在配套仓库中读取：

```bash
git show part-01/chapter-06:examples/chapter-06-source.patch
```

补丁中以减号和加号开头的行表示删除与新增，其余上下文用于定位。将它与自己的 `git diff -- src/server.ts` 对照，检查每处差异是否服务于需求；不要因为排版或变量名不同就覆盖自己的实现，也不要对已有成果直接执行 git apply。书中的关键代码与推导仍是理解依据，补丁用于核对完整改动。

如果需要直接运行参考结果，在原代码目录另外创建一份全新的工作目录：

```bash
git worktree add -b practice/chapter-06-reference ../epp-chapter-06-reference part-01/chapter-05
```

确认创建成功后，再进入这个新目录；分支或目录重名时仍选择新的名字，不清理旧成果。在新的第五章工作目录根路径执行 `git status --short`，确认没有待保留改动，才应用补丁：

```bash
git show part-01/chapter-06:examples/chapter-06-source.patch | git apply -
```

应用成功后，按前文执行 nvm use、npm ci、类型检查与构建，再启动并核对请求。若 Git 报补丁不适用，先确认起点确实是第五章、文件没有额外修改，不通过强制覆盖解决。第六章分支中的主服务本身仍是第五章版本；只有这份独立参考目录应用补丁后才具有 sourceLabel 行为。

### 保留实验，回到下一章的起点

在实验目录运行 `git diff -- src/server.ts`，把自己的改动与需求逐项对照。可以在个人实验分支提交已完成的工作，也可以暂时保留未提交文件；它们都留在这个独立目录。停止实验及其独立产物服务，回到同一 shell 先前记录的原目录：

```bash
cd "$main_dir"
git status --short
```

若换过终端，使用自己记录的原目录路径；不要猜路径后执行清理。这里不用 git reset、git clean 或强制切换，也不删除实验目录。继续第七章时，按第七章说明从 `part-01/chapter-05` 主线状态起步，不把个人实验分支合入其中；若原目录还保留自己的其他未完成工作，同样先保留，再在另一工作目录开始下一章。sourceLabel 的规则与字段只属于这次实验，后续正文不会假定它已经存在。

### 用结果回看能力边界

以下结果可以作为自己操作后的核对依据，不必额外建立检查工程：

| 改变的条件 | 应能独立说明或观察的结果 | 对应讲解 |
| --- | --- | --- |
| 新增可选来源标签 | 自行定义缺失与非法值、规范化和写入位置，保持旧请求兼容，并交付验证过的新产物 | 本章 6.6，结合第 2、5 章 |
| 换 cwd、换端口 | 入口、模块与配置各有明确定位基准；有效覆盖成功，错误覆盖在监听前失败 | 第 3、5 章 |
| 发来数字、空白或多字节原文 | 拒绝发生在写入前，原文内容保留，长度单位能解释 | 第 2、5 章及支线 2B |
| 重启或同时启动另一进程 | 状态不共享且重启丢失；资源占用与数据寿命分别解释 | 第 2、3 章 |
| 开发能运行但产物失败 | 依据实际产物区分导入地址、公开入口、资源和依赖缺失 | 第 5 章及支线 5A |
| 计算耗时与外部等待互换 | 能判断阻塞来源，选择分段、执行隔离或异步等待，并说明取消责任 | 第 4 章及其支线 |
| 请求失败或源码断点不命中 | 先确认实际请求和目标进程，再区分提前拒绝、旧产物及源码映射问题 | 第 5 章支线 5B |
| 收到停止信号 | 区分默认终止与接管信号后的收尾责任，不把日志打印当成关闭完成 | 第 3 章支线 3C |

来源标签以自己的实验实现、错误输入后的状态和独立产物为依据；运行条件沿用第五章的目录与实际请求。执行成本、调试与停止信号分别回到对应的有限实验核对，不把实验中的收尾协议宣称为记录服务已经具备的完整优雅关闭。

前五章建立的是运行基础，不是整个后端系统的完成证明。下一篇会把路由、业务、存储与横切处理组织起来，第三篇把数据放到进程之外；之后在并发、权限、后台执行与部署的新约束下，继续复用和扩展这些判断。已有的接口行为与已解释的运行机制会一起延续，迁入框架不意味着它们可以被忘掉。

## 附录：本章必要技术点速查

本章复用前文的实现与命令，并在独立实验中组合输入与类型边界，以下用于回查实践中的判断依据。

| 名称 | 本章用途 | 必要注意点 |
| --- | --- | --- |
| `git show`、`git apply -` | 读取完整参考补丁；在另建的干净第五章目录应用 | 已有独立成果只对照，不直接应用补丁覆盖 |
| `git worktree add -b`、`git worktree list` | 建立隔离实验，并按路径和分支恢复已有实验 | 起点不包含原目录尚未提交的改动；恢复时直接进入已有目录，不重新应用补丁 |
| 可选属性、`in`、`trim()` | 区分未提供、提供非法值与规范化结果 | 静态可选属性不验证输入；按需求决定原值还是转换值进入存储 |
| `PORT` 与工作目录 | 改变启动条件，核对配置与路径基准 | 环境变量属于本次进程；模块相对路径与 cwd 相对路径分别判断 |
| `curl -i`、`-H`、`--data` | 查看状态、响应头并提交有效或非法原文 | 校验错误响应后还要读取列表，确认错误输入没有写入 |
| Buffer、UTF-8 与 UTF-16 代码单元 | 区分请求字节、解码结果与字符串长度 | 字节上限、代码单元数与视觉字符数不是同一个量 |
| Map、进程与重启 | 核对状态归属与寿命 | 独立进程不共享当前 Map，重启不保留内存记录 |
| `npm run build` 与运行目录 | 区分源码、配置快照和可运行产物 | 完整构建成功后再交付，运行副本不会自动跟随源码变化 |
| `async`、`setImmediate()` 与 Worker | 解释等待、分段和执行隔离的不同代价 | 复用第四章实验；根据实际成本来源选择执行方式 |
| 停止信号与资源释放 | 核对停止入口、已有工作和退出条件 | 有限任务示例的收尾机制不等于记录服务已经实现优雅关闭 |
