# 第 6 章 第一篇回顾：把服务搬离开发目录

**阅读前提：请先按顺序读完第 1～5 章，再阅读本章。** 本章回顾并综合应用前五章的内容，操作复用前文示例和第五章建立的运行目录。

**代码起点与完成状态**：沿用第五章代码分支 `part-01/chapter-05`。本章不修改服务实现，通过改变运行条件核对已有能力。

第一篇从三个记录接口出发，最终得到了一份可以检查、构建并独立运行的 Node.js 程序。它能接收英语原文、返回列表和详情，也有清楚的输入拒绝与启动失败行为。数据仍在单个进程的 Map 中，服务停止便会丢失；还没有数据库、身份隔离和长期运行保障。

这些边界决定了下一步该做什么，也决定了现在能独立判断什么。进入 Nest 之前，我们先改变几个真实的运行条件，检验自己的理解能否离开逐行照做。下面使用第五章完成状态 `part-01/chapter-05`，不增加新业务，也不要求额外的测试框架。

**时间参考（估算）**：约 3900 个汉字，包含能力边界与后续学习安排的说明，阅读约 19～24 分钟；复用第五章已经建立的运行目录，新增请求、状态与配置核对另加约 10～15 分钟，不重复计算第五章的构建与复制操作。第四章实验按已有结果回看，不重复计时。

## 6.1 第一篇结束后，怎样理解自己对 Node.js 的掌握

读完前五章，还不能据此认为自己已经全面掌握 Node.js。第一篇建立的是独立编写和运行小型服务所需的基础；随着服务开始持久化数据、处理文件、执行后台任务和长期运行，我们还会继续深入 Node。篇章名称标出了当前集中的技术主题，Node 的学习会贯穿后续实践。

这并不降低第一篇的要求。此时应该能够脱离逐行照抄，建立一个与当前记录服务规模相近的内存服务：安排输入校验、写入和响应的顺序，解释字节怎样成为业务数据；换目录、换端口或重启时，能判断程序的配置、资源和状态发生了什么；请求变慢时，能先区分异步等待与 JavaScript 阻塞；交付时，能把类型检查、模块解析、构建和产物运行串起来。前面的正文和支线负责建立这些理解，下面的实践负责检验它们能否用于改变后的条件。

如果仍然解释不清为何输入非法却已经写进 Map，或为何源码能运行、产物却找不到模块，就需要回到第二章或第五章补足推导。当前承担的基础，应当在当前讲透；不能把这些疑问一律留给后面的框架解决。另一方面，暂时还不会设计完整的服务关闭流程、定位内存持续增长，或者控制大文件传输的资源占用，也不能单凭这些就判断第一篇白读了：这些问题需要在已有基础上加入新的机制和约束。

以停止服务为例。第三章通过有限任务解释了停止接收、等待已有工作与释放资源，已经让我们知道“收到信号”和“可以退出”是不同的时刻。但记录服务仍采用默认信号处理。等服务需要协调正在处理的 HTTP 请求，就要进一步决定停止接受请求的时机、已有请求的等待期限和关闭失败的处理。第十三章会围绕应用生命周期展开；第三篇接入数据库后，再把连接的初始化与释放纳入同一套判断。到独立 Worker 和管理命令出现时，还要分别处理长期工作与一次性工作的结束条件。

文件处理也是如此。第二章针对有明确大小上限的小段 JSON，采用收集字节后统一解码的方式，这让我们看清了消息完整性和字符编码。后面接收文件时，输入规模、处理速度和中断位置都会改变。第 50～51 章会继续展开流、背压、文件处理及失败清理，解释哪些场景可以缓冲，哪些场景需要边读边处理，以及接收方跟不上时怎样控制资源。前面的实现有明确适用范围，后面的内容负责说明条件变化后如何选择。

第四章的执行模型也会继续使用。知道长计算阻塞主线程，是判断延迟的起点；在实际系统中，还需要结合请求耗时、事件循环、内存、连接和任务积压的证据定位瓶颈。第 55～57 章会把这些判断接到已有服务的性能与长期运行上。第五章建立的模块和产物边界，则会在第 54 章的多个程序入口、第 65 章的发布更新，以及第 88 章的共享契约中继续接受检验。

这样安排，是为了让每次深入都有可以操作的对象和需要解决的约束。先理解一个请求和一个进程，再面对多个连接、长期任务和不同运行环境，才能说明新增机制解决了什么、为什么原来的方案需要调整。若在最小服务阶段就把这些实现全部堆进来，读者很容易记住一组配置和清理代码，却无法判断其中哪些由当前需求决定。分阶段展开要保留完整解释，并在后续场景中真正落实。

进入 Nest 以后，这条理解路线仍然继续。框架会组织路由、依赖和生命周期，但请求仍由运行中的程序处理，阻塞仍会影响响应，资源仍有自己的寿命。后续章节会解释框架替我们完成了哪些工作、应用自己仍需承担什么，以及出现问题时怎样回到这些基础定位原因。

因此，本篇结束时，可以用下面的实践核对自己是否已经能独立处理基础运行问题；随着后续篇章推进，再通过文件、后台任务、性能和部署等场景逐步建立完整的开发与维护能力。判断进步的依据，是面对新的条件能解释、选择、实现并排查问题。这里列出的后续章节只是路线，具体机制、实现和结果仍要在对应篇章中展开，不能由一份目录代替。

## 6.2 不先改代码，先说明程序依赖什么

假设同事只拿到你提供的运行目录，要从另一个 cwd 启动服务，使用端口 `3001`，并接收包含中文与表情的原文。你需要说明应交给对方哪些文件、怎样启动、收到不合法输入时应发生什么，以及重启会保留什么。

先独立写下自己的判断，再对照第五章的独立目录操作。不要把整个开发项目连同 `node_modules` 复制过去；那会保留许多本次要排除的偶然条件。也不要提前把数据库或 Docker 加进来，当前问题由已经建立的能力解决。

最小的推导从消费者开始：Node 执行编译后的入口，因此需要产物 JavaScript 与正确的模块分类；配置按模块相对地址读取，因此需要保持 `dist/src/` 与 `dist/config/` 的布局；启动端口由环境提供，因此进程应继承 `PORT=3001`；运行依赖需要按清单与锁文件准备，本章没有第三方运行实现。类型声明与开发执行器不参与普通产物启动。

这说明交付的对象是一组满足关系的文件与环境，不是「某个能双击的 server.js」。如果交付后从另外一个目录失败，要把入口定位、模块定位、配置定位分别拆开看，不能把三个问题都归为相对路径。

## 6.3 用一条有效输入和一条无效输入确认边界

按照第五章建立独立运行目录，并从不同 cwd 用端口 `3001` 启动。在另一个终端发送：

```bash
curl -i http://127.0.0.1:3001/captures \
  -H 'Content-Type: application/json' \
  --data '{"originalText":"  I want to explain this clearly. 我想表达清楚。🙂  "}'
```

核对 `201`、生成的 ID、创建时间和 `Location`，再读取列表与该条详情。返回原文应保留两端空格，中文和表情不应被拆坏。第二章已经解释过 UTF-8 字节与块边界，这里不要求网络恰好按某个字符分块；要知道实现为什么先收集字节、再合并解码，而不是把某一次正常显示当成所有分块情况都正确的证明。

再发送：

```bash
curl -i http://127.0.0.1:3001/captures \
  -H 'Content-Type: application/json' \
  --data '{"originalText":42}'
curl -i http://127.0.0.1:3001/captures \
  -H 'Content-Type: application/json' \
  --data '{"originalText":"   "}'
curl -sS http://127.0.0.1:3001/captures
```

两次错误输入都应返回 `400`，列表只保留此前那条有效记录。能够解释这一结果，要同时说明三个边界：JSON 语法正确不等于字段正确；类型声明不会改变网络输入；拒绝发生在 Map 写入之前。若列表新增了错误记录，即使错误响应看起来正确，写入顺序也仍有问题。

请求体限制是字节数，原文长度限制则沿用 JavaScript UTF-16 代码单元，两者不能互换。把原文全部换成表情后，代码单元数与视觉字符数可能不同。如果业务以后要求按用户看到的字符计数，需要重新定义契约和实现，不能只是把现有常量从 `2000` 改大。当前已能指出规则的位置和单位，并说明修改会影响什么。

## 6.4 把进程寿命、配置寿命与产物寿命分开

停止刚才的进程再启动，列表应为空。把同一份产物同时启动到另一个空闲端口，两边也不会共享 Map。这是两个运行实例分别拥有状态，不是同一个文件只能保存一份内容。数据库篇要解决的正是进程之外的持久状态与一致访问。

另一个容易混淆的现象是配置修改。第五章构建把默认配置复制到 `dist/config/`，因此修改开发目录的默认文件不会自动改变已经交付的副本；即使修改运行目录的配置，当前进程也不会自动重新读取，因为第三章只在启动时加载一次。重新构建、更新文件、重启进程是三个不同的动作，应当知道当前需要哪一个。

将一次启动的 `PORT` 改为 `3001oops`，应在监听前失败并返回非零状态。若另一个进程已经占用端口，应在监听阶段报冲突。这两类错误都使服务不能提供接口，但发生的位置不同：前者是配置不满足程序条件，后者是操作系统资源申请失败。定位时应从诊断信息沿对应阶段检查，而不是先修改请求处理代码。

第五章还让构建先清理旧产物再编译。遇到类型错误时，不能把上一版程序仍能启动当成新代码已经通过。把失败构建的输出交给同事也不成立：应当在构建完整成功后再建立运行目录。这是交付事实与开发状态之间的边界，后面的发布篇会在此基础上加入版本与回退。

## 6.5 需求变成批量处理时，先判断成本再选执行方式

现在暂时离开文件布局。假设有一项新需求：对一批原文做分析，单次分析是约半秒的纯 JavaScript 计算，希望期间查看列表仍能获得响应。不急着给 EPP 添加一个演示路由，先用第四章的 `/block`、`/slice` 与 Worker 例子说明可选方案为什么不同。

把函数写成 `async` 不能把半秒计算搬离主线程。在循环里 `await Promise.resolve()` 也不能保证 I/O 有机会推进，因为连续的微任务仍可能占住处理时机。分段配合 `setImmediate()` 让事件循环在片段之间推进，可以改善交错响应，但没有减少总计算量，也没有把计算并行到另一个核。

如果确实需要把计算移出主线程，Worker 可以提供另一个 JavaScript 执行环境，同时带来输入复制、结果消息、失败与退出的责任。每个请求随手创建一个 Worker 也不能自动解决容量问题；工作到达过快仍然会争用 CPU 与内存。当前有限示例能支持执行位置的判断，持续服务的线程复用与容量安排在后面的性能章节继续展开。

再把需求改为等待外部 I/O，判断又变了：异步等待本身不需要另一个 JavaScript Worker 来「帮忙等」。应关注等待是否有期限、真正的操作是否支持取消、失败由谁接住，以及已经接受的工作如何收尾。第四章的 `Promise.race()` 与合作取消实验已经给出了这种差别。

这里没有增加一个大作业。目标是面对改变后的成本来源，能够解释为什么选择不同，不把「后台」「异步」「多线程」当成可以互换的词。如果解释卡住，返回第四章对应的执行实验；若只会列出工具名称而无法预测探针与结果顺序，就还需要对照实际输出重建判断。

## 6.6 如何确认这一篇已经形成可迁移的能力

以下结果可以作为自己操作后的核对依据，不必额外建立检查工程：

| 改变的条件 | 应能独立说明或观察的结果 | 对应讲解 |
| --- | --- | --- |
| 换 cwd、换端口 | 入口、模块与配置各有明确定位基准；有效覆盖成功，错误覆盖在监听前失败 | 第 3、5 章 |
| 发来数字、空白或多字节原文 | 拒绝发生在写入前，原文内容保留，长度单位能解释 | 第 2、5 章及支线 2B |
| 重启或同时启动另一进程 | 状态不共享且重启丢失；资源占用与数据寿命分别解释 | 第 2、3 章 |
| 开发能运行但产物失败 | 依据实际产物区分导入地址、公开入口、资源和依赖缺失 | 第 5 章及支线 5A |
| 计算耗时与外部等待互换 | 能判断阻塞来源，选择分段、执行隔离或异步等待，并说明取消责任 | 第 4 章及其支线 |
| 收到停止信号 | 区分默认终止与接管信号后的收尾责任，不把日志打印当成关闭完成 | 第 3 章支线 3C |

前四行以第五章的独立目录和实际请求为核对对象；后两行复用已运行过的有限实验，不把实验中的收尾协议宣称为记录服务已经具备的完整优雅关闭。

前五章建立的是运行基础，不是整个后端系统的完成证明。下一篇会把路由、业务、存储与横切处理组织起来，第三篇把数据放到进程之外；之后在并发、权限、后台执行与部署的新约束下，继续复用和扩展这些判断。已有的接口行为与已解释的运行机制会一起延续，迁入框架不意味着它们可以被忘掉。

| 名称 | 本章用途 | 必要注意点 |
| --- | --- | --- |

| 停止信号与资源释放 | 核对停止入口、已有工作和退出条件 | 有限任务示例的收尾机制不等于记录服务已经实现优雅关闭 |
