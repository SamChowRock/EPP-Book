# 支线 2A：Node 怎样接住一个 HTTP 请求

正文第 2.2 节使用 `createServer` 建立了 HTTP 服务。现在沿这条支线把它背后的执行过程连起来：JavaScript 是谁执行的，请求是谁接收的，为什么最后会调用我们提供的函数。

## 执行 JavaScript 与提供运行能力

浏览器里的 JavaScript 可以创建对象、调用函数、操作 DOM，还能发送请求。这几件事来自不同层次。对象与函数属于语言；让代码实际执行，需要 JavaScript 引擎；DOM、网络接口等能力则由宿主环境提供。因而，同样使用 JavaScript，不意味着换一个运行环境后仍能访问同一组对象。

Node 使用 V8 执行 JavaScript，并提供访问文件、网络、进程等资源的接口。执行 `node src/server.js` 时，操作系统启动 Node 程序，Node 加载入口模块及其依赖，再执行我们的代码。此时没有网页，也没有浏览器给当前程序创建的 `document`。程序能够建立 HTTP 服务，是因为 Node 提供了相应能力，而不是因为 JavaScript 的函数语法本身能够监听网络。

这也解释了正文中的 `node:http`。前缀表明它是 Node 内置模块，安装 Node 时就已经具备，无需通过 npm 再下载一个同名包。`createServer` 是这个模块提供的 JavaScript 接口，它往下连接着 HTTP 解析、网络 I/O 等实现。业务代码可以调用它，通常不用自己处理底层的系统调用。

以后我们会遇到另一种包：它通过 npm 安装，却仍然需要 Node 才能运行。包组织和复用代码，运行时提供执行环境，两者不处在同一个层次。因此，只有项目依赖版本相同，而 Node 版本不同，依然可能出现运行差异；这就是正文同时保留锁文件和 `.nvmrc` 的原因。

## 创建服务对象之后，为什么还要 listen

回看正文中的两步：

```javascript
const server = createServer(handleRequest);
server.listen(3000, '127.0.0.1');
```

这段只摘出调用关系；完整的请求错误处理仍按正文实现。第一步创建 HTTP 服务对象，并注册收到请求后执行的函数。第二步才申请监听指定的地址和端口。仅仅声明“收到请求后调用谁”，并不会让操作系统自动把某个端口交给这个程序。

地址决定监听哪一个网络入口，端口帮助区分同一主机上的服务。本章的 `127.0.0.1` 指向本机回环接口，所以客户端也在本机调用。端口 `3000` 是我们选定的入口编号，它没有“记录服务”的业务含义；把它改为 `3001`，业务路由可以不变，但调用地址必须一起改变。

申请监听可能失败，例如已有进程占用了同一个监听地址。失败发生在请求处理之前，此时没有一份用户请求可供回应。所以正文在 `server` 上监听启动错误，而不是在创建记录的逻辑里返回一个 HTTP 错误。

监听成功后，服务进程可以等待连接。等待由运行时与操作系统协作完成，不需要在 JavaScript 中写一个 `while (true)` 不断问“有请求了吗”。一个不让出执行机会的 JavaScript 循环，反而会妨碍请求回调得到执行。第四章会用并发请求进一步观察这种区别。

## 网络交付的是字节，谁知道它是一份请求

本章使用的 HTTP/1.1 通常运行在 TCP 连接上。TCP 提供有序的字节传输，交给接收方的字节批次没有 JavaScript 对象的边界。客户端一次发送完整 JSON，并不意味着服务端一次读取就会拿到相同大小的一块数据。

HTTP 则在字节之上定义消息的结构，包括方法、请求目标、头部和消息体。Node 的 HTTP 解析器按这些规则识别消息。例如，请求体的结束可以通过 `Content-Length` 指定的长度或分块传输编码等规则确定；我们无需靠“暂时没有新的数据”猜测它结束了。

这里有三个容易混在一起的边界：TCP 连接、一次 HTTP 消息，以及一次 `data` 事件交付的块。一个连接可以承载先后多次 HTTP 请求；一份 HTTP 请求体可以通过多次 `data` 交付；HTTP 的分块传输编码也不能直接等同于 JavaScript 中每次收到的块。

因而，正文等待请求流的 `end`，是利用 HTTP 模块已经识别出的这份消息体结束信号，而不是等待整个连接断开。如果必须关闭连接才能知道第一份请求何时结束，就无法在同一条连接上继续正常处理下一份请求。

## 请求到达后，我们的函数怎样参与

HTTP 模块解析出请求头后，便能提供方法、路径和头部等信息，并触发请求处理。传给回调的 `request` 还负责提供后续请求体数据。它不是已经填完所有业务字段的对象，而是一份正在读取的请求的接口。

例如，看到 `GET /captures`，程序可以直接读取 Map 并响应；看到 `POST /captures`，程序需要继续接收内容；看到不支持的媒体类型，程序可以在解析业务字段之前拒绝。把回调提前到这个时刻，保留了这些处理选择。

回调只在运行时安排它执行时才运行。注册 `request.on('data', listener)` 是留下“数据到来时怎样处理”的规则，不会在注册的那一行就立刻得到全部数据。因此，把 `JSON.parse` 写在注册代码之后，也不意味着它会等待所有 `data` 回调完成。正文用 Promise 表达“读完且解析成功”的完成条件，再让路由 `await` 这个结果。

同理，回调中的 `return` 只结束这次 JavaScript 函数调用。HTTP 模块没有把任意返回值当作响应体的约定。要让客户端收到结果，我们通过 `response.writeHead` 和 `response.end` 明确提供状态、头部与内容。

`response.end` 表示应用不再向这次响应追加数据。运行时还要把数据交给底层连接，客户端也还要接收和处理，所以执行了 `end` 并不等于已经得到客户端确认。正文断点中“记录已写入，客户端还在等待”的现象，就发生在业务状态与网络交付的这段距离中。

## 回到 EPP：错误应该沿哪一层查

现在再看几个现象，就能缩小排查范围。服务连监听都没有成功，要查地址、端口和启动环境。收到了 `404`，说明已经有 HTTP 服务回应，再查请求落到哪个路径。收到了 JSON 解析错误，要查实际请求体和读取过程。响应创建成功却查不到旧记录，还要查服务是否换了进程，以及状态存在哪里。

这些判断适用于其他业务。把英语记录换成订单、笔记或设备上报，运行时接收字节、HTTP 解析消息、应用解释内容的分工仍然存在。改变的是业务规则，以及我们在这些接口之上组织代码的方式。

| --- | --- |
| V8 与 Node | 前者执行 JavaScript，后者提供运行环境及资源访问能力 |
