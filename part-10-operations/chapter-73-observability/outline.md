# 第 73 章　通知已经积压，怎样在人来报障之前发现

**章节提要**　第 72 章的一条密码重置通知能从后台走到用户的浏览器。今天 API 仍能登录，另一笔通知却迟迟没有入箱。接班人希望在用户催问之前收到告警，也要知道什么时候能结案。

## 73.1 从成功样本找出还缺哪段证据

用上一章留下的用户、请求时间、任务 ID 和通知 ID 对齐一轮成功样本。任务与收件箱可以按相同事件 ID 精确连接；同一收件人可能有多次申请，只靠邮箱与相近时间无法把某次请求逐笔归给某次投递。原 nginx 配置关闭了访问日志，Worker 与 API 分属不同进程，请求上下文不会自动传过去。需要跨层关联时，在代理记录上游返回的请求 ID、状态和耗时，在创建任务处补一条含请求 ID 与任务 ID 的脱敏记录；再发两笔区分得开的操作验证。构建版本从实际运行的制品或镜像摘要取。不要记录 Cookie、正文、令牌或带签名的完整 URL。既有旧记录缺少关联时就注明能追到哪一步。

## 73.2 定义一笔通知从何时算起等待

停下练习副本的通知 Worker，保持 API 在线，按上一章产生一笔新的 password-reset 任务。从独立观察连接按其 ID 读 created_at、expires_at、status，并与收件箱对照。通知入队后即可消费，从 created_at 开始等待；expires_at 是业务失效时间。积压查询统计仍 pending 的通知并读出最早创建时刻，再区分仍有效与已过期的数量。过期任务在后续消费时可能成为 obsolete，用户不会收到那一条。用一个有效期内的练习样本做本轮恢复。

## 73.3 让持续积压发出告警，恢复后再解除

先约定允许等待多久、采样间隔、连续几次超限才告警。用一个独立于通知 Worker 的定时检查，从只读连接取任务数与最早等待时长，向值班人能实际收到的独立接收处发送本次告警；数据库查询失败单独记录为采样失败。保留上一轮告警状态，持续超限只开一次，首次恢复时发送解除。同一套规则分别观察短暂积压和持续停工，记下采样值、实际收件时刻以及触发差异。空队列只能证明当时无人等待。现有 Worker 只在启动时报告 ready，空轮会休眠；若另需检测空闲 Worker 是否持续巡视，须先增加有时间戳的巡视证据并验证停止时会变旧。

## 73.4 判定这张告警单能否关闭

恢复通知 Worker，按原任务 ID 检查 pending 到 done、同 ID 入箱，再用原账号读到这一行。等检查器发出解除，比较业务恢复、采样恢复与值班人收到解除三个时刻。若积压已消退但任务已过期，记录该笔未实现的承诺并单独处置。已有邮件 unknown 时沿用第 53、57 章的投递核查；attempts 只保存累计次数，每一次 SMTP 尝试的结果需另有记录。需要跨轮转追查时，分别按轮转前后两笔请求的 ID 检索 journal，核对历史日志能保留多久。在 Mac 部署的读者可复用[70B 的日志对照](../../part-09-deployment/chapter-70-target-environment/side-02-macos-supervision.md)。多机检索或容器值班确有需要，再比较集中采集、Pino 或 Dozzle 的读取权限与脱敏范围。
