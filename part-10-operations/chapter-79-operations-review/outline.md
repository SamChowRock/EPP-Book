# 第 79 章　运维回顾：接手一次原因未知的报障

**章节提要**　上一章交接了一套恢复后的 EPP。此时只向接班人提供用户报障、请求时间和可使用的管理入口。先独立决定取什么证据，再展开故障设置。

## 79.1 接受一张未揭晓原因的报障单

给接班人的报障只有三句话：“上午发布以后，我还能看到旧素材，刚保存的那一条也在。旧头像能打开，刚选的照片却传不上去。另一位同事说她能换。”给出两笔请求的时间和练习账号，让接班人先自己决定还需要哪个样本。

## 79.2 用业务证据排除一个处置方案

保留刚创建的素材 ID、旧头像的实际字节和失败请求。问两位使用者各要一份可公开的练习图片，把两份输入都通过同一入口发送；再保持同一份输入，改变一个经过的组件。接班人要凭取得的结果决定查入口、应用还是持久数据，并指出恢复上午的数据库会丢掉哪一条仍然合法的写入。

## 79.3 在副本执行并从用户入口验收

在事故副本按选定方案处置，从用户入口核对旧记录、头像、待办和权限。容器路线另核对网络、卷与镜像版本。

## 79.4 改变条件后重新判断

<details>
<summary>给布置练习的人：接班人完成第一次取证后再展开</summary>

在独立入口副本将第 72 章的请求体限制恢复到 nginx 默认值，预检、重载。给一人一张小 PNG，给另一人一张 1～2 MiB、符合原像素限制的有效 PNG。两张图片直达同一上游均可处理，经入口只有较大者失败。在录入答案前，请接班人解释哪一层发出了响应，如何验证修复后保留了发布后的那条素材。

第二轮恢复正确入口，按 71A 的方法仅把 API 工作目录指向只读 release。旧头像仍能读取，这回连小图预览也失败。请接班人用失败响应、请求 ID 和日志决定是否沿用上一轮的处置。两轮都使用专用数据和入口，结束后还原工作目录与代理设置。

</details>

## 79.5 交还服务

交接已恢复的业务、仍有疑问的记录、继续开放的条件。写清哪条新证据会让你改变当前决定。
