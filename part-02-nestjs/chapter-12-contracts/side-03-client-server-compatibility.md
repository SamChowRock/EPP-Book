# 支线 12C：服务升级时，旧页面还能告诉用户哪里填错了吗

设想周一上午，用户打开了素材编辑页，一直没有刷新。午休时后端从第十一章升级到第十二章。下午她保存一段合法文字，页面照常工作。隔壁开发者却说：“错误提示空了。”两件事完全可以同时发生。要判断一次接口变更的影响，先问清楚：谁产生这份数据，谁要读取它，读完以后准备做什么？

读完 12.3、12.4 后，用两个已有的配套版本回答这个问题。阅读约 15～19 分钟，对照两次运行和保存请求另加约 15～20 分钟。首次准备依赖另计。

## 把一张“接口正常”的截图拆成两个方向

输入从页面流向服务。旧页面发出的 `{"originalText":"我的素材"}` 能被新服务接受，这说明旧页面仍能提交这个动作。反过来，如果新页面多发了一个字段，第十二章的创建 Schema 会丢弃未知字段，只把解析出的 originalText 交给后续逻辑。调用能成功，但如果新页面承诺“我顺便帮你保存分类”，就还需要按创建响应的 Location 读回分类，才能告诉用户保存成功。接受这段 JSON 和兑现其中每项业务意图，是两个不同的问题。

输出的方向倒过来。服务产生一个对象，页面要从里面取值。即便按钮仍收到预期的 HTTP 状态，只要页面依赖的字段消失，它下一步就可能做错。只看两个版本的接口字段各有几个，推不出是否兼容。应当把调用方实际发送的样本、实际读取的字段以及读取后的动作摆在一起。

## 留住同一份请求，只换接收它的版本

准备第十一章和第十二章两个完成快照。如果已有两份配套目录，可直接使用。若只有当前跟写目录，在 VS Code 集成终端切到存放学习项目的父目录，用两个尚未使用的目录名取得配套：

```bash
git clone --single-branch --branch part-02/chapter-11 https://github.com/SamChowRock/epp-public.git epp-client-compat-11
git clone --single-branch --branch part-02/chapter-12 https://github.com/SamChowRock/epp-public.git epp-client-compat-12
```

在 VS Code 用两个窗口分别打开这两份目录。在两个窗口各自的集成终端执行 `nvm use`、`npm ci`、`npm run check`。第一份运行 `PORT=3011 npm start`，第二份运行 `PORT=3012 npm start`，等终端分别显示各自监听的本机地址。这里使用两份刚构建的产物，便于保持它们同时在线，也能避开两个开发监听器共用调试端口的问题。两个进程各有自己的空存储。

在 Postman 新建一个请求，方法选 POST，Body 选 raw 和 JSON，确认请求头 Content-Type 为 application/json。地址先填 `http://127.0.0.1:3011/captures`，正文填 `{"originalText":7}`。保留请求的副本，只把端口改为 3012。分别 Send，展开响应的 Headers 和 Body。把两份错误正文和 Content-Type 分别复制到笔记里，标明端口，供后面和成功响应并排查看。数值 7 是合法 JSON，可以让两个版本都走到字段或业务检查。如果改成残缺的 JSON，就换了一条失败路径。

| 从哪里读 | 十一章服务，3011 | 十二章服务，3012 |
| --- | --- | --- |
| HTTP 状态 | 400 | 400 |
| 响应 Content-Type 的媒体类型 | application/json | application/problem+json |
| 哪里有给人看的说明 | error 字符串 | detail 字符串 |
| 页面怎样定位应标出的字段 | 正文没有结构化的字段路径 | code 为 VALIDATION_ERROR，issues 中的 path 指向 originalText |

媒体类型后可以带字符集参数。比对媒体类型时取分号前的部分。接着把两个请求的正文都换成 `{"originalText":"周一的素材"}` 再发一次，分别从各自的创建响应抄下 Location，仍在原端口按这个地址 GET。两个版本都应返回 201 后能读回同一笔原文；两份服务独立分配身份，不要拿两边的 ID 相等当作通过条件。

## 把两份失败响应分别交给两代页面

现在回到刚才的数字输入。旧页面的渲染规则很短：状态为 400 时将 `body.error` 作为提示。设想新版页面严格按本章文档实现：它识别 application/problem+json，从 `body.detail` 取说明，若有 issues 再标字段。先遮住下表后两列，单凭手里的两份响应，逐格说出页面能展示什么。

| 页面实际需要什么 | 对接十一章服务 | 对接十二章服务 |
| --- | --- | --- |
| 旧页面只读 error | 能显示旧提示 | 找不到 error，单靠该字段无法显示原因 |
| 新页面只识别 Problem | 收到旧媒体类型，不能进入 Problem 分支 | 能显示 detail，并根据本次 issues 标出原文 |
| 过渡页面同时理解两种格式 | 显示 error，保留普通表单提示 | 显示 detail，有可用的字段路径时再定位 |

可以在 Postman 的响应 Body 里直接查找表中字段。左下格不能从英文错误字符串里反推出可靠的字段路径，翻译或措辞调整就会让这种推断失效。右下格也不能约定每种 Problem 都有 issues：换成第十二章的 GET，访问一个不存在的素材 ID，会得到 404、CAPTURE_NOT_FOUND 和 detail，此时没有表单字段需要标红。面对一个没见过的 code，页面仍可以根据状态和可展示的说明保留用户输入；判断结构或内容类型失败时，普通的“保存失败，请保留原文”也比把整份异常当成字段错误更准确。

这个表可以直接用来判断发版顺序。如果先发只认 Problem 的页面，旧服务还在线，左边就有窗口；若先发新服务，一直打开的旧页面会落入右上格。先发能读两种格式的页面可以覆盖已更新的客户端，但不会自动更新周一早晨已经打开的标签页。如果业务承诺这批页面仍能显示具体原因，就得让旧表示继续可用一段时间，或让客户端在切换前完成更新。要不要安排双版本接口、协商表示或明确提示刷新，取决于你能控制哪些客户端、要保留旧体验多久；把两个发布动作排在同一分钟并不能回答这个问题。

## 换一个字段，重新判断谁应先升级

产品希望以后可以传可选的 `category`。用 3012 发送 `{"originalText":"留个分类","category":"摘录"}`，沿本次 Location 读回。两次响应里都能找到原文，都没有 category。回编辑器看 `src/capture-contract.ts` 的 CreateCaptureSchema，再看 Controller 实际传给 Service 的参数：当前写入路径只采纳原文。若页面只是把 category 当作可忽略的提示，旧服务或许仍能满足动作；若页面已向用户承诺保存分类，这个组合已经失败，哪怕状态是 201。

再从响应方向试想相反的改动：服务开始公开一个可选字段，旧页面只读 originalText，通常可以继续展示。另一个旧客户端若执行“只准这三个键出现”的严格响应检查，同一改动就会触发拒绝。所以下次有人说“只是加了可选字段”，先取得一个旧调用方，弄清它在写还是在读、如何处理陌生字段、最终要完成什么动作。没有旧客户端源码时，至少把这些假设列出来，用真实响应交给当时的客户端验一次。新 Swagger 页面能发出成功请求，只覆盖新版说明所描述的一种组合。

做完后在两个终端各按 Ctrl+C。回到 12.4 的 OpenAPI 文档，定位 POST 的 201、400、Location 和两种响应媒体类型。现在你能从文档写出一个新调用者，也能指出仅凭这份文档无法回答的那个旧页面问题。

## 附录：本支线必要技术点速查

| 判断 | 最小对照 |
| --- | --- |
| 请求还能被接受 | 将旧客户端实际发送的输入交给新服务，并核对读回的业务结果 |
| 响应还能被消费 | 将新服务的成功和错误样本分别交给旧客户端，观察其下一步动作 |
| 两个版本交错 | 分别检查旧页／新服务与新页／旧服务，确认谁先上线会影响哪一格 |
| 字段是可选的 | 分别检查缺失时是否还能工作、出现时是否被拒绝、被忽略是否仍满足业务 |
