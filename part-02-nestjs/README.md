# 第二篇 用 Nest 组织一个可持续扩展的服务

第一篇已经建立了一个内存版记录服务：我们知道请求如何被读取、原文何时写入、错误怎样返回，也能检查、构建并运行它。现在继续使用这三个接口，把关注点从单个程序的运行移到职责与依赖的组织上。接口增长以后，输入变化、业务规则变化和存储替换应有可以解释的落点。

这一篇先比较普通 JavaScript 手动组装、Express 与 Nest 分别承担什么，再根据记录服务后续的业务协作与多种入口解释框架选择。我们先从已有代码抽出业务操作、手动传入依赖，然后让 Nest 负责相应的组装和路由注册。随后沿实际请求展开 Controller、Provider 与 Module，建立可信的输入输出契约，处理重复的错误转换，并把配置、日志与资源生命周期接到应用中。框架接手了一部分工作，但 Node 的字节、模块、异步和进程机制仍在下面运行；出现问题时，需要知道该沿哪一层追踪。

**阅读路径**：核心实践，按第 8～14 章推进，再进入第 15 章回顾。完整篇章目录见[全书目录](../README.md#第二篇-用-nest-组织一个可持续扩展的服务)。

**起点**：先完成第一篇第 1～7 章。项目沿用第六章的 TypeScript 服务与构建布局，第七章的来源标签只在隔离实践中实现，主线接口保持第六章状态；原有接口包括新增、列表和详情。

**本篇结果**：能够根据需求判断框架的收益与成本，组织同一个 Nest 服务，解释请求、业务、依赖与模块的边界，维护输入输出和错误契约，并沿配置、日志及资源生命周期定位问题。

**阶段边界**：保留进程内存存储，不新增数据库表、迁移、登录或后台任务。第十章准备可替换的存储边界，第三篇才接入 PostgreSQL 并保留重启后的记录。本篇的框架改造持续核对已有接口行为；第十二章明确升级错误响应为 Problem Details，成功响应与既有业务规则保持。

学习默认运行 `npm run dev`，VS Code 连接 `EPP: attach to npm run dev`；保存后自动编译、重启并尝试重连。生产使用 `npm run build` 生成产物，再以 `npm start` 运行，不开启 Inspector 或文件监听。重启会清空当前 Map，详细配置与产物交付沿用第六章。

贯穿本篇的一条线索是创建响应里的素材 ID。第 8、9 章先让旧客户端在新框架上创建素材，再沿 Location 取回**同一个 ID**；第 10、11 章换一个入口，判断它是否拿到了同一份存储，而不只是另一份类型相同的对象。独立实验与主服务不共享进程，隔天重新启动时要重新保存本次运行的 ID，不能把空列表直接归咎于模块接线。

第 12、13 章可以在“同为 400 的两个请求，已经知道它们分别停在哪里”之后暂停。第 14 章的停止实验则适合留一段连续时间：先在同一进程接下一份工作，再观察停止接收、工作完成和资源释放，不把三次独立启动的日志拼成一次关闭。第 15 章最后只改一条创建规则和一个存储实现，用旧记录、直接调用与 HTTP 请求分别验证哪些承诺变了、哪些不该变。
