# 第二篇 用 Nest 组织一个可持续扩展的服务

第一篇已经建立了一个内存版记录服务：我们知道请求如何被读取、原文何时写入、错误怎样返回，也能检查、构建并运行它。现在继续使用这三个接口，把关注点从单个程序的运行移到职责与依赖的组织上。接口增长以后，输入变化、业务规则变化和存储替换应有可以解释的落点。

这一篇先比较普通 JavaScript 手动组装、Express 与 Nest 分别承担什么，再根据 EPP 后续的业务协作与多种入口解释框架选择。我们先从已有代码抽出业务操作、手动传入依赖，然后让 Nest 负责相应的组装和路由注册。随后沿实际请求展开 Controller、Provider 与 Module，建立可信的输入输出契约，处理重复的错误转换，并把配置、日志与资源生命周期接到应用中。框架接手了一部分工作，但 Node 的字节、模块、异步和进程机制仍在下面运行；出现问题时，需要知道该沿哪一层追踪。

**阅读路径**：核心实践，按第 7～13 章推进，再进入第 14 章回顾。完整小节编排见[全书目录](../README.md#第二篇-用-nest-组织一个可持续扩展的服务)。

**起点**：先完成第一篇第 1～6 章。项目沿用第五章的 TypeScript 服务与构建布局，第六章没有新增代码；原有接口包括新增、列表和详情。

**本篇结果**：能够根据需求判断框架的收益与成本，组织同一个 Nest 服务，解释请求、业务、依赖与模块的边界，维护输入输出和错误契约，并沿配置、日志及资源生命周期定位问题。各章依次建立这些能力，不把第七章能启动应用等同于已经掌握整套 Nest 机制。

**阶段边界**：保留进程内存存储，不新增数据库表、迁移、登录或后台任务。第九章准备可替换的存储边界，第三篇才接入 PostgreSQL 并保留重启后的记录。本篇的框架改造持续核对已有接口行为。
