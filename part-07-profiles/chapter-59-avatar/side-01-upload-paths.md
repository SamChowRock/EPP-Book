# 支线 59A　如果上传变成 200 MiB，还要让 API 接文件吗？

同一个资料页多了一项需求：用户可以上传长达 200 MiB 的介绍视频，手机切换网络后还要能继续。沿用本章的做法，把 `maxBytes` 乘以一百，会发生什么？一条上行吞吐为每秒 1 MiB 的连接，即使完全没有丢包，光传输就约需 200 秒。保留十秒期限会误拒正常用户；把期限延长到数分钟，两条慢连接又能长时间占尽本进程的两个位置。更麻烦的是，当前服务接完会把整个文件读成 Buffer，再让库处理，两笔就可能持有约 400 MiB 的压缩输入。

阅读约 9～13 分钟。

## 小文件是否一定要先落盘

若需求仍是 2 MiB 的头像，只有两个并发位置，也可以直接把压缩输入收进固定大小的 Buffer：先取得名额，再分配 2 MiB，逐块检查剩余空间并复制，结束时只把已写区域交给解码器。两席为输入区预留 4 MiB，即使发送方把一个文件拆成很多小块，也不会积累一个很长的 Buffer 引用数组。这样少一次写盘和读盘，进程结束时无须找临时文件；传得很慢的用户会一直占着预留内存与名额，解码开销仍然存在。若机器临时盘特别小而这个内存预算付得起，这是合理选择。

本章采用私有暂存目录，慢传阶段只向文件流有节制地送数据，文件收齐后才为解码读入有界输入。代价是需要可写卷、足够的剩余空间，以及突然退出后的清理办法。API 容器若用只读文件系统，这一点会直接影响部署。换成只在内存里排队的「流式接口」也要核对库的实现：接一个 Writable 并不能证明最终消费者不会攒齐所有输入。选哪个方案，先把连接数、每笔最大的压缩输入、解码开销和临时盘预算分开算。

## 多字段表单解决的是另一件事

如果客户端要在同一次表单提交里带上一张图、裁剪焦点和辅助说明，可以用 multipart/form-data。请求的 Content-Type 带 boundary；各部分有自己的字段名和头。服务端需要用能按流解析边界的库，限制总请求、单文件、字段数、文件数和文本字段长度。只给单个文件设上限，仍可能被很多文本字段或多个各自合规的文件撑大。文件部分的声明类型与文件名仍由客户端控制，提取出字节后要继续执行图片检查。[RFC 7578](https://datatracker.ietf.org/doc/html/rfc7578#section-4)

把两个字段装进同一个 HTTP 信封也不会得到跨系统事务。假设昵称修改会扣一次额度，头像准备发布时又失败了，这时昵称应不应该生效？如果用户要先预览直到满意，继续让预览与资料保存各有独立请求会更自然；如果产品真要统一确认，应先定义一次确认究竟提交哪些数据库事实、未发布文件如何回收，再选择表单封装。

## 大文件把哪些工作移出 API

回到视频。可让 API 负责授权与记录尝试，客户端向存储端发送内容，处理进程从私有候选区读取输入。由此省下应用转发大文件的连接、带宽和临时盘；传输中断、分片对账、候选区的占用、回收及费用控制仍要有负责人。若存储端支持多段上传，可以把 upload ID 和已经确认的分段记下来，恢复时先向接收端核对，补齐缺段并完成合并。只凭手机显示「发到了第七段」无法判断第七段的确认是还没发送还是应答在路上丢了。长期未完成的上传也要按有效期作废并清理已经占用的各段。

授权应只涵盖本次尝试的目标、允许的操作与期限，私有候选不可被其他用户直接读。以 Amazon S3 为例，普通预签名 PUT 在有效期内可能被重复使用，同键上传会替换内容。若校验器刚验证完 A，客户端又用仍有效的链接把同键换成 B，随后直接发布这个可写键就会让 B 绕过校验。若存储支持版本，可让校验、发布引用和以后每一次读取都明确指向同一版本号。只在校验时读 A 的版本，资料里只存 key，后来按 key 读取仍可能得到 B。另一种做法是验证后把**同一份已验证字节**生成到客户端无写权限的新键，仅发布后者。给每次尝试独有的键可以隔开两次尝试，却无法使同一尝试的可写键自动变成只写一次。[Amazon S3 预签名 URL](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

再改变一个条件：客户端断线时服务端已经收齐文件，只是没把响应送回。对本章临时预览，直接重做只多花一次计算，资料没有改变。若是按完成的视频转码收费，客户端应先查尝试状态，服务端对同一次确认、计费和任务入队建立稳定身份与回执。用前篇已经见过的办法，把「上传完毕」「校验已通过」「允许这位用户发布」「已计费」分开记录。第 60 章回到小头像，只引入私有对象与数据库发布需要的事实，大文件分片不会成为跟做前提。

## 附录：必要技术点速查

| 条件变化 | 需要重新决定的边界 |
| --- | --- |
| 输入很小、可为每个名额预留内存 | 最多有多少输入 Buffer，解码预算另算 |
| 同一表单里有多个部分 | 边界解析、总量和数量限制、失败时哪些字段可一起提交 |
| 长传输要跨网络恢复 | 存储端确认的分段、尝试有效期、未完成上传的回收 |
| 接收端允许原键再次写入 | 证明发布的是哪一份通过校验的内容 |
| 成功处理会产生费用 | 先查尝试与回执，再决定是否发起新任务 |
