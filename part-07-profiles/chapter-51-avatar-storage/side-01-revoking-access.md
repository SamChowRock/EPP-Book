# 支线 51A　如果隐藏后必须立即拒绝读图

产品经理补了一句：「用户关掉头像展示，其他人再点刚才的图片链接也要看不到。」正文里的 B 可以在关闭之前拿一个 30 秒地址，关闭后一秒才第一次下载。应用这时已经拒绝给 B 新签地址，存储服务仍然会把图交给它。把有效期改成三秒能缩短窗口，仍然回答不了这一次请求该不该成功。

阅读约 9～13 分钟。

## 谁处理下一次读取，谁才有机会撤销

主线里有两个时刻。B 先向 API 表明自己是谁，API 根据当时的资格签发读取能力。随后客户端直接向存储服务出示这份能力，存储端检查签名、方法、键和时间。它无需认识 EPP 的账号，也不知道主人半秒之前在 PostgreSQL 里改了开关。这正是它能独立服务字节的原因，也是后续读图仍有授权窗口的原因。

如果用户能接受最多一个短窗口，继续使用按对象、按操作、寿命有限的预签名地址即可。界面收紧设置后立即停止发新地址；到期的客户端应重新向业务 API 申请，让变化有机会生效。不要把“公有 URL 很难猜”和“私有对象由有期限的能力授权”混成同一种设计。有人复制前一种地址后，没有一个可说明的授权截止时刻。

如果要求是「隐藏提交之后才开始的新访问必须被拒」，可以把浏览器访问地址固定为受保护的应用路由。每次打开该路由，服务端重新检查当前会话、目标状态与展示设置，获准后以应用身份从私有桶读对象，并把字节流交给客户端。底层对象不再另发可直接使用的地址；如果应用只做权限检查，然后 302 到仍可独立重放的预签名 URL，B 仍可绕开下一次应用检查。换成反向代理的内部取件机制，也要确保外部用户无法直接访问内部入口。

这一选择把带宽、背压、范围请求、客户端断开和错误收尾带回受控读取路径。小头像可以沿第 50 章的有限响应和排空策略思考；换成大视频，服务一百条慢读连接的成本就不同了。可让专门的网关处理字节，每次向授权服务查询或验证可撤销的授权版本。只要在网关缓存「B 可以看」，就要算清这份缓存的有效期及失效传播时间；做不到及时撤销时，承诺也要写成有界窗口。

## 哪一条时间线才算「立即」

考虑一笔已经在发送的图片。B 的请求先在数据库获得读取资格，主人随后提交隐藏，最后一个响应分块再过一毫秒才到达 B。逐请求鉴权可以阻止下一笔请求，无法让已经交给内核甚至已经显示的像素倒流。如果业务真正要求中断进行中的长传输，需要额外维护正在发送的连接、广播撤销并让各节点停止输出，还得说明已经在途及缓冲的部分如何计算。对多数小头像，界面承诺「保存后新请求受新设置约束」有更容易复核的边界。

缓存也参与时间线。按 URL 共享缓存私有对象，命中时如果不再经过授权，源站返回 403 也救不了这一跳。可先禁止共享缓存，再评估受控缓存：缓存的可以是按不可变版本分隔的**字节**，而每一次把字节交给请求者之前仍要通过授权。一次客户端已取得的副本、截图和离线下载不在服务端可撤回的范围内。

## 一个能区分方案的试验

用 A 管权限、B 读图，在两个独立会话准备同一张已经发布的头像。B 取得地址后暂缓 GET；A 关闭展示并确认保存；B 用原地址进行**第一次**读取，同时用会话向资料 API 再申请。主线方案里可能得到对象 200、申请 404；等同一地址到期后再发才是 403。若改为逐请求鉴权，关闭之后第一次经受保护地址读图就应被拒。每次都重新申请地址的检查，会漏掉两种方案之间最重要的差别。

再把条件换成「A 只撤销 B 的访问，C 仍能看」。一个全账号布尔值已经不能表示结果，得保存谁与谁有访问关系；只要底层还发可转交的持有者凭证，C 依然可能把链接给 B。要判断一张图应由谁读取，必须同时说明授权生效的时刻、执行检查的组件及凭证是否绑定读者。第 51 章选择的是账号级开关配合短期地址，适合接受上述窗口的资料展示。

## 附录：必要技术点速查

| 要求 | 要查的事实 |
| --- | --- |
| 停止签发新链接 | API 查到的当前会话、目标状态和展示设置 |
| 已发链接在指定时间后不能重新使用 | 签名的真实起点、到期时间、存储端校验及客户端实际请求时刻 |
| 撤销后每个新访问都检查权限 | 所有对外读取入口、代理与缓存命中路径 |
| 撤销某位读者或中止长传输 | 关系授权、凭证是否可转交、活动连接与撤销传播时间 |
