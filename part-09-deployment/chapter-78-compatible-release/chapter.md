# 第 78 章　发布、迁移与回退

第 77 章留下了可独立恢复的副本，现在要发布一个改变数据规则的版本。新程序启动成功之后，旧客户端还在发请求，数据库里也已经出现新写入。若此刻退回旧程序，会恢复哪些行为，又会破坏哪些行为？本章在带旧数据的独立副本演练，沿第 23 章的回填问题判断发布边界；正式 EPP 和下部仍沿用中文意图可空的契约，这轮规则实验不直接施加到日常库。

第 68 章用摘要确认接收端取得了验过的制品，并在兼容数据上验证旧包能运行。本章继续使用这些产物，改变的是数据规则与写入条件：即使旧包的字节完全没变，面对新约束和新版留下的数据，也要重新验证每种读写请求，才能确定回退范围。

## 78.1 发布同时移动三种版本

设练习需求改为“今后保存的当前记录必须有中文意图”，历史修订保留当时原意。先重发旧客户端的两种请求：省略意图、显式清空意图。它们过去可能合法，新规则却需要区分“没有提供新值”和“要求清空”。不能仅在数据库加 NOT NULL，再让旧请求全部变成 500。

每次发布至少记录三组版本。程序版本是原生 release 的摘要或容器镜像摘要；配置版本包括端点、角色、公开来源和签名密钥的版本标识；数据版本包括迁移历史、已回填范围和当前约束。密钥不记明文。相同镜像连到不同库、使用不同配置，可能表现完全不同；相同数据库结构也可能处于不同回填进度。

原生部署过去分别交付 Node、运行库与 release；容器将其中一部分固定在镜像中，减少目标机重复安装与漂移。它没有把配置、数据迁移或第三方投递封进镜像。换镜像仍须回答“它能读当前库吗”，而不是仅问“这个镜像昨天能启动吗”。

## 78.2 先让新旧程序有一段共同适用期

在第 77 章建立的发布副本上，先保存旧客户端请求、旧记录与历史修订。准备过渡版：读取时继续接受旧 NULL；写入时明确新规则的错误响应，省略字段时按既定更新语义保留原值。公开错误码和字段含义要先让调用方能够理解，再决定何时停止接受清空请求。若过渡期必须保留旧写入行为，就不能提前声称新规则已对全部记录成立。

这一阶段数据库仍可空。先验证过渡版读取旧值、旧客户端读取新版响应，以及新旧写入方并存时的实际行为。API 之外的导入脚本、维护 CLI 和后台任务也属于写入方，不能只升级页面。固定旧程序和过渡版的产物、配置与预期迁移状态，在隔离副本完成演练后才安排正式切换。

迁移由独立身份执行一次，留存成功结果与校验记录，不能让每个应用容器启动时抢着执行。应用登录仅拥有业务权限，不能因为“迁移方便”给它 owner 权限。若迁移失败，先查数据库实际状态；没有成功记录就不能继续将流量导向依赖它的新程序。

## 78.3 分批回填，再收紧约束

回填不是给所有 NULL 随意塞一个占位词。按第 23 章及 23A 的条件更新方法，从可信来源取得意图，只更新仍符合缺值条件的当前记录；每批保留处理范围、成功数量与未解决项。更新条件须在数据库执行时再次判断，避免覆盖用户刚写的新意图。历史修订保留原值，不能为了满足当前规则批量改写过去。

遇到没有可信来源的记录，保留原值并说明新规则尚未对它成立；可以暂停那部分修改、要求用户补齐或继续支持兼容读取，由需求决定。不能为了完成迁移报告编造内容。另取一份所有缺值都可溯源的练习副本，完成回填后才演练整列约束收紧。

最终约束前要停止旧的清空写入方，建立数据库层的新写入保护，再扫描和补齐遗留缺值。若只先查“缺值为零”，旧程序可能在查询后、加约束前重新写入 NULL。采用第 23 章的分阶段约束方案时，分别记录新行保护、历史验证和最终约束状态；约束验证也有锁与资源成本，应设置等待预算并观察，不能把超时当作可以直接跳过验证。

由此得到一个具体回退边界：约束收紧前，旧版可能仍可读写；收紧后，它即使能启动和读取，原来的清空请求也会被数据库拒绝。所谓“兼容旧版”必须逐种请求判断。

## 78.4 用两种托管方式完成程序替换

[第 68 章](../chapter-68-artifact-promotion/chapter.md)已经建立按摘要验收、晋级和保留旧制品的方法。这里从已验过的新旧产物开始，把程序切换与前面判定的数据兼容区间接起来。

原生部署保留第 70 章的分权单元。把新版放到新的只读 release 目录，按第 68 章核对同平台产物和摘要，保留旧目录。用受限系统用户验证新入口可执行、配置可读、工作目录可写。不要覆盖正在运行的 release；进程可能仍在读取旧文件，使一次运行混用两份内容。

在 Debian 修改目标单元的 ExecStart，使它指向新的绝对路径，其他身份、工作目录和停止预算保持本轮已验证值。先执行 `sudo systemd-analyze verify /etc/systemd/system/epp72-api.service` 检查定义，再用 `sudo systemctl daemon-reload` 让管理器读取新定义，最后 `sudo systemctl restart epp72-api`。reload 不会替换已有进程，restart 才进入停止与重启。观察旧进程排空、app.stopped、新 PID 和 app.ready，再通过原 HTTPS 入口读旧数据、写入并复读一笔新记录。若超过停止期限被强制结束，不能将命令结束当作平滑切换。

Compose 把同一件事表达为固定镜像与重建服务。第 75.5 节之后，权威部署目录是 `/opt/epp-container`，旧 `/opt/epp74` 副本只作归档。由管理员保存 `compose.env` 中的旧 EPP_IMAGE、Compose 定义和配置版本，再将该文件的 EPP_IMAGE 改为已经验收、平台匹配的新引用。新开 Bash 先固定管理入口：

```bash
dc() { sudo docker compose --project-directory /opt/epp-container --env-file /opt/epp-container/compose.env -f /opt/epp-container/compose.yaml "$@"; }
dc config --quiet
dc config --images
```

先比较输出与本轮交付记录，发现引用不一致就停止，检查是否有管理环境变量覆盖。第 72～73 章本地交付的 `sha256:…` 是**本地镜像 ID**，它不是仓库的 `名称@sha256:…` 引用，不能向仓库 pull 这个 ID。若三个应用角色使用同一镜像，可取得唯一引用并核验：

```bash
new_image=$(dc config --images | sort -u)
sudo docker image inspect --format '{{.Id}} {{.Os}}/{{.Architecture}}' "$new_image"
```

`new_image` 应只有一行，镜像 ID 和平台应与交付记录一致；多行时分别核对角色，不能把它们当成一个引用。缺少本地镜像就按第 72 章 save/load 交付到**当前引擎**后重查，不把 pull 当作替代。只有本轮使用了实际仓库的 `名称@sha256:…` 引用，才先执行 `dc pull api notify` 下载；拉取不会替换已有容器。下载或导入完成后，两种交付都执行：

```bash
dc up -d --no-deps --pull never api
dc ps -a api
dc logs --since 5m --tail 100 api
```

`up -d` 按镜像或定义变化创建服务，`--no-deps` 不启动关联依赖，`--pull never` 只使用刚才核过的本地内容，缺失就失败。这一项目没有 db 服务，数据库仍由宿主管理。[Compose 创建与更新](https://docs.docker.com/reference/cli/docker/compose/up/)

按第 74 章读取新容器的实际镜像 ID，再验匿名探针、旧账号、旧素材、头像以及一笔新写入。API 通过后才用 `dc up -d --no-deps --pull never notify` 更新通知；邮件须先停妥当前发送者，按原 ID 完成投递核查，再决定何时启用新镜像。不能让批量 up 顺便复活因 unknown 停发的邮件。修改挂载配置后也不能仅靠 restart：启动配置要由新进程读取，原子替换文件还可能让旧挂载保留旧 inode，应重建并核对实际身份。

两种方式的单 API 实例都存在不可用窗口。所谓渐进发布是分阶段限制变化、观察结果，并不意味着必然零停机。若需要连续服务，先启动第二个 API、使用独立宿主端口，通过私有入口验证，再切换 nginx 上游并排空旧实例。共享会话、签名密钥、数据库连接预算和两版读写兼容必须事先成立；Compose 的一次 up 不会自动完成这套流量切换。即使进程切换连续，长事务、外部依赖与客户端连接仍须按业务要求处理。

## 78.5 退程序之前，先试旧程序的读写

在发布副本做两次回退。第一次在列仍可空、旧写入语义仍允许时，恢复旧产物或旧镜像，重新执行历史读取、省略和清空请求，检查新版本写入的数据是否仍可理解。第二次在约束收紧后做同一组请求，记录失败位置；不能只用健康探针证明回退成功。

原生恢复旧 ExecStart 后，仍需 verify、daemon-reload 和 restart；容器恢复旧 EPP_IMAGE 后，重新执行定向 up 并核对镜像。两种操作都只退程序，不撤销迁移、邮件投递、对象删除或已经接收的业务写入。若旧版不能写当前结构，应退到已验证的兼容过渡版，或维持停写向前修复。

发布后让新版接收一笔有明确 ID 的新记录，再与发布前备份比较。旧备份没有它；整库还原会覆盖这段新工作，即使 restore 本身成功也有数据损失。若必须还原，先保存事故现场和新增数据，明确接受的损失区间；需要保留新工作时，使用隔离恢复副本定位差异并作定向修复，不能把备份当成撤销按钮。

发布记录最后写明现在运行的程序、配置、数据状态，已验证的客户端请求、仍可回退到的版本以及停止发布的条件。下一班应能据此判断一次失败发生在哪一步，而无需重新猜测标签指向和迁移进度。

## 附录：必要技术点速查

| 动作 | 实际改变与判断 |
| --- | --- |
| systemd daemon-reload／restart | 读取单元定义／替换进程 |
| 仓库 pull／本地 load／up | 下载仓库引用／导入归档／按定义替换容器；本地镜像 ID 不可 pull |
| 过渡版 | 为旧数据、旧客户端与新规则留兼容区间 |
| 回填／约束 | 修复既有值／阻止后续非法写入 |
| 回退程序 | 仍须兼容当前结构与新版已写数据 |
| 整库还原 | 回到旧恢复点，可能丢弃之后的工作 |
