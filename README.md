# EPP 后端开发实践

面向已有 JavaScript、前端开发和前后端联调经验的开发者，从空项目开始，逐步搭建一个公开的 EPP，掌握后端开发与维护。\
围绕 Node.js、Nest、数据库与部署运维，在同一个持续演进的项目中讲清原理、实现与取舍；所需代码随实践逐步编写。\
以下按篇、章、小节展开；阅读路线和前置依赖附在完整目录之后。

## 第三篇 持久化与结构演进：PostgreSQL、SQL、Prisma

**阅读路径**：核心实践。

**起点**：已有能保存原文并查询的内存版 Nest 服务；重启后会丢失数据。

**本篇结果**：为原有功能建立最小表，接入 Prisma 持久化，再给已有记录追加中文意图，完成第一次带数据的结构演进。

**阶段边界**：先用 SQL 建立并理解两张最小表，再将已有结构纳入 Prisma 迁移管理；后续全部沿同一批数据追加迁移，修订与候选尚未创建。

### 第 13 章 PostgreSQL 运行环境：解决重启后记录丢失

- 13.1 重启内存版服务后记录丢失，确定持久化范围仍是原文、ID、创建时间和所属用户。
- 13.2 认识数据库服务、数据库、Schema、表与连接，准备账号和连接串。
- 13.3 本地安装并启动 PostgreSQL，用 SQL 客户端连接，确认服务端口、账号与目标库；解释停止应用与停止数据库服务的区别。
- 13.4 确认目标库；本篇沿同一实践数据库保留已写入数据，破坏性实验另用可丢弃环境。

### 第 14 章 关系建模：为已有记录设计第一组表

- 14.1 从保存和查看自己的记录推导最小用户表、记录表与 userId；固定开发用户由本地初始化写入。
- 14.2 选择 UUID、文本和带时区时间类型，解释主键、非空、默认值与外键。
- 14.3 写出 CREATE TABLE，先说明每个字段来自哪个现有需求，再插入和读取第一条数据。
- 14.4 用一对多关系说明用户与记录的归属；暂不创建修订、候选、表达等后续业务表。
- 14.5 数据库时间与 API JSON 的表示，保证重启后仍可读取此前记录。

### 第 15 章 SQL：查询、筛选和修改自己的记录

- 15.1 沿已有两张表完成增删改查、条件、排序和基础分页。
- 15.2 用用户和记录的 JOIN 获取列表，用聚合、分组与子查询统计记录；观察重复行和 NULL。
- 15.3 参数绑定与动态条件，避免把输入拼进 SQL。
- 15.4 用已有数据解释唯一约束与删除行为；关系变化时再引入新的约束。
- 15.5 通过 SQL 客户端核对当前记录，保留这批数据供 ORM 接入和后续迁移使用。

### 第 16 章 Prisma：将已有表纳入 Schema 与迁移管理

- 16.1 从刚刚手写的 SQL 回看 ORM 解决的问题，区分 Prisma Schema、生成客户端和真实数据库。
- 16.2 对现有最小表做 introspection，核对字段映射、类型、关系与约束；生成运行时客户端。
- 16.3 为现有结构建立初始迁移基线，只有核对结构一致后才标记已有数据库已应用；不重复执行建表。
- 16.4 用空的独立校验库确认初始迁移能重建相同结构，日常实践库和记录继续保留。
- 16.5 介绍开发迁移与部署迁移的不同职责；下一次业务加字段时实际追加迁移。

### 第 17 章 Prisma 与 Nest：让记录接口使用持久化数据

- 17.1 在 Nest 中提供 DatabaseService 与运行时适配器，替换此前的内存存储。
- 17.2 用同一批已有数据库记录调用列表和详情接口，保持公开响应契约一致。
- 17.3 实现写入、字段投影与数据库错误映射；从 ORM 调用回看 SQL。
- 17.4 连接池、连接耗尽与应用关闭时的资源释放。
- 17.5 停止并重启 API，确认此前记录仍可读取；此时形成第一条持久化业务链。

### 第 18 章 Migration：给已有记录增加中文意图

- 18.1 现有记录只有英语原文，现在需要补充中文意图；先确定旧记录允许暂时没有该字段。
- 18.2 修改 Prisma Schema、生成迁移、查看实际 SQL，再应用到保留数据的实践库。
- 18.3 更新写入、修改和查询契约，让新旧记录同时可读；检查接口和数据库中的实际结果。
- 18.4 如果业务以后要求必填：先回填与检查，再收紧约束，不能直接让旧数据失效。
- 18.5 漂移、失败迁移与只能追加历史的原因；生产期间的新旧应用兼容在发布篇进一步展开。

## 第四篇 业务一致性：修订、候选、事务与采纳

**阅读路径**：核心实践。

**起点**：原文、中文意图与记录归属已经持久化；具备 SQL、Prisma 和追加迁移能力。

**本篇结果**：从保留修改历史逐步扩展到候选和正式表达，围绕采纳掌握状态机、事务、并发、幂等与查询优化。

**阶段边界**：先说明新业务和数据关系，再实现其技术保证。候选内容仅用少量示例输入；AI 接入前不创建向量或付费调用。

### 第 19 章 关系演进：从覆盖输入到保留修订历史

- 19.1 用户补充原文或中文意图后，希望还能查看之前的版本；先列出现有记录无法满足的行为。
- 19.2 设计记录与 CaptureRevision 的一对多关系，区分稳定的记录身份与可追加的内容快照。
- 19.3 追加迁移：为每条旧记录生成初始修订，检查数量和字段对应后再切换读取；保留旧字段直至迁移确认。
- 19.4 实现追加修订和历史读取，用 JOIN 展示记录与版本；此时最新修订按序号读取，跨表状态更新在事务章节落实。
- 19.5 新增输入来源与已有 chunks 时，说明旧修订的默认含义；按实际查询需求选择结构化列或 JSON。

### 第 20 章 状态机与关系建模：修订如何进入候选确认

- 20.1 在已有修订上保存多份待确认候选，从用户操作推导状态、事件与非法转移。
- 20.2 新增候选、学习记录、正式表达及形式的最小关系设计：先说明采纳后哪些事实需要保存。
- 20.3 追加候选表迁移；已有修订保持无候选状态，不假设旧数据已经生成或采纳。
- 20.4 保存少量示例候选并实现读取与放弃；采纳先列出所需写入，交给下一章的事务完成。
- 20.5 区分采纳、放弃、未选择与旧修订，明确用户确认绑定的对象。

### 第 21 章 事务 让多次修改成为一次业务动作

- 21.1 沿上一章采纳所需的数据关系，迁移学习记录和正式表达表，再观察多次写入只成功一半的结果。
- 21.2 用数据库事务实现单次采纳，解释提交、回滚与原子性。
- 21.3 隔离级别和读写异常：单次成功不代表并发时仍正确，为下一章提供具体问题。
- 21.4 外部网络请求放进事务的代价；此处只完成数据库写入，不在采纳事务里调用模型。

### 第 22 章 并发控制 两个请求同时到来怎么办

- 22.1 同时采纳同一候选或提交相同表达，观察重复记录和先查后写竞争。
- 22.2 按当前冲突增加唯一约束、条件更新或版本校验；收紧约束前检查并处理已有重复数据。
- 22.3 行锁与事务级 advisory lock：用当前采纳场景解释锁定对象、作用范围和选择理由。
- 22.4 锁顺序、死锁、等待超时与事务重试，明确重新执行的业务范围。
- 22.5 保留用户与表达的锁边界，后续合并和账号处置在相同原则上扩展。

### 第 23 章 幂等与审计：响应丢失后如何安全重试

- 23.1 采纳已经提交，但客户端没有收到响应：区分业务 ID、修订 ID 与本次操作身份。
- 23.2 新增命令／审计记录的必要字段和唯一约束，保存请求指纹与结果。
- 23.3 在同一事务中提交业务修改和操作结果，支持重复请求返回既有结果。
- 23.4 同一身份携带不同内容时返回冲突；旧历史没有操作身份时不伪造可重放结果。
- 23.5 领域审计与运行日志的区别，以及敏感内容的保留边界。

### 第 24 章 一致性整合：完成可靠的候选采纳

- 24.1 串起已有状态、事务、并发与幂等实现，让记录—修订—候选—正式表达闭环运行。
- 24.2 规范化文本、义项身份与 ExpressionForm；追加必要字段和索引，并处理已有表达的回填。
- 24.3 采纳、放弃、未选择、旧修订与重复操作的统一行为；保留原学习记录来源。
- 24.4 回顾本项目已经建立的模型与接口，说明后续接入生成、语义推荐和向量能力的位置。
- 24.5 新旧记录同时参与读取，不通过清空数据库掩盖模型演进问题。

### 第 25 章 构建可供客户端使用的查询接口

- 25.1 从已有学习记录和正式表达提供基础星图、记录列表与详情，先给出有上限的简单列表。
- 25.2 定义存储模型与公开响应、字段白名单、用户范围和关系查询。
- 25.3 随着记录增多，明确调用方需要的筛选和翻页行为；下一章扩展分页契约。
- 25.4 用最小调用页面或 HTTP 请求观察旧记录与新增记录，界面实现不成为额外前置。

### 第 26 章 分页与时间 容易低估的数据问题

- 26.1 在上一章列表上加入 Offset 和 Cursor 分页，比较同时间戳和并发插入时的行为。
- 26.2 为稳定排序选择字段与唯一补充键，解释游标携带查询条件的校验；签名实现使用到的 HMAC 在本节就地说明。
- 26.3 旧调用方的默认分页行为与响应兼容，避免接口升级后无法读取。
- 26.4 UTC、时区、数据库时间类型与自然日；用实际记录的日期边界说明，练习计算在练习篇应用。

### 第 27 章 索引与执行计划 查询为什么变慢

- 27.1 从已经写出的列表和详情查询解释索引收益与写入成本。
- 27.2 单列索引、联合索引、过滤与排序。
- 27.3 用 EXPLAIN 观察查询计划和数据量变化。
- 27.4 识别 N+1 查询、过量返回与连接占用；任务领取和向量索引在各自业务再应用。
- 27.5 将选定索引写入追加迁移，在现有数据上比较执行计划；不只在全新的空表上观察性能。

## 第五篇 让服务认识用户：身份、会话与权限

**阅读路径**：核心实践。
