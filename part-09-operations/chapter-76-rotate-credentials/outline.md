# 第 76 章 让 API 和后台进程更换凭据与签名密钥

**教学规划**　接在第 74 章「运行环境变了，怎样交付同一份服务」之后。

## 76.1 盘点哪些进程还会以旧身份重连

沿用 API、邮件、通知及一次性命令，记录各角色的数据库登录名、授权来源、连接池、托管定义和配置加载时机。选一项由多进程使用的数据库访问能力，准备新的登录身份并给予相同的必要权限；若已有角色分隔，逐个角色配对，不重新合并权限。保留现有连接作为对照，并保存本轮未完成的业务 ID。再追 CURSOR_HMAC_KEY 的两个使用处：API 用同一把密钥验证分页游标，也按会话 ID 生成、核验 CSRF 令牌。事先保存一份仍有效的 Cookie、旧游标和 CSRF 令牌，全程仅在私有客户端保存。

## 76.2 先切一个进程并迫使它新建连接

将新秘密经各自受限配置交给一小部分实例，采用前台就绪与业务探测核实新登录身份。故意使用缺少必要授权的新角色复现认证成功、业务 SQL 拒绝，补齐授权或在旧身份仍可用时退回。用带不同 application_name 的会话和数据库活动核对哪些进程仍在用旧连接，日志仅记录身份与版本标记。另设两台共用同一库、同一公开 Origin 的 API，故意让 B 漏换 HMAC 密钥。旧 Cookie 在 A、B 读取本人身份都应得 200；在 A 取得新 CSRF 后，以同一 Cookie 和正确的 Origin、显式请求头向 B 发 POST /captures，应得 403/CSRF_REJECTED，库中没有那条素材。将 A 签发的新游标拿到 B 再取一次，分别查明两种失败为何同源。

## 76.3 轮流排空其余角色

另一个 API 继续承接读取，当前实例完成在途请求后更换配置并重启。通知 Worker 完成或交还当前工作，邮件 Worker 先按已有通道占用和尝试结果决定能否重启。当前实现每个进程只接受一把 HMAC 密钥。计划轮换时先备好全部新配置，在短维护窗口排空旧 API，切换并逐台核验后再对外接流。让读者实际重取 CSRF、从首页重新分页，在两个实例间交叉读写；数据库会话仍有效时无需仅为换签名密钥重新登录。把离线的单笔工具和计划任务也换好，用同一旧收据、两类新业务任务和一次新连接验证每个使用者。

## 76.4 撤掉旧登录后验证故障边界

在练习库先禁止旧身份新登录，分别观察旧池中已建立的一条连接和全新登录，再按已知应用逐步排空旧连接。预留一个停着的旧配置命令，启动时应认证失败，切换配置后可运行。若按密钥已泄露演练，先摘除所有仍接受旧签名的实例，包括漏换的 B，切新后从每个端点验证旧 CSRF 和旧游标都被拒绝；修复只向前，回退代码也不得恢复已泄露密钥。若泄露的是数据库密码，禁止旧登录后还需逐一终止可能失陷的旧会话。交接旧角色最后会话、撤销时刻和撤销前后不同的回退条件。后续容器运行时仍按进程刷新。本章为轮换规划，授权、双身份共存和撤销验证尚待执行。
